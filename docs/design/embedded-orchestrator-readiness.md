# Embedded Orchestrator Readiness (epic #1636 Phase 6 study)

Study note for Issue [#1735](https://github.com/ms2sato/agent-console/issues/1735), epic [#1636](https://github.com/ms2sato/agent-console/issues/1636) Phase 6 ("run a real Orchestrator session on an embedded worker end to end"). Design only: no code, no schema, no smoke, no billed run. Every claim below was read at `origin/main` **`a59fc303`** (2026-09-17) and is cited as `file:line` at that SHA; the Architect's AC anchors were read at `70b37753` and were re-verified here one by one. This document will be rewritten or retired after Phase 6 has run: it is a study of one CONSUMER of the embedded worker (the Orchestrator skill), not part of the worker's spec.

Why `docs/design/` and not a section of `embedded-agent-worker.md`: that document specifies the worker; this one maps a skill's procedure onto it, names the blockers, and scripts a run. Mixing the two would make the worker's spec carry a consumer's transient readiness state. `embedded-agent-worker.md` got one pointer sentence (Memory layer, Non-goals). `docs/glossary.md` gets no entry: "readiness table" and "run plan" are not domain concepts and this study coins no term.

## Context

The Orchestrator skill (`.claude/skills/orchestrator/`) was written for, and has only ever run on, a TUI Claude Code worker: a PTY `agent` worker with the full Claude Code tool set (Bash, EnterWorktree/ExitWorktree, TaskCreate, Task subagents, WebFetch/WebSearch, Chrome DevTools MCP when configured) plus the `agent-console` MCP server. Phase 0 of the epic ([#1637](https://github.com/ms2sato/agent-console/issues/1637), first live observations recorded on [#1636](https://github.com/ms2sato/agent-console/issues/1636#issuecomment-5656530213)) showed an embedded `claude-sdk` DELEGATE completing a real Issue end to end and surfaced three facts that bear on an embedded ORCHESTRATOR: it had no identity in its environment (filed as [#1694](https://github.com/ms2sato/agent-console/issues/1694)), it lacked the process discipline PTY delegates receive in their dispatch prompt, and auto-resume after a server restart is a real recovery path.

Phase 6 is not dispatchable until every step the skill prescribes has been mapped onto what the builtin definition can do today. That map is the [Readiness table](#readiness-table). Its first real finding is that **inbound `[inbound:*]` notifications never reach an embedded-agent worker** ([F5](#f5-designation-works-inbound-delivery-does-not)), which is also the first Issue to file.

## Facts the table is built on (re-verified at `a59fc303`)

### F1. Tool surface of the builtin: no Bash, no EnterWorktree, no Task, no browser

- `packages/server/src/services/embedded-agents/claude-sdk-builtin.ts:75` -- `enabledTools: ['Read', 'Glob', 'Grep', 'TodoWrite', 'Write', 'Edit']` (explicit literal since [#1724](https://github.com/ms2sato/agent-console/pull/1724)). `Bash` deliberately stays off (`:73-74`, pointing at [#1045](https://github.com/ms2sato/agent-console/issues/1045)).
- `packages/embedded-agent/src/sdk-engine.ts:599` -- the SDK `tools:` allowlist is built from that literal; `:576` appends the in-process `Compact` tool; `:604` hard-codes exactly two MCP servers (`agent-console`, `console`), so no external MCP server (Chrome DevTools included) is reachable until [#1726](https://github.com/ms2sato/agent-console/issues/1726) lands declared servers; `:630` `permissionMode: 'bypassPermissions'`; `:633` `settingSources: []`; `:648` `settings: { autoCompactEnabled: <worker toggle>, autoMemoryEnabled: false }`.
- `docs/design/embedded-agent-sdk-engine.md:130` -- WebFetch / WebSearch / Task are withheld on the SDK arm by ruling; `Task` is [#1726](https://github.com/ms2sato/agent-console/issues/1726) D3's owner decision.
- `EnterWorktree` / `ExitWorktree` / `TaskCreate` are Claude Code TUI tools and do not exist in the SDK allowlist. `TodoWrite` is served in-process (`sdk-engine.ts:197-198`) and stands in for `TaskCreate`; `SKILL.md:69` already sanctions the memo-checklist fallback.
- **Consequence for every shell step below.** `gh`, `git`, `bun run test`, `node .claude/skills/orchestrator/*.js`, `./scripts/upload-qa-screenshots.sh`: reachable ONLY through the `run_process` / `write_process_response` MCP pair. `run_process` accepts an embedded-agent caller (`packages/server/src/mcp/mcp-server.ts:1786-1789`, `canReceiveNotifications`), runs the command through `sh -c` as the session's spawn user (`packages/server/src/services/interactive-process-manager.ts:145`; `mcp-server.ts:1808-1812` resolves `createdBy`), and routes stdout back through `SessionManager.deliverWorkerNotification` (`packages/server/src/app-context.ts:509-510`), which for an embedded worker means `sendSystemNotification` (`packages/server/src/services/session-manager.ts:872-877`). The PTY echo of a `write_process_response` is a silent no-op for an embedded worker (`interactive-process-manager.ts:234-240` -> `session-manager.ts:1451-1453` -> `packages/server/src/services/worker-lifecycle-manager.ts:1766-1771` returns `false` for a non-PTY worker), so the response text is not mirrored into the transcript; the response still reaches the script's stdin (`interactive-process-manager.ts:244-245`). Cosmetic only.

### F2. Identity: the builtin has no source for its own ids today

- The openai-api arm's system prompt states `Session ID` / `Worker ID` / `Repository ID` in `buildPreamble` (`packages/embedded-agent/src/system-prompt.ts:274-290`). The SDK arm's `composeSdkSystemPromptAppend` (`:382-391`) renders `renderInstructionsBody` plus the definition prompt and deliberately omits the preamble (`:372-374`, "the SDK engine uses the SDK's own preset preamble"). With no Bash (F1), a builtin worker therefore has **no identity source at all** -- exactly [#1694](https://github.com/ms2sato/agent-console/issues/1694) C5.
- Every tool that takes the caller's OWN ids needs one: `set_orchestrator_session` (`mcp-server.ts:548`), `clear_orchestrator_session` (`:602`), `send_session_message.fromSessionId` (`:737`), `delegate_to_worktree.parentSessionId` / `parentWorkerId` (`:955-970`, required and non-empty at the time of this study; optional-with-token since #1696), `create_timer` / `create_conditional_wakeup` session + worker ids, `run_process.sessionId` / `workerId` (`:1749-1755`). Two more in this study's own list are NOT self-identity defaults and stay explicit and unchanged under #1696: `write_memo.sessionId` (`:1381`, the caller's own session, still required) and `write_review_annotations.sourceSessionId` (a git-diff worker's session, never the caller). `set_agent_parameters` is the one tool that already defaults to the bearer identity (`:2426-2430`), the precedent [#1696](https://github.com/ms2sato/agent-console/issues/1696) generalises.
- **Why `list_sessions` self-identification is not credited as a workaround.** The Phase 0 delegate self-identified by matching its title in `list_sessions`. `checkCallerOwnsSession` (`packages/server/src/mcp/mcp-auth.ts:244-250`) compares `claimed.createdBy === caller.userId` -- it binds the token to a USER, not to a session. A mis-identified id that belongs to another session of the same user (on the production host, the TUI Orchestrator's own session) is therefore ACCEPTED, and the call lands on the wrong session: `delegate_to_worktree` would make the delegate report to the TUI Orchestrator, `set_orchestrator_session` would designate the wrong session, `write_memo` would overwrite the wrong memo. A workaround whose failure mode is silent and cross-session is a bypass, not a workaround. Rows that need the caller's own ids are therefore **`blocked -> #1694`** until C5 merges; then they flip to **works via workaround** (the model restates ids it read from the preamble; the same-user acceptance above is the residual cost), and [#1696](https://github.com/ms2sato/agent-console/issues/1696) (token-derived defaults, bound to the token's session) turns them into **works**. That binding is #1696's territory; no separate Issue is filed for the same-user observation, it is cited there.
- `delegate_to_worktree` accepts an embedded-agent PARENT worker (`mcp-server.ts:1137-1141`, `canReceiveSessionMessages`), so once the ids exist, delegation from an embedded caller needs no server change.

- `packages/server/src/mcp/agent-operations-embedded.ts:22-31` -- `addWorkerToSession` and `manageDefinitions` are NOT exposed to embedded callers. Checked against every skill step: none needs them. Confirmed no gap.

### F4. Instruction, rules, skills and memory layers: how the skill text reaches the model

- `loadInstructions` (`system-prompt.ts:1287`) runs on both engines; the SDK arm composes its `systemPrompt.append` from the same result (`:382-391`). The unscoped `.claude/rules/*.md` files (the rules this repo auto-loads for a TUI session: `workflow.md`, `test-trigger.md`, `pre-pr-completeness.md`, `glossary-maintenance.md`, `design-principles.md`, ...) are loaded eagerly under `RULES_LAYER_CAP_BYTES` (`:71`, 160 KiB default).
- **Skills reach the model as an index, then `Read`.** `loadSkillsLayer` (`:976-1017`) discovers every `.claude/skills/**/SKILL.md`, parses `name:`/`description:` frontmatter, and emits ONE line: `Skills available (open the named SKILL.md to read full instructions): ...` (`:1003-1007`), capped by `SKILLS_LAYER_CAP_BYTES` (`:87`, 16 KiB default). The full text of `orchestrator/SKILL.md`, `sprint-lifecycle.md` and `core-responsibilities.md` reaches the model only when it `Read`s them (native SDK `Read`, in `enabledTools`). **`Required Skills (auto-load)` (`SKILL.md:10-14`) does NOT auto-load**: there is no mechanism behind that heading on either surface -- on the TUI it is Claude Code's own skill listing plus the model's judgment, on the builtin it is the same index line plus four more `Read`s (`test-standards`, `code-quality-standards`, `ux-design-standards`, `architectural-invariants`). Same shape, one more hop per skill.
- **Memory layer (Phase 2).** The builtin's memory is the server-owned `memoryDir` keyed by (definition, repository): `packages/server/src/lib/session-data-path-resolver.ts:73-80`. Its header and the `MEMORY.md` index convention (`system-prompt.ts:1034-1052`) are the TUI's auto-memory convention adopted verbatim precisely so the Orchestrator skill's memory instructions transfer unchanged (`docs/design/embedded-agent-worker.md:882-886`). The WRITE half is live on the builtin since [#1724](https://github.com/ms2sato/agent-console/pull/1724) (F1). **What does NOT transfer:** the TUI Orchestrator's existing files (`memory/project_sprint_status.md`, `memory/project_architect_handoff.md`, `MEMORY.md`, the `feedback_*` files) live in Claude Code's auto-memory directory for the source-repo path, which is a different store; the layer never reads it by design (`embedded-agent-worker.md:947`, `:949`: "Phase 6 decides whether to seed from it, and how"). Every skill step that says "update `memory/<file>`" therefore resolves, on the builtin, to the Phase 2 `memoryDir` -- a fresh, empty store on the first run. This is where the Phase 0 item-2 discipline (host test-slot request, stale-base rebase) lives for the TUI Orchestrator (`memory/feedback_*.md`) and where it is ABSENT for an embedded one; the skill-listed steps themselves come from the skill text (`Read`), and `delegation-prompt.js`'s hygiene block (`.claude/skills/orchestrator/delegation-prompt.js:148`) still reaches the delegates an embedded Orchestrator dispatches, because the block is part of the `prompt` argument and an embedded delegate receives the same text as its `initialPrompt` (`mcp-server.ts:1225`).

### F5. Designation works; inbound delivery does not

- `set_orchestrator_session` (`mcp-server.ts:539-596`) accepts any worktree session with a `createdBy` (`:558-563`); [#1716](https://github.com/ms2sato/agent-console/issues/1716)'s set model adds the caller alongside the TUI Orchestrator. Nothing there is worker-kind-specific. Designation: **works** once the caller knows its own session id (F2).
- **Inbound delivery to an embedded worker: BLOCKED.** `packages/server/src/services/inbound/handlers.ts:50-52`:

  ```ts
  export function canDeliverToAgentWorker(session: Session): boolean {
    return session.workers.some((worker) => worker.type === 'agent');
  }
  ```

  The embedded worker's discriminant is `type: 'embedded-agent'` (`packages/shared/src/types/worker.ts:24`), so a designated session whose only agent-shaped worker is embedded fails this predicate. `resolve-targets.ts:226` (the designated-session fallback, [#1661](https://github.com/ms2sato/agent-console/issues/1661)) and `resolve-targets.ts:333` (`issue:labeled` routing) both `continue` past it, logging "the designated orchestrator session has no agent worker to deliver to". The same predicate gates whether a delegate's parent counts as a live target (`resolve-targets.ts:100`). Even if routing were widened, `AgentWorkerHandler.handle` (`handlers.ts:102-105`) resolves `workerId` from `type === 'agent'` only and delivers through `writePtyNotification` + `sessionManager.writeWorkerInput` (`handlers.ts:118-131`), a PTY-only write (`worker-lifecycle-manager.ts:1766-1771` returns `false` for a non-PTY worker) -- NOT through the `deliverWorkerNotification` seam that timers, wakeups, session messages and process output already use for embedded workers (`session-manager.ts:841-880`; `app-context.ts:425`, `:470`, `:509-510`). So `issue:labeled`, `ci:completed`/`ci:failed`, `pr:merged`, `pr:review_comment`, `pr:changes_requested`, `pr:comment`: none reaches an embedded Orchestrator today, and none reaches an embedded DELEGATE either. Issue to file: [I-1](#issues-to-file).
- **Resolved by [#1739](https://github.com/ms2sato/agent-console/issues/1739) (PR [#1742](https://github.com/ms2sato/agent-console/pull/1742)):** `canDeliverToAgentWorker` is `session.workers.some(canReceiveSessionMessages)` (PTY agent or embedded-agent) and `AgentWorkerHandler.handle` delivers its unchanged params through `SessionManager.deliverWorkerNotification`, whose embedded branch activates a dormant worker (`ensureDeliverable`) before delivering the event as an `inbound-event` system-notification turn; the routing sites are untouched. Verified end-to-end by scenario 4c / 5-E of `scripts/smoke/check-webhook-issue-label-routing.ts` (an embedded-only designated session E, woken by the event). The text above is kept as the record of what was found at `a59fc303`.

### F6. Notification delivery to an embedded worker (everything except inbound): works, with one shape to know

- `deliverWorkerNotification` (`session-manager.ts:841-880`) branches on worker kind and routes embedded workers to `sendSystemNotification` (`packages/server/src/services/embedded-agent-worker-service.ts:1431-1441`): the notification becomes an ordinary user turn persisted with a `notification` marker. Timers (`app-context.ts:425`), conditional wakeups (`:470`), `send_session_message` (`mcp-server.ts:847`, `:870`) and `run_process` output (`:509-510`) all go through it.
- **R3 mid-turn queue.** A notification arriving while a turn is active is parked (`embedded-agent-worker-service.ts:1452-1467`, cap `MAX_PENDING_NOTIFICATIONS = 32` at `:237`) and delivered ONE per `state: idle`. For the acceptance check this means: the script's next question arrives only after the model ends the turn in which it called `write_process_response` -- one turn per Q, twelve or so turns per check. A TUI worker sees the same shape (the PTY notification is a new prompt), so this is parity, not a cost, but a Phase 6 Orchestrator that keeps calling tools inside one turn will not see the next question until it stops.
- **Activate-on-delivery.** `ensureDeliverable` (`:1659-1692`) awaits a running eviction, then `activate`s a dormant worker before delivering, so a timer tick or a session message wakes an evicted or restart-dormant Orchestrator.

### F7. Long-session behaviour: compaction and idle eviction

- Compaction on the SDK arm is the SDK's own auto-compaction driven by the per-worker `autoCompaction` toggle (`packages/shared/src/types/worker.ts:41`; `sdk-engine.ts:648`; live toggle at `:784-786`); the `Compact` tool is always present (`:576`). The restore-boundary usage seed applies to openai-api only. Measured by `scripts/smoke/probe-sdk-compaction.ts` (P1a: the setting arrives) -- what compaction does to a long ORCHESTRATOR conversation is not measured anywhere and is Phase 6's to observe.
- Idle eviction applies to `claude-sdk` (`isEvictableEngine`, `embedded-agent-worker-service.ts:475-477`) after `EMBEDDED_AGENT_IDLE_EVICTION_MS` (`packages/server/src/lib/server-config.ts:293-296`, 30 minutes default). Resume passes `init.resume.sdkSessionId` to the SDK (`sdk-engine.ts:370-377`; `packages/embedded-agent/src/main.ts:613`), so the CONVERSATION survives (measured: `scripts/smoke/check-embedded-agent-idle-eviction.ts`, nonce recall on the same SDK session id; `check-fatal-incarnation-replacement.ts` for the crashed-engine case; `check-restart-all-embedded.ts` for restart-all). **What an Orchestrator keeps across an eviction:** the SDK conversation; every timer and conditional wakeup (server-side, unaffected by the worker's process); the designation (a repository row). **What it loses:** the in-process `TodoWrite` list (served by the subprocess, `sdk-engine.ts:197-198`; the transcript still records the calls, the tool's store is fresh -- unmeasured, Phase 6 observes); scoped-rule activation state, so a scoped rule may be delivered a second time (`embedded-agent-worker.md:777`, accepted cost).

### F8. Server restart: the behaviour split that decides the run plan's "what survives" row

- **Timers persist and are restored at boot.** `packages/server/src/services/timer-manager.ts:72-81` saves each timer through `TimerRepository`; `app-context.ts:456-457` calls `restoreTimers()` at startup. A restored timer's tick calls `deliverWorkerNotification` -> `ensureDeliverable`, which activates the dormant worker (F6).
- **Conditional wakeups are in-memory and die with the server.** `packages/server/src/services/conditional-wakeup-manager.ts:67-68` (`private wakeups = new Map()`); `app-context.ts:459` ("in-memory, volatile"). `list_timers` (`mcp-server.ts:1717-1735`) lists timers only, so the model cannot even enumerate lost wakeups after a restart.
- **No auto-activation unless an `initialPrompt` is still undelivered.** `packages/server/src/services/session-pause-resume-service.ts:308-320` activates a revived embedded worker only when `hasUndeliveredInitialPrompt` holds ([#1264](https://github.com/ms2sato/agent-console/issues/1264); `embedded-agent-worker.md:574`). That is exactly the [#1637](https://github.com/ms2sato/agent-console/issues/1637) case the Phase 0 comment recorded as "auto-resume": a delegate whose worker died at spawn, prompt never delivered. An Orchestrator whose prompt WAS delivered stays dormant after a restart until a message, a restored timer tick, or a browser opening it activates it -- and then the SDK session resumes.
- **Designation and the inbound-notification ledger did NOT survive a restart before [#1762](https://github.com/ms2sato/agent-console/issues/1762).** `SessionInitializationService.initialize()` persists the session set through `SqliteSessionRepository.saveAll()`. At `a59fc303` that method ran `DELETE FROM sessions` (no `WHERE`) then re-inserted every session inside one transaction; with `PRAGMA foreign_keys = ON`, that `DELETE` cascaded through `repository_orchestrator_sessions.session_id` (`ON DELETE CASCADE`, v41) and `inbound_event_notifications.session_id` (`ON DELETE CASCADE`, v11), silently wiping the repository's Orchestrator designation and every pending inbound-event delivery on every server restart, even though the session row itself survived. [#1762](https://github.com/ms2sato/agent-console/issues/1762) replaced the delete-all with a per-row upsert plus a delete-only-of-the-sessions-actually-absent, so both dependents now survive a restart along with the session row.
- Verdict for "survives a server restart": **works via workaround** -- keep one standing self-check timer (already prescribed by `core-responsibilities.md:63`) as the wake-up path, and treat every conditional wakeup as lost after a restart. Cost: a wait that rests only on a conditional wakeup (the pattern `core-responsibilities.md:76-80` recommends over timers) waits forever across a restart, and nothing tells the model a restart happened.

### F9. Process discipline for the embedded Orchestrator itself

Phase 0 item 2 asked where the delegation-prompt discipline comes from when the Orchestrator has no dispatch prompt. Answer, by reading: the skill-listed steps come from the skill text via the skills index + `Read` (F4); the hygiene block still reaches delegates through `delegation-prompt.js` (F4); the TUI-only lessons stored in `memory/feedback_*.md` do not reach it (disjoint store, F4). The run plan below therefore delivers the two Phase-0 items (host slot request, stale-base check) in the run's own scripted message rather than assuming they are anywhere the builtin can read, and records "seed or not" as a Phase 6 observation, not a pre-decision.

## The tension: a Bash-less builtin, `run_process`, and #1045 Layer 1

Stated, not resolved.

- **What the skill needs.** By the table, every shell step of the Orchestrator's procedure (`gh`, `git`, `bun run test`, `preflight-check.js`, `acceptance-check.js`, `sprint-retro.js`, `suggest-criteria.js`, `brew-invariants.js`, `delegation-prompt.js`, the schema merge-tree check, `upload-qa-screenshots.sh`) is reachable on the builtin only through `run_process` + `write_process_response`. Roughly half the procedure (26 of the 43 blocked rows have `run_process` as their carrier, 23 of them as the sole one) depends on that pair. Section 6 of `core-responsibilities.md` (`:194-198`) already prescribes the acceptance check this way for the TUI Orchestrator too -- it is the one step DESIGNED for the pair.
- **What #1045 Layer 1 wants.** [#1045](https://github.com/ms2sato/agent-console/issues/1045) (open) rules that MCP tool visibility be filtered per caller kind, with the default embedded-agent allow-list "extremely restrictive (exclude `run_process`, `run_process_read`, similar arbitrary-execution tools)". The Architect's own note there records that `run_process` is ALREADY the arbitrary-execution surface an embedded caller has today (`mcp-auth.ts:234-268`, ownership only, no caller-kind filter -- verified). As of `a59fc303` nothing of Layer 1 has landed.
- **The two ways a Phase 6 Orchestrator definition can exist once Layer 1 lands.** (a) A user-created `claude-sdk` definition with `Bash` opted in -- which does not exist yet: `createEmbeddedAgent` hard-codes `engine: 'openai-api'` and the only `claude-sdk` definition is the code-declared builtin ([#1726](https://github.com/ms2sato/agent-console/issues/1726) fact 2; `claude-sdk-builtin.ts:9-12`). That is #1726's D1 owner decision. (b) `run_process` kept visible for that caller -- a caller-kind exemption or an allow-list entry, decided WITH #1045, not here.
- **Recommendation for the Phase 6 run: `run_process`, on the builtin as it is.** Reasons: it is what section 6 already prescribes; it keeps the builtin's tool policy unchanged (no Bash-on-the-builtin decision is pre-empted); the run then measures the procedure the skill actually writes down rather than a Bash-shaped variant of it; and Layer 1 has not landed, so nothing has to be exempted for the run to happen. The run does NOT pre-empt the owner's decision on D1 (whether a Bash-enabled `claude-sdk` definition should exist) nor #1045's decision on whether embedded callers keep `run_process` by default -- both stay open, and the Phase 6 result is an input to each: if the run shows the pair is workable for a full procedure, that is evidence for (b) as the Orchestrator's shape; if it shows the one-question-per-turn shape (F6) or the missing transcript echo (F1) is disabling, that is evidence for (a).
