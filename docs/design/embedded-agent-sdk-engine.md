# Embedded Agent SDK Engine

Status: **Draft — normative once merged.** Owner request 2026-08-16 (Issue #1324, owner-designated high priority); design settled 2026-08-17 through Architect/Orchestrator consultation, five owner answers, three empirical probes, and one owner re-acceptance (the memory trade, §2.1). This is a **sibling** to `embedded-agent-worker.md` Part II, not an amendment of it: the two engines are siblings, and the existing engine's normative text is untouched by this document.

## 1. Motivation

**The decisive motivation is authentication, not memory.** Talking to the Messages API directly requires an API key, which forces the product to care about the subscription-vs-API-key distinction at the configuration layer. The Claude Agent SDK removes that fork: the SDK-hosted subprocess runs as the executing user (through the existing `spawnAsUser` harness) and picks up that user's own claude authentication natively — the same auth the user already has for their terminal Claude Code workers. Vendor authentication stays outside the system's scope entirely (see #1325's correction to `shared-orchestrator-session.md`).

A raw Anthropic Messages adapter behind the existing per-turn `ProviderAdapter` interface is **explicitly out of scope** (owner decision, Q5). That interface remains the right shape for such an adapter if one is ever wanted; this feature is not it.

### 1.1 Memory: an accepted cost, not a benefit

The initial memory motivation **reversed under measurement** (all figures from the 2026-08-17 probes, recorded on #1324):

- The SDK's bundled `claude` binary is **byte-identical** (`sha256`) to the installed CLI — the same 307 MB process image, not a lighter runtime.
- Peak RSS per process: bare `claude -p` ≈ 355 MB; SDK-spawned child ≈ 358–360 MB. (The probe's +89 MB "SDK host" was a Node harness artifact — see §3's runtime note; the SDK library loads into the existing Bun subprocess, which in SDK mode also sheds the loop/provider/tool modules.)
- The existing custom-loop engine measures **92 MB baseline + ~350 KB/turn**.
- **Fleet totals use PSS, not RSS** (correction, 2026-08-17, #1332): RSS counts shared pages once per process, and N copies of the same 307 MB binary share their text segment (~160 MB shared per process measured on the live host; PSS 2.13 GB vs RSS 2.60 GB across the readable fleet). `VmHWM` cannot be decomposed into shared/private, so per-process peaks must never be summed into fleet claims. **The marginal cost of one more `claude` process on a host already running some is ~195 MB**, and that is the number that answers "what does one more SDK-engine worker cost".

Two framings, both true and both required wherever this trade is discussed: (a) an SDK-engine worker costs a multiple of a custom-loop worker (~195 MB marginal vs ~92 MB baseline, and ~355 MB peak when it is the only claude on the host); (b) an SDK-engine worker costs **about what a Claude Code TUI worker already costs** — and the 92 MB loop was never available for Claude-without-an-API-key, which is this feature's entire point. The cost is **per-Claude-SDK-worker, not a fleet conversion**: only definitions with the SDK engine discriminant pay it; OpenAI-compatible embedded agents stay on the custom loop.

**Owner re-acceptance (2026-08-17), recorded**: *embedded Claude costs TUI-Claude memory rather than custom-loop memory, and we accept that to remove the API-key fork.*

## 2. Terminology

- **Engine**: the in-subprocess machinery that turns user messages into NDJSON events — the conversation loop, tool execution, and provider communication as one unit.
- **Native-loop engine**: the existing stack — `agent-loop.ts` + `providers/` + `tools/` + `mcp.ts`. Untouched by this document.
- **SDK engine**: a new sibling module hosting a Claude Agent SDK session inside the same subprocess harness.

## 3. The seam — where the fork lives, and where it deliberately does not

**The seam is the existing host↔subprocess stdio/NDJSON protocol, not a new interface.** That protocol is already the single writer of "what an embedded worker means" to everything above it — server lifecycle, output persistence, restore-info, UI events all speak it. The engine fork lives inside the subprocess, at `main.ts`: the init command selects an engine, and both engines emit the **same event vocabulary** upward. Nothing server-side learns a new concept.

**Runtime: the SDK runs in the existing Bun subprocess — never a separate Node host.** The SDK's typed options include `executable?: 'bun' | 'deno' | 'node'` (auto-detected when unspecified) and the package ships Bun-aware loading; the engine passes `'bun'` explicitly rather than trusting auto-detection. The 2026-08-17 probe's +89 MB Node host process was a harness artifact, not an SDK requirement — an implementer who reaches for a Node sidecar pays 89 MB for nothing and adds a process the lifecycle machinery would have to manage.

What this rules out, with reasons:

- **SDK-as-a-provider** (behind `ProviderAdapter`) — rejected. `ProviderAdapter.run()` is a single model turn; `agent-loop.ts` owns tool execution and the next-turn drive. The Agent SDK owns the loop and tool execution itself, so slotting it behind a per-turn interface means either discarding the SDK's loop or fighting its design. The per-turn interface stays what its header says it is: the shape for a future raw Messages adapter (out of scope, §1).
- **A new worker kind** — rejected. The embedded worker's server-side machinery (persistence, epoch/resync, delivery obligations, UI surfaces) is engine-generic; a new kind would re-open every Q11 surface question for no gain.

### 3.1 Engine selection: a structural discriminant, never inference

The engine is **not user-facing configuration**. There is nothing to choose: for Claude, the SDK is the only embedded path (Q5 removed the alternative), so the engine is determined by **which agent definition the user picks**. The user-facing choice already exists and needs no new concept — at session/worktree creation: Claude Code as a TUI worker, or Claude as an embedded SDK worker, presented through the existing uniform picker with kind badges.

Internally, `EmbeddedAgentDefinition` carries an **explicit engine discriminant** (a definition kind the subprocess dispatch switches on, exhaustively — `satisfies`-style, so a future third engine is a compile error). **Field-presence inference is prohibited** (e.g. "no `provider.apiKey` → SDK engine"): inferring behavior from an absent field is the adaptive-silent-behavior shape rejected in #1291, and here it would make a misconfigured OpenAI-compatible definition silently become an SDK agent.

**Picker/badge surfaces (SDK Engine Phase 3, #1335) — audited, none leak `engine`.** Every surface that lets a user pick an agent was checked against the "no new concept" rule above: `UnifiedAgentSelector` (`packages/client/src/components/AgentSelector.tsx`, used by session/worktree creation and restart) and `AddAgentWorkerMenu` (add-worker-to-session) both distinguish the Claude-SDK builtin from Claude Code purely via the pre-existing kind-badge/optgroup doctrine (Terminal vs Embedded) plus display naming ("Claude Code" vs "Claude") — neither surface, nor the `/agents` management page, nor the `list_agents` MCP tool (`packages/server/src/mcp/mcp-server.ts`, which returns `kind`/`id`/`name`/`description`/`capabilities` only) ever exposes the word "engine" or the `engine` field itself to a user or caller.

**Naming convention for `engine` values (owner decision, Issue #1364): `<vendor-or-dialect>-<access method>`.** The value fills a 2x2 rather than a flat list, so a future engine has a slot rather than an ad-hoc name:

| | api | sdk |
|---|---|---|
| **openai** | **`openai-api`** (this engine) | `openai-sdk` (hypothetical: an OpenAI Agents SDK-hosted engine) |
| **claude** | `claude-api` (hypothetical: our own loop against the Anthropic Messages API, §1's rejected `ProviderAdapter` design) | `claude-sdk` (this repo's other engine, already fits the scheme) |

`openai-api` replaces the original `native-loop` name, which named the wrong axis: "native" read as "Claude-native", the opposite of what the value means (our own agent loop talking to an OpenAI-compatible endpoint — Ollama, DeepSeek, LM Studio, or anything else speaking that dialect). `compat` is deliberately NOT part of the name: "OpenAI API" already denotes the dialect in common usage, and the field is full of compatible implementations, so the qualifier would add length without adding meaning — the provider's actual endpoint is already carried by the definition's `baseUrl`. The two `hypothetical` cells above are not implemented and are not a commitment to build them; they exist to show new engines have a slot in this scheme rather than requiring a new naming exercise.

### 3.2 Authentication property

**In SDK mode, no provider secret crosses the server at all.** The init command's `provider.apiKey` is absent — not optional, absent — for this engine. The subprocess runs as the user; the SDK uses the executing account's own claude configuration, exactly as that user's TUI workers already do. The embedded-agent secrets rule (stdin init only) is untouched; this engine simply has fewer secrets to carry. The MCP dial-back token is still delivered via stdin init and configured into the SDK as an MCP server (§4, tools row).

**What superseded it.** That acceptance rested on PS4 — whether `resume` actually restores a conversation across a process kill — being *typed-but-unprobed*. **What did NOT change.** The two engines still differ in *mechanism*, which is why this is parity rather than `mapped`: `openai-api` reconstructs the conversation from our persisted NDJSON stream and hands it to the provider; `claude-sdk` asks the SDK to resume its own session state, and never sends it a reconstruction. The row's "different mechanism" is the whole content of the divergence that remains, and it is invisible to the user — which is what the track's contract asks for (see `embedded-agent-worker.md` § Transcript Restore, "The track's contract").

### 4.1 Tool surface — the inverted parity question, ruled

Embedded-agent v1's lesson (#1042–#1044) was tools we LACKED. The SDK inverts it: its default toolset is a **superset** of our builtins — including WebFetch, WebSearch, and Task/subagents, capabilities embedded v1 **deliberately does not have** while sandboxing (#1045) remains unresolved. The design-time question is therefore "does SDK mode silently grant what we withheld," and the answer is ruled:

**Web tools and subagents are OFF in v1 SDK mode** (owner, Q1). The SDK's allowed-tools configuration is driven from the definition's `enabledTools`, with the withheld set excluded by default. Re-enabling them is a tracked revisit (Issue filed after implementation, per the owner's answer) — a deferral with an address, not a silent drop.

**Account-level MCP connectors are NOT governed by this engine's tool containment (verified-absent suppression option, SDK package `0.3.233` / bundled CLI `2.1.233`).** Probed directly: `options.tools: []` together with `options.settingSources: []` still reports the executing account's claude.ai connectors (Drive/Calendar/Gmail-class integrations configured on that Anthropic account) in the SDK session's tool list — no combination of documented SDK options suppresses them. This is accepted, not a gap: **TUI parity**. The connectors are the executing user's own capability surface on their own account — a TUI Claude Code worker running as that same user already has the identical connectors live today, so the SDK engine grants nothing the user's existing (terminal) workers lack. The shared-session case inherits the same parity argument (a shared TUI session already exposes the shared account's connectors to every participant). Pin 2's containment assert (S5, #1333 AC) is therefore scoped to the SDK's own withheld BUILTIN tools (WebFetch/WebSearch/Task) — `mcp__`-prefixed entries are excluded from that subset check by design, not by oversight. #1045 (sandboxing) is the tracked address for anyone who wants this class of surface governed later. Re-verify this finding on every SDK version bump alongside the other version-premised facts in §5 — a future SDK version adding a suppression option is the revisit trigger.

**Both-version confirmation (SDK Engine Phase 1 implementation PR; see the version-naming correction in §5):** re-verified identically on `0.3.226` and `0.3.233` — `options.tools: []` together with `options.settingSources: []` reports the same executing-account claude.ai connectors on both versions, and `options.tools: ['Bash']` produces exactly `Bash` among non-`mcp__`-prefixed reported tools on both. No suppression option appeared between the two versions; the finding is unchanged.

**Third-version confirmation (Issue #1338 SDK bump, 2026-08-28):** re-verified identically on `0.3.238` — `options.tools: []` together with `options.settingSources: []` reports the same executing-account claude.ai connectors (this probe's environment has real Google Drive connectors configured, a genuine positive control rather than the earlier probes' "none configured" caveat), and `options.tools: ['Bash']` produces exactly `Bash` among non-`mcp__`-prefixed reported tools on `0.3.238`, with WebFetch/WebSearch/Task absent in both cases. No suppression option has appeared across three SDK versions now (`0.3.226`/`0.3.233`/`0.3.238`); the finding remains unchanged.

**Account-scoped context is a two-member class, not one (#1348).** The TUI-parity argument above covers claude.ai account connectors specifically. A second, independent account-scoped channel — the executing account's personal memory — was found to reach an SDK-engine session outside `settingSources`' reach as well (#1348); its disposition (whether the same TUI-parity argument extends to it) is tracked there, not in this document.

### 4.2 Instruction loader — corrected (CodeRabbit finding, SDK Engine Phase 1 implementation PR)

**Correction trail — "Instruction loader" row (SDK Engine Phase 1 implementation, CodeRabbit review):** the row above originally stated the SDK's own native CLAUDE.md/AGENTS.md project-file loading was "the mechanism" for this engine, with `instructions?: string[]` extras "delivered via the session seed if configured." Both halves were wrong. The SDK's own native loading does not actually run in v1: `settingSources: []`, which the engine sets for a different, load-bearing reason (below), disables it as a side effect. And `instructions[]` extras were not delivered anywhere at all — `main.ts`'s `claude-sdk` init arm never read `init.instructions`, so a definition configuring it silently got nothing. This PR fixes the second half (`instructions[]` now works, via the mechanism described below) and corrects the documentation for the first half.

**Why `settingSources: []` is kept, even though it also disables native auto-discovery we might otherwise want:**

1. **The load-bearing reason: the runtime tool-containment check structurally cannot detect this leak class.** An ambient project-level `.mcp.json`-configured MCP server surfaces as `mcp__`-prefixed tool names, and that prefix is excluded from the containment check by design (the account-connector ruling in §4.1). A leak through that path would bypass both the `mcpServers` allowlist (never loaded through it) and the runtime subset check (excluded by prefix) — a hole with no detector is not an acceptable wall. **This argument does not depend on whether the leak is currently reachable — the decision stands on this alone.** The re-probe below (point 2) now also confirms the hole is real, not merely structurally possible; the argument's logical structure is unchanged, but it no longer rests on hypothesis alone.

2. **Second correction (owner re-probe, 2026-08-17) — no longer a conservative premise, now a measured fact.** The earlier text carried worktree-content-driven capability composition (project `.mcp.json` / project hooks) as an assumption the original probe could not confirm or refute. The owner re-probed directly and got matching results on both SDK `0.3.226` and `0.3.233`:

   | `settingSources` | project `.mcp.json` | project `CLAUDE.md` | user `.mcp.json` |
   |---|---|---|---|
   | `[]` (current) | doesn't leak | doesn't load | doesn't leak |
   | `['project']` | **leaks** | loads | doesn't leak |
   | default (unset) | leaks | loads | **leaks** |

   The worktree-content leak (a committed `.mcp.json` loading under `settingSources: ['project']`) is therefore no longer a hedged assumption — it was directly measured and confirmed, matching on both SDK versions tested. Unlike the account-connector case in §4.1 (TUI parity held because no suppression mechanism existed AND the capability's subject was the account owner's own surface), TUI parity does NOT apply here: a suppression mechanism DOES exist (`settingSources: []` doing exactly its intended job), and the capability's subject is worktree CONTENT (a project's `.mcp.json` / hooks) — a different actor, a different acceptance calculus.

3. **Third correction (owner re-probe, 2026-08-17) — "which wall is live" is resolved: there is no project-trust gate.** The earlier text hedged between two candidate walls (`settingSources: []` itself, or an SDK-internal project-trust gate unrelated to it) because the original probe's negative-control case was also negative and could not distinguish between them. The re-probe found the root cause of that ambiguity: the original probe used an `echo`-command fake MCP server, which cannot speak MCP's JSON-RPC handshake and therefore could never appear in a tool list regardless of whether `.mcp.json` was actually being read — the probe's own methodology was blind to the thing it was trying to observe. It WAS being read all along, visible not in the tool list but in the SDK's `mcp_servers` field, which reported the fake server with `status: "failed"` (a failed handshake, not a rejected load). In the headless `bypassPermissions` configuration this engine uses, on the probed versions, there is no project-trust gate — the ONLY wall is `settingSources: []` itself. The previous "two candidate walls" framing is now known to have been wrong within that scope — there was only ever one, and the re-probe found it directly. (The original gate hypothesis was specifically about this headless context; other `permissionMode` configurations were not probed and are not claimed here.) This actually STRENGTHENS the original decision to keep `settingSources: []`: what was assumed to be a possibly-redundant second wall (kept "regardless" of whether an internal gate was also doing the job) turned out to be the only wall doing the job at all.

**`instructions[]` extras now work (as of the SDK Engine Phase 1 implementation PR; superseded by #1343 Phase A below).** The definition's explicit opt-in file list was read through the same confined reader the openai-api engine used (`loadOptInInstructions`, `system-prompt.ts`), and composed onto the SDK preset's `systemPrompt.append` alongside the definition's own `systemPrompt`, in `main.ts`'s `claude-sdk` init arm. As of the SDK Engine Phase 1 implementation PR's follow-up commit, the builtin `claude-sdk` definition (`claude-sdk-builtin.ts`) configured `instructions: ['CLAUDE.md']`, making this the mechanism (not just the machinery) by which CLAUDE.md content reached an SDK-engine session in Phase 1.

**Correction trail — "Instruction loader" row, Issue #1343 Phase A (2026-09-03): the door noted below is now taken.** The "now-open door" paragraph that used to close this section reasoned that running our own chain-walking loader for this engine, alongside the SDK's native mechanism kept off, would not double-load anything — that reasoning is now implemented, not merely available. `main.ts`'s `claude-sdk` init arm calls the SAME `loadInstructions` the openai-api arm calls (global layer, chain, opt-in `instructions[]`, and a new fourth layer, `.claude/rules`), and the builtin `claude-sdk-builtin.ts` definition's `instructions: ['CLAUDE.md']` entry was REMOVED — it is no longer needed, since the chain layer resolves the same file automatically (CLAUDE.md/AGENTS.md, root-to-cwd), and `loadInstructions` dedupes by resolved path so a definition that still lists it explicitly does not double-load. `settingSources: []` is UNCHANGED by this PR — the native mechanism stays off for the same reason recorded above; only the machinery delivering equivalent content from outside it changed. Every limitation the paragraph below used to list is therefore resolved except (b), which was never really a limitation of the `instructions[]` path specifically:

- ~~(a) single file confined to `cwd` only, no chain merge, no global layer~~ — **resolved**: the same 4-layer `loadInstructions` the native engine uses now runs for this engine too.
- (b) content lands in `systemPrompt.append`, appended after the SDK's own preset preamble — **unchanged, and not a defect**: this is simply where an `append`-shaped SDK option composes; it was never a gap relative to native auto-discovery, whose own placement remains unobserved and out of scope for this document either way.
- ~~(c) a missing file is skipped with a warning, not an error~~ — **unchanged in effect, now the general loader's behavior**: `loadInstructions` (like `loadOptInInstructions` before it) treats a missing/absent file as silent-by-design, not this-path-specific behavior anymore.

**What is still out of scope, and where it is tracked.** Phase A does not touch `settingSources` (still `[]`) and does not implement Phase B's lazy activation of SCOPED `.claude/rules` (a rule with `paths:`/`globs:` frontmatter is listed in a one-line index but its content is not injected until a matching tool call — tracked as a checklist in Issue #1343, not this PR). The web-tools/subagents half of #1343 (§4.1) is entirely unaffected by this section and stays gated on #1045.

### 4.3 UI: the restore-divergence notice (SDK Engine Phase 3; polarity inverted by R1)

**What the notice is now.** A `claude-sdk` worker that restored a prior transcript normally **shows no notice at all**, because the conversation genuinely did continue: R1 resumes the SDK session, so the live model sees what the transcript shows. The notice survives as the **fallback confession** — shown whenever **this incarnation's SDK session did not resume** (`sdkResumed === false`), by any of the routes enumerated below, which is the case where the displayed transcript and the model's memory really do disagree. Not "a resume was attempted and did not take": most of those routes never send a `resume` at all, and defining the notice by the attempt would leave them uncovered.

**What it was, and why it changed.** From Phase 3 ([#1335](https://github.com/ms2sato/agent-console/issues/1335)) until R1 the notice was shown **whenever** a `claude-sdk` worker displayed a restored transcript — a standing confession of §4's accepted-divergence, on the owner's Q2 condition that the consequence be stated rather than discovered. R1 removed the divergence itself (see §4's correction trail), so a notice on every restore would now be false: it would claim a break in continuity that no longer happens. See the polarity correction trail below.

**Mechanism — no wire change.** Both signals the notice needs already existed before Phase 3, unrelated to each other:

- The engine discriminant: `EmbeddedAgentDefinition.engine`, already delivered to the client via the existing `GET /api/embedded-agents` registry fetch (`useEmbeddedAgents()`), which `EmbeddedAgentWorkerView` already joins against `embeddedAgentId` for Compaction's `contextWindowTokens`/`compaction` fields.
- Whether *this* activation actually restored a non-empty prior transcript: `restoredMessageCount` (client store field fed by the pre-existing `restore-info` `WorkerServerMessage`, [Transcript Restore](../glossary.md#transcript-restore) / #1123 / #1205) — non-null and greater than zero iff the current incarnation's restore succeeded against a non-empty log.
- **Added by R1: whether the SDK session actually resumed.** `restore-info.sdkResumed`, a new optional boolean on the same message, set **only** by the `claude-sdk` engine; `openai-api` omits the field entirely.

  **`false` means "this incarnation's SDK session did not resume" — not "a resume was attempted and refused".** The wider reading is the correct one and covers four distinct routes to the same user-visible situation: no `sdkSessionId` was persisted to resume from; the activation-time pre-flight could not find the session, so no `resume` was ever sent; the pre-flight could not *run* (a lookup failure — see the failure handling below, where this route keeps the id but still starts this incarnation fresh); or a resume was sent and the SDK refused it. All four leave a restored transcript in front of a model that does not have it, which is the only thing the notice claims. Defining `false` by the refusal route alone would leave the other three undefined, and an implementation could then start fresh **without** showing the notice while still satisfying the letter of the spec — the transcript displayed with no warning, which is the exact outcome the notice exists to prevent (CodeRabbit finding, 2026-08-29). **Inferring resume failure from the field's absence is forbidden** — absence means "this engine does not have the concept", not "the resume failed", and the two are exactly the states a negation would collapse. The client therefore tests `sdkResumed === false` explicitly, never `!sdkResumed`. This is the same two-valued-negation trap the engine discriminant already carries below, in a second place; the reason it gets its own prohibition is that here the third state is not a loading race but a permanent property of the other engine.

**R1 does add wire surface, unlike Phase 3.** Phase 3 could ship its notice with no schema change because both its signals already existed. `sdkResumed` is genuinely new, so it carries the full `pre-pr-completeness.md` Q10 three-part set: the TypeScript field, the matching valibot member on `RestoreInfoMessageSchema`, and an integration test that exercises the field across the real wire boundary rather than a mock factory.

`EmbeddedAgentWorkerView.tsx` combines the two purely client-side: `engine === 'claude-sdk' && restoredMessageCount !== null && restoredMessageCount > 0`. No new server event, no new `WorkerServerMessage` field, no schema change — this is the reason Phase 3 could ship this notice without re-triggering `pre-pr-completeness.md` Q10 (wire-surface schema/integration-test overhead). The `engine` discriminant itself is genuinely **three-valued** client-side (`openai-api` / `claude-sdk` / unresolved — the registry fetch still loading, or a dangling/unmatched `embeddedAgentId`), so the generic v1 banner's gate is the explicit positive check `embeddedAgentDefinition?.engine === 'openai-api'`, never a negation like `!isSdkEngine` — a negation of a two-valued check collapses "confirmed openai-api" and "unresolved" into the same branch, which would show the openai-api-only restore claim before the engine is actually known (caught by CodeRabbit during this phase's own implementation).

**Polarity (rewritten by R1; matches the AC and the client test suite):**

| Engine | Restored a non-empty transcript? | `sdkResumed` | Notice shown |
|---|---|---|---|
| `openai-api` | either | absent (this engine never sets it) | the pre-existing v1 generic banner (conversation IS reconstructed for this engine — accurate, unchanged) |
| `claude-sdk` | no (fresh worker, nothing to have diverged from yet) | absent | none |
| `claude-sdk` | yes | `true` | **none** — the SDK resumed the session, so the transcript and the model's memory agree. Showing a divergence notice here would confess a divergence that did not happen |
| `claude-sdk` | yes | `false` | the divergence notice, **replacing** the generic banner. This is the fallback confession: the session did not resume — for any of the four reasons above — so the displayed transcript really is ahead of the model's memory |
| engine unresolved (registry still loading, or a dangling/unmatched `embeddedAgentId`) | either | either | **none — no claim about session continuity for an engine that isn't confirmed yet.** Omitting this row would reseed the two-valued-negation bug for the next reader who implements against this table without noticing the third state |

**Correction trail — row 2 was unreachable, and is now reachable (Issue [#1428](https://github.com/ms2sato/agent-console/issues/1428)).** This paragraph previously read *"the implementation cannot reach it"*, recorded against `8ac8490e`. That is no longer true and the row now behaves as the table says.

What was wrong was never the design statement — it was the implementation's inability to reach it. `restore-info`'s count was the reconstruction's whole array **including the seed it prepends itself**, so it had a floor of 1 (or 2 past a compaction boundary) and the client's `> 0` conjunct could never go false. A `claude-sdk` worker that had said nothing therefore took row 4 and showed the divergence notice for a conversation that never existed. #1428 redefined the field by a criterion — **an entry counts if and only if its content originates from a line of the persisted transcript** — and renamed it to `restoredMessageCount` so a reader cannot mistake the new meaning for the old. Replayed messages and the compaction summary originate in rows and count; the synthetic system prompt and Tier C repair markers are invented by the reconstruction so the provider accepts the array, originate in no row, and do not. Empty transcript now reports 0, the conjunct goes false, and row 2 yields "none" as written.

Two things worth keeping from how it was found. **[#1412](https://github.com/ms2sato/agent-console/issues/1412)'s acceptance criteria cited this very table as already yielding "none" here**, and the claim survived until someone measured it rather than read it — the table describes intent, and nobody had grepped the implementing gate's reachability against it. And the fix's own first definition ("exclude the seed") had an edge that would have re-broken the row from the other side: a worker killed immediately after a compaction, with nothing replayed after the boundary, would have reported 0 and **suppressed the notice exactly where the model has lost the most**. A compaction summary is restored content, not a synthetic seed, which is why it counts.

**Row 2's `sdkResumed` column is `false`, not absent** — the code sets `sdkResumed: resumeId !== null` for every `claude-sdk` activation, so a worker with no persisted id reports `false` rather than omitting the field. The outcome is still "none", now gated by the count conjunct rather than by this one. Absence remains reserved for the other engine, which is what the three-valued reading below is about.

**Read the `sdkResumed` column as three-valued, not two.** `absent` is a distinct state from `false` and never stands in for it — an `openai-api` worker and a failed `claude-sdk` resume are not the same situation, and the row that says "none" for the former must not be reached by a check that also matches the latter.

**Correction trail — polarity inverted (R1, [#1410](https://github.com/ms2sato/agent-console/issues/1410), 2026-08-29).** The table above previously had three rows, and its third read: *`claude-sdk` + restored a non-empty transcript → show the divergence notice*, unconditionally. That was correct for as long as a `claude-sdk` worker's revival really did start the model fresh. It stopped being correct when R1 made the SDK resume, and the supersession is worth stating plainly because it inverts rather than refines: **the same condition that used to be the trigger is now the case with no notice.** A reader who ports the old rule forward would show a permanent, false warning on every successful resume — the most likely way this section gets re-broken.

The chain is: the accepted-divergence (owner, Q2) rested on PS4 being unprobed → [#1400](https://github.com/ms2sato/agent-console/issues/1400) probed PS4 and it passed → the premise was gone, so R1 closed the divergence → the notice lost its standing justification and became a fallback. Each link removed the reason for the next.

**What the notice must never say.** Its wording may state what is true — that this worker's model does not have the earlier conversation and the transcript above is a record, not its memory — and must not promise restoration, recovery, or that anything will be re-sent. This is the same prohibition [Compaction](embedded-agent-worker.md#compaction) carries for its own marker, for the same reason: a notice that over-promises is worse than the divergence it describes.

**Form.** A standalone banner in `EmbeddedAgentWorkerView`'s header area (same visual slot as the pre-existing persistent notice) — deliberately NOT a new `EmbeddedAgentChatEntry` kind / transcript row, to stay clear of #1351's ownership of transcript message-row rendering in the same file. Non-dismissable, same as the banner it replaces — visible without user action, and a single slim row never obstructs the view.

**See:** [`EmbeddedAgentWorkerView.tsx`](../../packages/client/src/components/workers/EmbeddedAgentWorkerView.tsx); [embedded-agent-worker.md § UI](embedded-agent-worker.md#ui) (the pre-existing generic notice this one sits alongside/replaces).

- **PS1 — the SDK honors `settings.autoCompactEnabled`.** Re-graded 2026-08-28 into three layers; see the PS1 correction trail below. **PS1a (arrival): verified** — the write key `settings.autoCompactEnabled` and the read key `getContextUsage().isAutoCompactEnabled` name the same switch, at construction and mid-session via `applyFlagSettings`, in both directions. **PS1b (reconfiguration): verified** — the flag makes `autoCompactThreshold` appear and `maxTokens` shrink, and when off it selectively discards `autoCompactWindow` too. **PS1c (honoring under pressure): verified for `true`** at a real auto-compaction firing; **structurally unverifiable for `false`**, because the flag and the effective window move together, so the OFF arm can never be given the ON arm's window. An earlier "PS1-false confirmed under pressure" verdict is **retracted**.
- **PS2 — `getContextUsage()` supplies a usable threshold signal** (totalTokens/maxTokens/percentage). Verified. **Must-not-assume: threshold TUNING of the SDK's own window** — `settings.autoCompactWindow` had no observable effect in the 2026-08-17 probe (inconclusive, not proven dead). We never needed it (our threshold is our own), but nobody may build on it later without verifying it first. **The 2026-08-28 probe found a partial write path and a likely explanation for the original non-observation; see the PS2 correction trail below before relying on either.**
- **PS3 — session-boundary seeding works**: a successor `query()` with a fresh session id, seeded via `systemPrompt: { type: 'preset', preset: 'claude_code', append: <distillation> }`, recalls the distilled context. Verified with a real recall test. This is what makes the owner's handoff decision implementable regardless of whether the SDK's conversation state is otherwise sealed.
- **PS4 — `resume` restores a session's conversation across a process kill. VERIFIED** (2026-08-28, Issue #1400; SDK `0.3.238`). Previously TYPED-BUT-UNPROBED: the option's documentation says it "loads the conversation history from the specified session", but the 2026-08-17 probe deliberately did NOT exercise `resume` (its session A fully exited with no resume; PS3 tested fresh-session seeding), and a typed surface is not verified behavior. It has now been probed on the real shipping surface — see the PS4 verification trail below for what passed and what the controls were. All three sub-cases are answered, including whether a resumed session lands in the post-compaction state (it does). The gate this premise carried is discharged: the idle-eviction phase's AC ([#1336](https://github.com/ms2sato/agent-console/issues/1336)) is no longer blocked on it. Note what that does NOT mean — §4's process-lifetime row stays `reserved`, because lifting it means shipping eviction, not verifying its premise.
- **PS5 — a query that resumed successfully reports the same session id it was asked for. VERIFIED** (2026-08-29, R1's G2 gate; SDK `0.3.238`). Promoted to a named premise because R1's resume-success signal reads it: a `system:init` reporting the requested id is what `sdkResumed: true` means. Measured with a planted-nonce positive control — the resumed session recalled a word planted before the kill AND reported back the id it was asked to resume — so the premise is verified together with the thing it is a premise about. `forkSession` defaults off, which is why the id does not change; **anything that turns forking on breaks this premise**, and the detector with it.
- **PS6 — a failed resume never emits `system:init`. VERIFIED** (2026-08-29, R1's G2 gate; SDK `0.3.238`). This is the premise R1's *failure* detector rests on, and it is what makes that detector structural rather than textual. Measured for both invalid shapes (a well-formed but nonexistent uuid, and a malformed string): construction returns normally; nothing happens until the first prompt is pushed; **no `system:init` of any kind arrives**; one `result` with `subtype: 'error_during_execution'` and `is_error: true` appears; then the query's async iterator throws `Claude Code returned an error result: No conversation found with session ID: <id>`. The query is dead afterwards — a second turn pushed onto the same queue never runs.

  **Why the detector cannot key on anything else.** The `result` subtype is not discriminating: `error_during_execution` is also what `interrupt()` produces (Appendix A's `cancel` row, re-verified under [#1338](https://github.com/ms2sato/agent-console/issues/1338)), so an ordinary user cancel and a failed resume are indistinguishable at that field. The thrown message is undocumented CLI wording and free to change on any bump. What separates the two is **causal structure**: a cancel always has a `system:init` behind it, because a turn was already running; a failed resume never does, because the session never started. So the detector is *we asked to resume, and the query reached a terminal error without ever having reported a `system:init`* — and it is exactly PS6 that this depends on. **If a future SDK emits a `system:init` before failing a resume, the detector breaks silently and reports every failed resume as a success.**
- **PS7 — `getSessionInfo(id)` does not report `undefined` for a live session. VERIFIED for every shape production creates** (2026-08-29, R1's (d) micro-probe; SDK `0.3.238`). R1 pre-flights the persisted session id with `getSessionInfo` before constructing the query, which moves the failure to activation time and off the user's first message. The SDK's own doc says the call returns `undefined` when the session file is missing **or** when the session "is a sidechain session, or has no extractable summary" — that second clause is the risk, because a false `undefined` would make the pre-flight discard a resumable conversation, the one way the pre-flight could be worse than not having it. Probed adversarially rather than on an easy sample: four real worker sessions all returned defined info, including a one-turn session whose entire reply was `OK` (2 898 B) and, deliberately constructed as the worst case, **a session killed during its first turn with no assistant message ever produced** (5 644 B) — which still returned a defined record with an auto-generated summary. Invalid ids (nonexistent uuid, malformed string) return `undefined` **without throwing**, so there are no exception semantics to get wrong. Cost is a filesystem read: 0–14 ms with the `dir` hint, 12–63 ms without; no `claude` spawn and no billable turn, which is why it can run on every activation.

  **The pre-flight removes the failure from the main path; it does not remove the failure.** A false `undefined` could not be forced but the documented clause cannot be ruled out, and there is a small window between the check and construction. The fallback path is therefore still required and still reachable — see the failure handling in Appendix A's `init` row.

  **Extension (2026-08-29, Issue [#1426](https://github.com/ms2sato/agent-console/issues/1426)) — `undefined` structurally merges "absent" and "unreadable", and the throw path is unreachable.** PS7 above records that invalid ids return `undefined` without throwing. That is stronger than it reads: **no filesystem fault produces a throw either.** Measured against `0.3.238` through the production `probeSdkSession`, with a planted-session positive control re-run after every negative (the control also establishes that the redirected `HOME` is load-bearing, so a `not-found` means the SDK looked and found nothing rather than that the harness stopped working):

  | condition | result |
  |---|---|
  | planted session file present (positive control) | `found` |
  | session `.jsonl` mode `000` (EACCES on read) | `not-found` |
  | project directory mode `000` (EACCES on traverse) | `not-found` |
  | `~/.claude` mode `000` | `not-found` |
  | session path is a directory (EISDIR) | `not-found` |
  | `.claude/projects` is a regular file (ENOTDIR) | `not-found` |
  | malformed JSON in the session file | `not-found` |
  | `HOME` points at a nonexistent path | `not-found` |
  | `HOME` unset entirely | `not-found` |

  The SDK's default file session store swallows read errors and reports "no session". **So the SDK's API cannot distinguish "this session does not exist" from "I could not read the store", and no caller can recover that distinction from `getSessionInfo` alone.** The consequence for design: an `undefined` verdict must never be treated as durable evidence about the session — it is a statement about one moment's read, and the only safe response is to keep the id and re-check next time (see the failure-handling table in Appendix A's `init` row). The direction of danger is that this looks like a verdict and is not one.

  **This table is part of the SDK-bump re-verification set** (below): re-run all nine conditions on any `@anthropic-ai/claude-agent-sdk` bump. If a bump makes the store propagate read errors, the `lookup-failed` route becomes reachable and starts doing the job it was written for — a behavior change worth knowing about deliberately rather than discovering.

**Correction — the preserved probe did not originally reproduce the hard case (CodeRabbit, 2026-08-29).** The adversarial measurement above was made with an ad-hoc script that killed the session while its first turn was genuinely still running. The `--invalid` item preserved in `probe-sdk-resume.ts` **awaited** that turn before killing, so the artifact a future re-prober runs was exercising a COMPLETED-turn session — the easy case — while its own comment claimed the hard one. The finding was true; the preserved instrument was weaker than the finding, which is the failure mode preserving probes exists to prevent. The item now starts the turn without awaiting it and asserts `turnInFlight` at kill time, reporting a RECORDED NON-RESULT rather than a pass if the turn settled first — the same guard, and for the same reason, that `itemMidTurn` already carried.
- **PS8 — `terminal_reason: 'aborted_streaming'` discriminates a cancel from a genuine `error_during_execution` failure. FIELD documented; MAPPING observed** (2026-08-30, Issue [#1495](https://github.com/ms2sato/agent-console/issues/1495); SDK `0.3.238`). `terminal_reason` is a typed, exported field on `SDKResultError` (`terminal_reason?: TerminalReason`, `sdk.d.ts`), so its EXISTENCE is a contract, not a guess about undocumented shape. What is NOT documented anywhere in the SDK's own types or prose is the specific mapping `buildExecutionErrorMessage` (`sdk-engine.ts`) relies on: that a user-initiated cancel (`interrupt()`) produces `aborted_streaming`, and that no other `error_during_execution` cause reachable by this engine produces the same value. That mapping is an OBSERVATION — "confirmed live" per the pre-existing comment this premise formalizes — with the same shelf life as PS6's causal-structure premise, which shares this result subtype. **Re-verify both together on the next SDK bump.** Fail-open direction (R5 of #1495's AC): an absent or unrecognized `terminal_reason` routes to the genuine-error path, never to canceled — a bump that stops setting the field, or renames the value, degrades a cancel to R3's generic copy plus the raw diagnostic on the server log, i.e. **the cancel is worded as a generic error**, never to "the raw diagnostic reaches the user again" (R3 covers that path too, so the transcript never regresses to the pre-#1495 raw string) and never to "a real failure is silently relabeled as a cancel".
- **H1 (hazard) — memory cost** is §1.1's measured trade; any future claim of SDK-mode memory *savings* is false until re-measured.
- **H2 (hazard) — transport settle race**: calling `getContextUsage()` immediately after a turn's `result` intermittently broke the transport (`ProcessTransport is not ready for writing`); ~300–500 ms of settle fixed it reliably. Encode as **retry-with-settle, not a bare sleep**, and re-verify on every SDK upgrade — this is an empirical workaround for observed 2.1.233 behavior, not a documented contract (see the version-naming correction in §5).

**Correction trail — H2 (Issue #1338 SDK bump re-verification, 2026-08-28):** re-probing this hazard surfaced a methodology gap, not (necessarily) a version-specific behavior change. A probe that ends its `for await` loop on the turn's `result` message (via `break`) — which does NOT match production's `consumeLoop` (`sdk-engine.ts`), which never breaks and keeps iterating for the life of the session — reproduces "ProcessTransport is not ready for writing" on every attempt, indefinitely (12 retries over 3.3s, still failing), on BOTH `0.3.226` and `0.3.238` alike. Breaking a `for await` early on an async generator invokes the generator's `return()`, and `Query extends AsyncGenerator`; this is a plausible mechanism for why an early-breaking probe would observe a permanently-wedged transport regardless of SDK version. A second probe, corrected to match production's exact sequential await chain (poll `getContextUsage()` from a call awaited *inside* the still-live `for await` body, exactly as `handleResult` does), reproduced the race ZERO times: 5/5 trials on `0.3.238` with a plain-text turn (attempt 1 succeeded at t+0-1ms), 10/10 trials on `0.3.238` with a Bash-tool-call-bearing turn (attempt 1 succeeded at t+238-282ms), and 5/5 trials on `0.3.226` run as a same-methodology control (attempt 1 succeeded at t+0ms). **Epistemic status change, not a design change:** the original 2026-08-17 probe script is not preserved in this repository, so whether it shared the early-break artifact discovered here cannot be determined — this downgrades H2 from "an observed intermittent race, reliably fixed by ~300-500ms settle" to "an observation whose reproduction conditions are no longer known with confidence." This downgrade is itself the record a future re-prober needs — a probe that terminates iteration early on `result` is a plausible false-positive generator for this exact hazard, independent of the SDK version under test. **This finding does not change the code.** The retry-with-settle mechanism remains in place as a cheap, harmless defensive measure — exactly the "an SDK upgrade that removes the race makes the retry a no-op" outcome §7's verification floor already anticipated. `CONTEXT_USAGE_SETTLE_DELAY_MS`/`CONTEXT_USAGE_MAX_ATTEMPTS` are unchanged. Both probes that produced this finding are preserved and re-runnable: `scripts/smoke/probe-sdk-h2-transport-settle.ts` (production-faithful) and `scripts/smoke/probe-sdk-h2-transport-settle-negative-control.ts` (the early-break artifact demonstration) — a future re-prober should not repeat this PR's mistake of describing findings without preserving what produced them.

**Correction trail — PS1 (Issue [#1400](https://github.com/ms2sato/agent-console/issues/1400), 2026-08-28), re-graded into layers.** The 2026-08-17 entry read "verified at small scale", and that phrasing hid a gap that the compaction swap could not have been built on:

> A successful read-back of a setting is not proof of behavior. P1a verifies that the setting arrives; P3 is a separate layer verifying that behavior follows the setting. Auto-compaction must not ship as the default ON state on the strength of the former alone. The 2026-08-17 PS1-false verification did not distinguish these two layers, and its "false was honored" observation, taken in a context too small for compaction to fire at all, was unfalsifiable.

The mandated statement above is written in two layers. Probing found a **third** sitting between them — the setting is observably reconfiguring the SDK rather than merely being echoed back — so the results are recorded in three, against SDK `0.3.238` with `scripts/smoke/probe-sdk-compaction.ts`:

- **PS1a — arrival. Verified.** Constructing with `settings.autoCompactEnabled: false` reports `getContextUsage().isAutoCompactEnabled === false`; `applyFlagSettings({ autoCompactEnabled: true })` flips the read-back to `true`; the symmetric case (construct `true`, flip to `false`) holds too. The write key and the read key name the same switch, so `sdk-engine.ts:286`'s `autoCompactEnabled` was never a misspelling of `isAutoCompactEnabled`. **This also discharges the live-toggle-reflection gate** the implementation PR's per-worker toggle depends on — mid-session `applyFlagSettings` reflection is exactly the half of PS1a that was exercised.
- **PS1b — reconfiguration. Verified, and it refutes the null hypothesis.** Turning the flag on makes the `autoCompactThreshold` field *appear* and `maxTokens` *shrink* (on `claude-sonnet-5`: `934000` / `967000`); turning it off makes the field vanish and `maxTokens` revert to the full `1000000`. More pointedly, `autoCompactWindow` is honored **only while compaction is on**: an `autoCompactEnabled: false` session given `autoCompactWindow: 100000` reports `maxTokens: 1000000`, and the CLI says so in its own words when the same window is set via `/autocompact` on such a session — `Auto-compact window set to 100k tokens, but a higher-priority override is active (1m tokens)`. This layer is **circumstantial evidence that the flag reconfigures the SDK's compaction machinery**. It is not a substitute for a positive behavioral claim, but it does refute the null hypothesis that the flag is a no-op: a flag being ignored cannot explain why the threshold field appears and disappears with it, nor why it selectively disables an entirely different setting.
- **PS1c — honoring under pressure. Verified for `true`; STRUCTURALLY UNREACHABLE for `false`.**
  - **`true`, verified at a real firing.** With the window shrunk to the SDK's 100,000-token floor (see the PS2 trail below for why that is the only available lever), a driven conversation crossed the reported `autoCompactThreshold` of `67000` and compaction **fired on its own**: a `system/compact_boundary` with `trigger: 'auto'` reached the query iterator (`pre_tokens` 102150 → `post_tokens` 2710, `duration_ms` 26146, `preserved_messages` 3), and `getContextUsage().totalTokens` fell 101588 → 25544. A nonce planted before the boundary was recalled **verbatim** afterwards, along with the conversation's gist.
  - **`false`, not verifiable at any budget — and the reason is a finding, not a shortfall.** The AC designed the ON arm to be the OFF arm's positive control. That control design **cannot hold**, because the flag and the effective window move together (PS1b): an OFF session cannot be given the ON session's 100,000-token window by any path, so the two arms differ in *two* variables at once. A first run did drive an OFF arm to 112796 tokens with zero boundaries and the probe reported "confirmed under pressure" — **that verdict was retracted**. At the OFF arm's unavoidable 1M window the threshold is ~934000, and 112796 is 11% of it: an enabled session would not have compacted there either, so the absence of a boundary is fully explained by the window and leaves nothing to attribute to the flag. This is the same unfalsifiability shape #1400 was written to retire, one level up — not "the context was too small to compact" but "the window was too large to compact at". Verifying it honestly would mean driving to ~934000 tokens, beyond any realistic budget.
  - **The confound is itself second-layer evidence.** The very coupling that broke the control — `false` discarding the window along with compaction — is what shows `false` is not being ignored. A flag that were a no-op would have no reason to selectively disable a different setting. The measurement that destroyed one layer's verification contributed to another's.

**What may therefore ship.** `autoCompactEnabled: false` is supported by layers 1 and 2 (it arrives, and it demonstrably reconfigures the machinery, whose effective window becomes the model's full 1M), with layer 3 structurally unverifiable. **The default-ON state must not ship on layers 1 and 2 alone** — for `true` that is moot, because layer 3 *is* verified at a real firing. The user-facing OFF toggle is not a fake affordance: with `false` the effective window is 1M, which no real embedded conversation reaches, so "off" means off in every situation production can produce. The residue — whether a `false` session would compact anyway near ~934000 — is unreachable in practice and harmless if it exists.

**Which layer is load-bearing was inverted by the compaction swap (#1401).** When this document was written, `autoCompactEnabled: false` was the setting the engine actually set, and PS1 named exactly one risk: *the SDK might compact anyway*. Everything the design needed from PS1 was that **`false` be honored**. That is no longer what the design rests on. The SDK's own auto-compaction **is** this engine's automatic compaction now, driven by the worker's toggle, so the load-bearing premise is that **`true` be honored** — and that is the layer PS1c verified at a real firing, which is why the default-ON state may ship. `false`'s remaining status (layers 1 and 2, layer 3 structurally unverifiable) has moved from *the premise the feature depends on* to *the premise a user's OFF choice depends on* — still worth having, but no longer what would break the feature if it failed. A future reader comparing PS1's grade against the risk it was written for should read it against the current direction, not the original one.

**Unexpected behavior found while probing PS1, recorded here in the same correction-trail form as H2.** Three things the design did not predict, each of which an implementer would otherwise meet as a surprise:

1. **The PS1 tripwire's sensitivity depends on the conversation-to-baseline ratio, and it is not a defect.** `sdk-engine.ts`'s `MATERIAL_DROP_RATIO` (0.2) compares consecutive `getContextUsage().totalTokens` polls, but `totalTokens` includes a fixed ~21,500-token system-prompt-and-tools baseline that `compact_metadata.pre_tokens`/`post_tokens` do not carry the same way. In a *small* conversation this swamps the signal: a manual `/compact` that took the conversation from 25335 to 2133 moved `totalTokens` only 25308 → 24792, a 2% drop, and the tripwire correctly did not fire. At a *real* auto-compaction — which by construction happens near the threshold, where the conversation dominates the baseline — the same tripwire saw a **74.9% drop and would fire**. So the correct statement is not "the tripwire is broken" but "the tripwire is insensitive exactly where a drop is not worth reporting". This matters because the compaction swap's marker detection uses `compact_boundary` as its primary source and the ratio only as an anomaly check for a large drop *without* a boundary; that division of labour is what makes the small-context insensitivity a consequence rather than a hole.
2. **`applyFlagSettings` is not a uniform mid-session write channel.** It moves `autoCompactEnabled` (both directions, verified above) but has **no effect** on `autoCompactWindow` — the same call, the same session, the same control request, one key honored and one silently ignored. Mid-session window changes have to go through the `/autocompact` slash command instead.
3. **`autoCompactThreshold` is a read-only derived value.** It is not a `Settings` key at all (only `autoCompactWindow` is), and writing it — at construction or via `applyFlagSettings` — changes nothing. This is the concrete instance of the trap the probe's AC was written against: **appearing in a response is not the same as being settable**, and the two must be verified separately.

**Correction trail — PS2 (Issue #1400, 2026-08-28): the observation stands, its interpretation is updated.** The 2026-08-17 record — `settings.autoCompactWindow` had no observable effect — is not contradicted here; what changes is the understanding of the conditions under which that non-effect was observed. The 2026-08-28 probe found the window **is** writable, but only through specific paths and only above a floor:

| write path | result |
|---|---|
| `settings.autoCompactWindow` at **construction** | **works** — `100000` gives `maxTokens: 100000`, `autoCompactThreshold: 67000` |
| `applyFlagSettings({ autoCompactWindow })` **mid-session** | **no effect** |
| `/autocompact <n>` as a plain user message | **works** — replies "Auto-compact window set to 100k tokens" |
| any of the above **below 100,000** | rejected |

The floor is the load-bearing part. `/autocompact 30000` is refused *out loud*: `Couldn't parse '30000'. Expected 'auto' or 100k–1M tokens (e.g. 500k, 200000, or 200 as shorthand)`. But `settings.autoCompactWindow: 30000` is dropped **silently** — no error, no warning, and `getContextUsage()` reads back exactly as if the key had never been passed, which is indistinguishable from "the key does nothing". **It is therefore likely — and this is inference from the shape of the failure, not something the 2026-08-17 probe recorded — that the original non-observation was a below-floor value being silently discarded rather than the key being inert.** Stated as a probability because the original probe's value is not preserved; a future re-prober who reaches for a small round number will reproduce the same silent nothing.

PS2's must-not-assume is therefore **narrowed, not lifted**: the window is tunable at construction and via `/autocompact`, within `[100k, 1M]`. Anyone building on that must still verify it for their own SDK version, and must not assume the mid-session `applyFlagSettings` path works, because it does not.

**Verification trail — PS4 (Issue #1400, 2026-08-28): probed on the real surface, and it passes.** Measured with `scripts/smoke/probe-sdk-resume.ts` against SDK `0.3.238`, each result paired with controls in the same run:

- **(a) Idle kill → resume. PASS — this is the PS4 pass condition.** A conversation with a planted nonce, then `SIGKILL` on the `claude` child while no turn was in flight, then a *new* `query()` with `resume: <sessionId>`: the resumed session recalled the pre-kill nonce **verbatim** and restated the conversation's subject. The resumed query reports the **same** session id it was asked to resume (it does not fork; `forkSession` defaults off). Three controls make the negative interpretation unavailable: the origin session answered the same question correctly *before* the kill; the resumed process completed an ordinary fresh turn afterwards; and a session started **without** `resume`, against the same isolated `CLAUDE_CONFIG_DIR`, answered `UNKNOWN` — so the recall is attributable to `resume` rather than to the model, the prompt, or the environment.
- **(b) Mid-turn kill → resume. Survives.** With a long generation genuinely in flight (the probe asserts the turn had not settled at kill time — a first attempt killed after a turn had already completed, which would have reported an idle kill under a mid-turn label), the interrupted turn is dropped entirely (0 characters reached us, no `result`), and the resumed session still recalls the pre-kill nonce.
- **(c) Compaction × eviction composite. Resume lands in the POST-compact state.** A ~95,000-token conversation compacted with `/compact` (`pre_tokens` 95104 → `post_tokens` 2214), then `SIGKILL`ed, then resumed: the resumed session's context usage was 27344 tokens against a post-compact expectation of 23755 and a pre-compact expectation of 95104 — a 71,349-token separation, so the reading is unambiguous. The nonce and the gist came back, and the no-resume control answered `UNKNOWN`. **This answers the question [#1336](https://github.com/ms2sato/agent-console/issues/1336)'s AC would otherwise have had to assume: an evicted-then-resumed session inherits the compacted context, not a replay of the pre-compaction history.**

  Getting here required fixing the measurement first. The item's original small-conversation form put the two candidate states ~260 tokens apart — below the noise of the recall turn itself — and the first run's "landed closer to the PRE-compact state" was reading that noise. The probe now computes the separation, refuses to answer below a 5,000-token floor, and says so; `--post-compact --pressure` inflates the conversation until the reading means something.

**What the swap may now rely on, and what it may not.** `/compact` sent as a plain streaming-input user message reaches the CLI and produces a `compact_boundary` with `trigger: 'manual'` (a conversation the CLI considers too short is answered with `Not enough messages to compact.` and no boundary — a refusal, not a missing command, and the two must not be conflated). Auto-compaction produces the same message shape with `trigger: 'auto'`, so **`compact_boundary` is a usable primary detection source for both paths**. `PreCompact` and `PostCompact` hooks wire up through `Options.hooks` and both fire, with `PostCompact` carrying a real `compact_summary` (9,413 characters in the measured run) and a `transcript_path`. What may *not* be relied on: mid-session window tuning via `applyFlagSettings`, any window below 100,000, `autoCompactThreshold` as a writable knob, any window at all on a session with compaction disabled, and the fidelity of any single compaction (see §5.1 — a summary can silently drop a value the prompt asked to preserve).

Both probes are preserved and re-runnable, alongside the H2 pair, and share `scripts/smoke/probe-sdk-session-harness.ts` so the two cannot drift apart on methodology. They are billable manual tools with no `check:` alias and no CI gate, for the same reason the H2 probes are.

### 5.1 Compaction fidelity is non-deterministic (Issue #1400, 2026-08-28)

Recorded under its own heading, not as an aside, because it is an input to a shipping decision rather than a curiosity: the swap ships auto-compaction as a **per-worker toggle defaulting to ON**. That decision was made knowing compaction is summarisation and therefore lossy. **What was measured here is not lossiness.**

**The observation.** In one `--pressure` run, a ~95,000-token conversation was compacted to an **872-token** summary that dropped **both** the planted nonce **and** the conversation's own topic — the session answered `UNKNOWN` to both questions. The prompt that planted the nonce stated explicitly that it "must be preserved verbatim through any later summarisation". A second run, same probe, same prompt, same conversation shape, same ~95,000 tokens, produced a larger summary that preserved both.

**The failure is on the compaction side, not the resume side — and that is directly evidenced, not inferred.** The origin session could no longer answer *before* any kill occurred, while its own process was still alive. Resume had not yet entered the picture. (The probe now encodes this attribution: when the pre-kill control fails, the nonce comparison is voided rather than read as a resume result.)

**Sample size, stated honestly.** One loss in two ~95,000-token `--pressure` runs. N is small. In the same session of work, every *other* compaction preserved the nonce verbatim: the small-conversation manual `/compact` runs (25k → ~2.1k, several runs) and PS1c's real auto-compaction (102k → 2.7k). So the loss is not simply "large conversations lose things" — the largest compaction measured is among the ones that preserved. **The conditions that produce the loss have not been isolated.**

**The mechanism is unknown.** No claim is made here about why one run's summariser produced 872 tokens and the next's produced more, nor about whether conversation content (the losing run's context was dominated by ~95k of synthetic filler), model sampling, or something else drives it. This paragraph separates what was measured from what would be a guess, and offers no guess.

**Scope change for [#1350](https://github.com/ms2sato/agent-console/issues/1350).** That Issue records exactly this concern for *our* handoff distillation — fidelity under uncoached usage. This is the first measurement showing it applies to the **SDK's own compaction** as well, so the question is not engine-specific: it spans both the distillation path we wrote and the summarisation path we delegate to the SDK.

**Correction trail — the `init` row's no-`resume` pin (R1, [#1410](https://github.com/ms2sato/agent-console/issues/1410), 2026-08-29): discharged and re-scoped, not deleted.**

The pin read *no `resume`* — "this engine constructs fresh sessions, and eviction, the feature that would pass `resume`, is not shipped". It was a **gate on an unprobed premise**: PS4 was typed-but-unprobed, so passing `resume` would have been building on a should-work claim. [#1400](https://github.com/ms2sato/agent-console/issues/1400) verified PS4, which discharged the gate, and R1 passes `resume`.

**The pin is re-scoped rather than removed**, because it was protecting two different things and only one of them expired. What expires: "never pass `resume`". What does not: **the engine must never invent a `resume` of its own.** The re-scoped pin is therefore:

> **`resume` appears in `query()`'s options if and only if it came from `init.resume`.** The engine has no other source for it — not `listSessions()`, not a scan of the SDK's own on-disk transcripts, not a value it remembers from an earlier query. The resume id is the server's to supply, derived from the `workers` row and nothing else.

The existing no-resume pin **test** is re-scoped the same way: it asserted `resume` never appears in the built options, and now asserts `resume` appears in the options exactly when the engine's deps carried one, and never otherwise. **This is a strictly stronger assertion than the one it replaces** — the old test would pass against an engine that had no `resume` support at all, which is precisely the state R1 changes; the new one fails both if `resume` goes missing when it was supplied and if it appears when it was not.

**Where the resume id comes from, and the failure handling.** The server sends `init.resume` only when the worker has been activated before **and** carries a persisted `sdkSessionId`; a first-ever activation, or one with no id, stays fresh exactly as before. Before the query is built, **the subprocess** pre-flights the id with `getSessionInfo` (PS7) -- the server cannot, for the reason in the layer correction trail below. The pre-flight has three outcomes, not two, and they are carried as distinct values all the way to the server rather than collapsed and reconstructed:

| pre-flight outcome | `sdk-resume-failed` reason | this activation | persisted `sdkSessionId` | incarnation |
|---|---|---|---|---|
| the session is there | *(no event)* | resumes | unchanged | unchanged |
| the lookup ran and found nothing | `not-found` | fresh, `sdkResumed: false` | **kept** | unchanged |
| the lookup could not run | `lookup-failed` | fresh, `sdkResumed: false` | **kept** | unchanged |
| a resume was sent and the SDK rejected it | `refused` | fresh, `sdkResumed: false` | **cleared** | replaced once |

The refusal case is the only one where a resume was actually attempted. It is detected by PS6's structural detector, answered with a `turn-error` naming the cause, and the server clears `sdkSessionId` and re-activates fresh **once**.

**The invariant is "a refused id is never retried" — not "there is never a second resume attempt".** The wider form stood here until 2026-08-29 and was never justified in that width. Its whole argument is a property of *refusal*: a rejected resume costs the turn in flight and leaves the SDK query dead in a live harness, so offering the same id again repeats the damage. Nothing in that argument reaches `not-found` or `lookup-failed`, which are decided **before** any resume is sent and whose retry costs one filesystem read (6-63 ms) with no turn at risk. Applied at the wider width the invariant discarded a session's continuity every time the store was momentarily unreadable — and, because a discarded id is never reconsidered, permanently.

**What clears a kept id is the fresh session superseding it.** Nothing needs to clear eagerly. The fresh session reports its own `sdk-session-id` at its first turn, and that overwrites and persists last-write-wins. This is the right authority as well as the right moment: once the user has spoken to the fresh session, that session *is* the conversation, and reviving the old one would abandon what was just said. So a kept id is retried only in the window before the user speaks again — exactly the window in which retrying is free.

**Idle eviction raises the stakes on all of this.** R3 ([#1412](https://github.com/ms2sato/agent-console/issues/1412)) drops an idle subprocess on purpose and wakes it on the next input, so activations -- and therefore pre-flights -- happen far more often than a worker's own lifecycle would produce. Every one of them is a fresh chance to read the store at a bad moment. A rule that discarded the id on a single unlucky read was tolerable when re-activation was rare; under eviction it is a conversation lost per unlucky read, on a timer.

**Accepted residual: a user who speaks before the worker recovers loses the old session.** Supersession overwrites the kept id, and the original conversation's SDK memory is gone for good. This is not fixed and is not intended to be: at that point the user has invested a turn in the live session, and preferring the older one would discard real work to recover memory of older work. The price is strictly smaller than the defect it replaces, which discarded the session even when nobody had spoken at all.

**Correction trail — a fix aimed at an unreachable branch, corrected by measurement before it shipped (2026-08-29).** The `lookup-failed` reason above exists because a lookup that *fails* and a session that is *absent* are genuinely different events, and the code path that conflated them was real. But the failure this document and the originating report both named as the motivating cause -- a transient `getSessionInfo` throw -- **does not occur on SDK `0.3.238`**, and the counter-evidence was already recorded in this document's own PS7, which states that `getSessionInfo` returns `undefined` *without throwing*. The report was written from the code path without checking its entry condition against the premise ledger; the AC adopted the report's premise for the same reason. Recorded by the Architect as their own miss, at their instruction, alongside the §4.3 boundary row of the same day: the same shape twice -- citing a document and not reconciling it with a measurement already in hand.

What the measurement changed: the actual reachable route for every filesystem fault is `not-found` (see PS7's table), so the fix moved to where the defect actually lives -- `not-found` stops clearing -- and the `lookup-failed` mapping stays as the structurally correct shape for a version where the SDK does throw. It is **currently unreachable**, and is documented as such rather than deleted: PS7 is version-pinned, the `catch` it replaces exists in production today and currently mislabels what it caught, and a bump can make the path live without notice.

**Correction trail — the two anticipated failure shapes were both wrong (R1, 2026-08-29).** R1's AC, authored by the Architect, anticipated exactly two ways an invalid resume could fail: a **loud** one (the constructor throws synchronously, rescued in `main.ts` alongside the existing construction-failure rescue) and a **silent** one (the session starts fresh and is caught by comparing the requested session id against the one reported at the `sdk-session-id` handler). The G2 gate measured the real behavior before implementation and **neither occurs**. Construction succeeds; the failure surfaces only once a turn is in flight; and no `system:init` ever arrives, so the `sdk-session-id` handler — the entire basis of the silent detector — never runs. The id comparison would have been worse than useless on the nonexistent-uuid shape, where the failing `result` carries **the requested id**: comparing it against the request would have matched, and reported a failed resume as a success.

Recorded as the AC author's own miss, at their instruction. The general lesson is the one this document keeps re-learning: an anticipated failure shape is a hypothesis, and a gate that measures it before implementation is what keeps the hypothesis from being built on. Both anticipated shapes were plausible; the gate cost one probe and changed the mechanism, the detector, and the layer the fallback lives in.

**Correction trail — the pre-flight's layer was unspecified, and the obvious reading was wrong (R1, 2026-08-29).** The ruling that introduced the `getSessionInfo` pre-flight said to run it *before constructing the query* and did not name **which process** runs it. The natural reading — the server, which is where the resume id is decided — is broken in the deployment this feature exists for. `getSessionInfo` reads the **calling OS user's** own session store, and in multi-user mode the server is a different user from the worker: a server-side pre-flight would find nothing for every worker but its own, report "no session" every time, and silently convert every re-activation into a fresh start. The failure is invisible in single-user dev, where the two users coincide.

It runs in the subprocess, which is already spawned as the requesting user. Same mechanism, same gate, correct in both modes.

Recorded, again at the AC author's instruction, as the third defect in that ruling — and the one whose shape is most reusable: it is `pre-pr-completeness.md` Q9's target-environment cross-check, not applied by its author to their own ruling. Q13 names the role-switch blind spot for verification plans; this is the same blindness one layer over, in a design decision. **A layer that is left unstated has a default reading, and the default is not neutral** -- it is whichever layer the writer happened to be thinking from.

**Removed row — `handoff` (#1401, 2026-08-28).** The `handoff` command is gone from `EmbeddedAgentCommand` entirely, so it has no row: commands are not persisted, and a union member no client or server can send is dead weight. Its replacement is not a command at all — auto compaction fires inside the engine, and manual compaction arrives as a `Compact` tool call. The engine-level mechanism it named (distill → terminate → reseed) is deleted from `sdk-engine.ts` along with it.

**Correction trail — `context-usage`/`context-handoff` rows (SDK Engine Phase 2 implementation, 2026-08-18):** the rows above described the target mapping before implementation; both are now built. Three details the pre-implementation text did not fully specify, settled during implementation and recorded here rather than as a correction to a wrong premise (none of PS1/PS2/H2 moved from what §5 already stated):

- **H2's retry budget** is 6 attempts with a 500ms settle delay between attempts (5 gaps, 2500ms total) — comfortably above both the empirically observed 300–500ms settle window and the AC's "at least 3 attempts spanning at least 2s" floor. Named constants `CONTEXT_USAGE_MAX_ATTEMPTS`/`CONTEXT_USAGE_SETTLE_DELAY_MS` in `sdk-engine.ts`.
- **The PS1 tripwire** (§5) is a runtime compaction detector, not just a documentation caveat: the engine remembers the previous poll's `totalTokens` and logs a loud warning naming PS1 if a later poll drops by more than 20% with no intervening compaction (`MATERIAL_DROP_RATIO` in `sdk-engine.ts`). **Made mode-aware by #1401**, because with auto-compaction ON a large drop is now the expected outcome rather than a violation: with the toggle OFF a material drop still warns exactly as before; with it ON, a drop **accompanied by a `compact_boundary`** produces only the boundary marker, while a drop with **no** boundary still warns — an unexplained shrinkage remains a genuine anomaly no matter which mode we are in, and that quadrant is the whole reason the tripwire is not simply deleted when the toggle is ON.
- **The reseed-vs-clean-stream-end interaction (S4, not previously named in this table):** terminating the old query to reseed made its `consumeLoop` end without throwing — the same shape Phase 1's clean-stream-end guard treats as fatal. Phase 2 added a per-query generation counter so a superseded loop could recognize itself. **Retired with the mechanism (#1401):** with handoff gone there is exactly one `query()` per engine and nothing can supersede it, so the counter degenerated to a constant and was removed, returning the guard to its Phase 1 shape (a clean end is unexpected unless `dispose()` caused it).

**Correction trail — `tool-call` row's "only render" premise, RETIRED ([#1457](https://github.com/ms2sato/agent-console/issues/1457), 2026-08-30).** This row read *"Downstream consumers only render, so the contract holds"*, and the premise was load-bearing: it is what licensed emitting `tool-call` immediately on observation without regard to where the iteration's `assistant-message` lands relative to it.

**A structural consumer exists now, and did not always.** Transcript restore's `replayWindow` does not render the stream — it rebuilds a provider-shaped conversation from it, and it read the relative order of `assistant-message` and `tool-call` as meaningful. This engine emits the call first for an iteration that opens with a tool use, since there is no accumulated text to flush yet; the reader was written against the other engine, which emits the (empty) assistant message first. The result was that **every `claude-sdk` turn beginning with a tool call failed restore** and fell to the destructive reset — reproduced on a two-turn conversation of thirteen lines, with no rotation involved.

The premise's failure is not that rendering was the wrong description of the consumers that existed then; it is that **a premise about "all consumers" was recorded against the consumers of the day and never re-asked when a new one was added.** The consumer that broke it — restore — was designed later, in a different document, by someone reading the reader's own expectations rather than this row.

**The writer is unchanged.** Immediate emission is what the row's own earlier correction trail deliberately chose, and changing it now would not help any log already written. The reader was made to accept either order instead, discriminating a turn that legitimately opens with a tool call (its `user-message` is in the window) from debris left by a window that began mid-turn (it is not).

**Correction trail — `ready` row (SDK Engine Phase 1 implementation, 2026-08-17):** this table's original text classified `ready` as `mapped`, described as "emitted after the SDK session's init/system message is received". A live probe against SDK 2.1.233 during implementation found this cannot work: `system:init` is gated on the FIRST prompt being yielded on the streaming-input generator — zero events of any kind arrive while the queue is empty, not even a spawn signal. A literal ⟺-mapped implementation would deadlock every worker that has no initial prompt queued at activation (the exact shape `main.ts`'s activation-complete contract depends on). The row above reflects the corrected design, consulted with the Architect the same day: `ready` is engine-authored at construction — decoupled from `system:init` entirely — matching openai-api parity (that engine's `ready` is also authored by the subprocess host, not derived from the provider). `sdk-session-id` (the row above) is unaffected and remains the SDK-derived signal for session establishment; it simply now arrives strictly after `ready`, bundled with the first real turn (sub-30ms lag in the probe), rather than gating it.

**Both-version confirmation (SDK Engine Phase 1 implementation PR; see the version-naming correction in §5):** re-verified identically on `0.3.226` and `0.3.233` — zero events of any kind arrived before the first prompt was yielded on either version, and `system:init` arrived ~22ms after the first prompt yield on `0.3.226` versus ~28ms on `0.3.233` (both consistent with the sub-30ms figure recorded above). The decoupling design is unaffected by the version difference.

**Third-version confirmation (Issue #1338 SDK bump, 2026-08-28):** re-verified on `0.3.238` — zero events arrived before the first prompt was yielded on the streaming-input generator, and `system:init` arrived 24ms after the yield (consistent with the sub-30ms figures recorded on `0.3.226`/`0.3.233`). The decoupling design is unaffected.

**Correction trail — `tool-call` row (SDK Engine Phase 1 implementation, real-browser QA finding, 2026-08-17):** the implementation originally buffered every `tool_use` block observed on an `assistant` SDKMessage and flushed it (emitted `tool-call`) only at that iteration's `message_stop`, specifically so `tool-call` would follow `assistant-message` on the wire — matching the native engine's own emission order. This assumed `tool-result` (sourced from the SDK's own `user`-role `tool_result` echo, emitted immediately/unbuffered) could never arrive before the `message_stop` that flushes its matching `tool-call`, because the SDK "can't have a result before it fully described the call". That assumption was never verified against a real run; it was a single earlier probe observation elevated to a guarantee. A real dev-instance Browser QA session captured a live NDJSON transcript where the `tool_result` for a fast `Glob` call arrived on the wire BEFORE the buffered `tool-call` was flushed — the client (`embedded-agent-store.ts`'s `applyToolResult`) correctly treats an unknown callId as corruption and silently drops the result, producing observable transcript corruption. The corrected, precisely-named premise this table now relies on is: *the complete `assistant` SDKMessage containing a `tool_use` block is yielded by the query iterator before the `user` SDKMessage carrying that call's `tool_result`* (single-iterator transcript-order FIFO on `query()`'s own AsyncGenerator). This premise is plausible by construction and held in a 5-trial live re-probe (`Glob`, the same adversarial fast-tool shape as the captured bug) run during the fix, but is understood to be a NAMED premise, not folklore. The implementation now (a) emits `tool-call` immediately upon observing the `tool_use` block on the `assistant` message, no longer buffered until `message_stop`, and (b) adds a structural guard at the SDK boundary: a `tool_result` for a callId whose `tool-call` has not yet been emitted is held in a per-callId queue and flushed immediately once that `tool-call` is emitted, so a future violation of the premise degrades to correct re-ordering (or, in the pathological case where the `tool-call` never arrives at all before the turn ends, a still-delivered but loudly logged result) rather than silent data loss. See `sdk-engine.ts`'s `handleAssistantMessage` / `handleUserMessage` / `flushOrphanedToolResults` for the implementation and `__tests__/sdk-engine.test.ts` for the bug-polarity and guard tests (including a fixture reproducing the captured transcript's exact ordering).

**Re-verified (Issue #1338 SDK bump, 2026-08-28):** the FIFO premise held on `0.3.238` in a fresh live re-probe using a fast `Glob` call (the same adversarial shape as the originally-captured bug) — the `assistant` SDKMessage carrying the `tool_use` block arrived 14ms before the `user` SDKMessage carrying its `tool_result`. The ordering guard remains in place regardless; this is confirmation, not a relaxation.

**Remaining `verify`-marked rows, re-confirmed (Issue #1338 SDK bump, 2026-08-28):** the `user-message` row's streaming-input mechanism was re-exercised with a genuine second turn pushed onto the same live `query()`'s queue after the first turn's `result` — both turns settled normally on one session id, on `0.3.238`. The `cancel` row's `interrupt()` behavior was re-exercised mid-stream on `0.3.238` and produced the same recorded shape (`result.subtype === 'error_during_execution'`, `result.terminal_reason === 'aborted_streaming'`). The `assistant-delta`/`assistant-thinking-delta` rows' `includePartialMessages` mechanism was observed functioning normally (`stream_event`/`content_block_delta`/`text_delta`) across every probe in this bump's re-verification; a dedicated thinking-delta re-probe was not run (the row's own caveat — model-config-dependent, absent when the model emits no thinking — makes this an expected non-observation, not a gap).

### A.3 Server-side events (engine-agnostic)

`user-message` (server echo), `exited`, and `turn-interrupted` are appended by the SERVER, not the subprocess — unchanged for both engines by construction. Listing them here prevents a future reader from hunting for their SDK mapping.

**`turn-interrupted` (new, R1).** Appended at activation when the persisted stream shows a turn that never reached a terminal event — a `user-message` with no `state: 'idle'` and no `turn-error` after it. Rendered on replay as a marker row, so a conversation that was cut off mid-turn says so instead of ending in silence.

**Server-authored on purpose.** A.3's rule is that the server does not forge engine-authored events, so this is emphatically **not** a synthesized `turn-error`: no engine reported an error, and a fabricated one would be a claim about what the model did. `turn-interrupted` says only what the server itself observed — that a turn was started and no terminal event was ever recorded for it — which is a fact about the transcript, and the server is the transcript's writer.

**Detection rule and its terminal set.** The terminal set is **`{ state: 'idle', turn-error }`**, and `exited` is deliberately **not** in it. The rule is: *a `user-message` with no `state: 'idle'` and no `turn-error` after it was interrupted.* Both the exclusion and the inclusion are load-bearing:

- **Why `exited` is excluded.** The server appends `exited` on **every** exit it observes, so including it would make the detector fire only when the server itself died without appending — and never for a worker death the server did observe, which is the common case and the one a deliberate eviction ([#1412](https://github.com/ms2sato/agent-console/issues/1412)) creates by design.
- **Why `turn-error` is included** — and this is where the rule's original rationale was wrong. It was first justified by a suspicion that the `openai-api` loop emits `turn-error` without a following `idle`. **That is false, and one grep disproves it**: `agent-loop.ts`'s `emitTurnError` is a single private helper that emits `turn-error` and then unconditionally calls `emitIdle()`, and all twelve call sites go through it — an existing test (`agent-loop.test.ts`, "emits a single turn-error then state idle") already pinned the order `['state', 'turn-error', 'state']`. On that engine `turn-error` is redundant with `idle`.

  It is **not** redundant on this one. `sdk-engine.ts`'s `handleResult` emits `turn-error` for a non-success subtype and then, when a `Compact` was booked during that turn, **returns before emitting `idle`** — the turn is held open until the injected `/compact` reaches its own `result` (#1401). That is a real window in which `turn-error` stands with no `idle` behind it, and a process death inside it would be misclassified as interrupted under an idle-only rule. The mechanism that saves the rule is the deferral #1401 introduced — so the correct rationale was one layer down from where it was first looked for.

**Vacuous cases are not interruptions.** An empty stream (no `user-message` at all) and a position immediately after a completed turn boundary both yield "not interrupted". Stated explicitly because `[].every()`-shaped vacuity is this codebase's recorded blind spot, and because "no terminal event after the last user-message" reads as true when there is no last user-message.

**Scope.** R1 ships detection and the local signal only. Routing it to a delegating parent that is still waiting stays in [#1273](https://github.com/ms2sato/agent-console/issues/1273), and re-delivering the interrupted instruction is out of scope by the owner's decision and #1264's ruling. This event is the hook a future delivery mechanism would read.

### A.4 Coverage statement

Every member of `EmbeddedAgentCommand` and `EmbeddedAgentEvent` appears above (as of #1401, which added `context-compacted` and removed the `handoff` command; R1 added `init.resume` to the `init` row and `turn-interrupted` to A.3); nothing is classified `unavailable`. The two `approximated` degrees of freedom (turn-error granularity; thinking-delta model dependence) carry their consequences in place. If the shared union gains a member, this table gains a row in the same PR — the union and the table are a mirror pair.
