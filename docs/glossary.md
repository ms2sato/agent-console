# Glossary

This document defines canonical terminology used throughout the Agent Console project to resolve terminology drift across documentation and codebase.

## Core Architecture

### Agent
A general term for AI-powered tools like Claude Code. See also: [AgentDefinition](#agentdefinition), [AgentWorker](#agentworker).

### Vendor Authentication (agent → LLM provider)
**How an agent authenticates to its LLM vendor, and Agent Console's deliberate non-involvement in it.** Three distinct cases are routinely conflated; they are not the same mechanism and only one of them involves the server at all.

| Case | Who holds the credential | Server's role |
|---|---|---|
| **Terminal agent, personal session** | The OS user's own home (e.g. Claude Code's own login state) | **None.** The server spawns the CLI as that OS identity; the CLI reads its own home. |
| **Terminal agent, [SharedSession](#sharedsession)** | The shared account's own home, placed by the operator | **None.** Structurally identical to the personal case — only *whose* home differs. |
| **[EmbeddedAgentWorker](#embeddedagentworker) provider key** | The server, delivered over stdin at activation | **Holds and delivers it.** See [McpToken](#mcptoken) neighbours and the init handshake. |

**The first two cases are the reason this entry exists.** For terminal agents, Agent Console does not supply, inspect, constrain, or observe vendor credentials — it spawns a process as an OS identity and that identity's home decides everything. This is a scope boundary, not an unimplemented feature: the host runs arbitrary agent CLIs, so encoding one vendor's licensing terms as a system-enforced constraint would impose that vendor's rules on agents those rules do not govern. Compliance with a given CLI's terms is resolved locally, by whoever configures that CLI.

**The third case is genuinely different** and is the one place a credential crosses the server. It exists because an embedded agent has no CLI of its own to carry credentials — `EmbeddedAgentDefinition.provider` names an OpenAI-compatible endpoint, and the key travels as the first stdin message specifically so it touches neither argv nor env. **It is not the Claude path**: an embedded agent pointed at Claude via the Agent SDK would carry no `provider.apiKey` at all, because the SDK picks up the executing user's own auth like any other CLI (Issue [#1324](https://github.com/ms2sato/agent-console/issues/1324)).

- **Common misreading:** that Agent Console handles Anthropic API keys generally. It does not — for terminal agents it handles none, and the embedded provider key is for OpenAI-compatible providers.
- **See:** [Authentication model in shared-orchestrator-session.md](design/shared-orchestrator-session.md#authentication-model); [Credentials in embedded-agent-worker.md](design/embedded-agent-worker.md#credentials-provider-keys--the-init-handshake); `scripts/setup-shared-account.sh` (provisions the account, deliberately writes no secrets)

### AgentDefinition
The stored configuration for an AI agent, including command templates and activity patterns. Referenced by `agentId` in [AgentWorker](#agentworker).
- **Aliases:** Agent configuration, Agent preset
- **See:** [Agent concepts in session-worker-design.md](design/session-worker-design.md#agent-types)

### AgentKind
**Implemented (Issue #1160 PR-A).** The discriminator `'terminal' | 'embedded'` distinguishing which registry an agent entry belongs to. Single writer: the `AGENT_KINDS` constant in [agent-surface.ts](../packages/shared/src/types/agent-surface.ts); every consumer derives from it or the `AgentKind` type rather than hardcoding the union. Does not merge [AgentDefinition](#agentdefinition) and [EmbeddedAgentDefinition](#embeddedagentdefinition) — the two registries stay separate; `AgentKind` only tags which one a given [AgentDirectoryEntry](#agentdirectoryentry) came from.
- **See:** [Agent Surface design](design/agent-surface.md)

### AgentDirectoryEntry
**Implemented (Issue #1160 PR-A).** A kind-tagged union `{ kind: 'terminal'; agent: AgentDefinition } | { kind: 'embedded'; agent: EmbeddedAgentDefinition }` returned by [AgentSurface](#agentsurface) and [AgentDirectory](#agentdirectory). Full-fidelity (not a lossy summary projection) — consumers narrow on `kind` via an exhaustive switch/if-else to recover the concrete `AgentDefinition` or `EmbeddedAgentDefinition`.
- **See:** [Agent Surface design](design/agent-surface.md)

### AgentSurface
**Implemented (Issue #1160 PR-A).** A per-registry query interface (`list` / `get` / `findByName`, generic over [AgentKind](#agentkind)) implemented by both `AgentManager` (`AgentSurface<'terminal'>`) and `EmbeddedAgentManager` (`AgentSurface<'embedded'>`). Read-only query surface; does not add CRUD or lifecycle methods beyond what each manager already exposes.
- **See:** [Agent Surface design](design/agent-surface.md)

### AgentDirectory
**Implemented (Issue #1160 PR-A).** A stateless, policy-free composite (`packages/server/src/services/agent-directory.ts`) over the `terminal` and `embedded` [AgentSurface](#agentsurface) registries. Provides `listAll()` (used by the MCP `list_agents` tool) and `resolve({ agentId?, agentName? })` (used by `delegate_to_worktree`'s agent resolver, absorbing the short-term two-registry facade from PR #1165 verbatim — same terminal-first-by-id precedence and ambiguity error messages). Owns no lifecycle, no caching, no CRUD; suggestion policy and default-agent policy stay at callers, following the same strict-thin-wrapper discipline as [`privilege-elevation.ts`](../.claude/rules/elevation-helpers.md). Does NOT merge [AgentDefinition](#agentdefinition) and [EmbeddedAgentDefinition](#embeddedagentdefinition) — the two registries remain separate data models with separate id namespaces; `AgentDirectory` only unifies what their consumers can *query*.
- **See:** [Agent Surface design](design/agent-surface.md)

### AgentOperation
**Implemented (Issue #1160 PR-D).** The discriminator naming a cross-surface action performable against "an agent" (`listAgents`, `resolveAgent`, `createSessionWithAgent`, `addWorkerToSession`, `manageDefinitions`, `restart`). Single writer: the `AGENT_OPERATIONS` constant in [agent-operations.ts](../packages/shared/src/types/agent-operations.ts). Distinct from [AgentKind](#agentkind): `AgentKind` tags which registry an agent belongs to; `AgentOperation` names what a consumer surface (UI / MCP / embedded-visible) can do to an agent. Each surface owns an exposure table typed `satisfies Record<AgentOperation, SurfaceExposure>`, so adding a new operation is a compile error in every table until it records an explicit exposed/not-exposed decision.
- **See:** [Agent Surface design](design/agent-surface.md) Mechanism 3

### SurfaceExposure
**Implemented (Issue #1160 PR-D).** The value type of an exposure-table entry: `{ exposed: true; via: string } | { exposed: false; reason: string }`. `via` names a human-locatable entry point (a component, a page, an MCP tool name); `reason` is the rationale for an intentional omission. Defined alongside [AgentOperation](#agentoperation) in `agent-operations.ts`.
- **See:** [Agent Surface design](design/agent-surface.md) Mechanism 3

### AgentParameterCapabilities
**Implemented, Phase 1 (Issue #1541); unchanged by Phase 2 (Issue #1554) — Phase 2 added a separate kind-dispatch layer instead of widening this accessor.** The result shape `{ model: boolean; reasoningEffort: boolean }` answering "does this **terminal** agent accept a model / reasoning-effort override?" Single writer: `getAgentParameterCapabilities(agent)` in [agent-parameter-capabilities.ts](../packages/shared/src/types/agent-parameter-capabilities.ts) — for a terminal [AgentDefinition](#agentdefinition), derives the answer by scanning `commandTemplate` for `{{model...}}` / `{{effort...}}` placeholders. **No stored boolean anywhere**: a `supportsModel`-shaped flag beside the template would be a second writer to the same fact, letting template-vs-flag drift become a defect class (mirrors [AgentCapabilities](#agentdefinition)'s `computeCapabilities()`, recomputed fresh on every read rather than persisted). The wire fields (`model`, `reasoningEffort`) are pass-through strings validated at the schema boundary (non-empty after trim) and enforced against this accessor's result at `WorkerLifecycleManager.createWorker` — the ONE validation choke point covering session creation, the add-worker route, `POST /:id/worktrees`, and MCP `delegate_to_worktree`. A worker's accepted override is persisted on the `workers.model` / `workers.reasoning_effort` columns (migration v37) and beats its agent definition's own template default; the override survives a same-agent restart but is dropped on an agent change. `buildAgentParameterTemplateVars` maps the wire field `reasoningEffort` onto the **`effort`** template variable (not `reasoningEffort`) when merging into `expandTemplate`'s `templateVars` at `WorkerManager.activateAgentWorkerPty`. **Detection and consumption are not the same fact.** `getAgentParameterCapabilities` (detection) scans `commandTemplate` only, by design, and stays that way. But `WorkerManager.activateAgentWorkerPty` gates the actual per-activation merge on `templateSupportsModel(template)` / `templateSupportsReasoningEffort(template)` called against the ACTUALLY-SELECTED template — which for a `'continue'` startup intent is `continueTemplate`, not `commandTemplate`. The builtin Claude Code agent's `continueTemplate` literal now also carries `{{model:+--model}}` (Issue [#1299](https://github.com/ms2sato/agent-console/issues/1299) PR-2), so a worker-level override is consumed on the continue path too even though this accessor's own detection result (derived from `commandTemplate`) is unaffected and unchanged. **Phase 2 did NOT widen this accessor's input** — the Architect ruled that `getAgentParameterCapabilities` stays terminal-only, unmodified. Instead, a SEPARATE kind-dispatching entry point, `getAgentParameterCapabilitiesFor(entry: AgentDirectoryEntry): `[`AgentParameterCapabilitiesByKind`](#agentparametercapabilitiesbykind) in `agent-surface.ts`, spreads this accessor's own (unchanged) result for a terminal entry and derives from [`EMBEDDED_AGENT_ENGINE_PARAMETER_CAPABILITIES`](#embedded_agent_engine_parameter_capabilities) for an embedded one — see those entries for the boolean-only dispatch view and its per-engine, full-fidelity source table.
- **See:** [Model & Reasoning-Effort Parameters in agent-surface.md](design/agent-surface.md#model--reasoning-effort-parameters-issue-1521-phase-0--design-rulings)

### AgentParameterCapabilitiesByKind
**Implemented (Issue #1554, Phase 2 of #1521).** The boolean-only capability view `{ model: boolean; reasoningEffort: boolean; contextWindowTokens: boolean }`, defined in [agent-surface.ts](../packages/shared/src/types/agent-surface.ts). The return type of `getAgentParameterCapabilitiesFor(entry: AgentDirectoryEntry)`, the SINGLE kind-dispatch entry point for this shape — every consumer that needs to know "can this entry accept model / reasoningEffort / contextWindowTokens", regardless of whether the entry is terminal or embedded, calls this function rather than re-deriving per-kind logic. For a terminal entry it spreads [AgentParameterCapabilities](#agentparametercapabilities)'s own (unchanged) result plus `contextWindowTokens: false`; for an embedded entry it derives from [`EMBEDDED_AGENT_ENGINE_PARAMETER_CAPABILITIES`](#embedded_agent_engine_parameter_capabilities), keyed by the definition's `engine`. `contextWindowTokens` is derived per-KIND here rather than stored on the per-engine table, because it is a fact about the KIND (terminal has no repo-side context-window concept at all) intersected with the engine's `model` capability, not a fact about the engine alone — a terminal entry is always `false`; an embedded entry equals its model row's `capable`. **Not used by `WorkerLifecycleManager.createWorker`'s embedded-agent validation branch** — that branch already knows its kind statically and needs the full per-row shape (`acceptedValues` / `reason`), which this boolean-only view intentionally discards.
- **See:** [Agent Surface design](design/agent-surface.md)

### EMBEDDED_AGENT_ENGINE_PARAMETER_CAPABILITIES
**Implemented (Issue #1554, Phase 2 of #1521).** The per-(engine, param) capability table in [embedded-agent-parameter-capabilities.ts](../packages/shared/src/types/embedded-agent-parameter-capabilities.ts) — SINGLE WRITER for embedded-agent parameter capability. Row type `EmbeddedAgentEngineParameterCapability` is a discriminated union, not optional fields on a single shape: `{ capable: true; acceptedValues: readonly string[] | null; consumptionSite: string } | { capable: false; reason: string }` — every capable row names where the value is actually consumed, every incapable row names why. `acceptedValues: null` means pass-through (the provider/SDK is the value-domain authority, this file does no local value validation); a non-null array is a closed domain rejected upstream, at `WorkerLifecycleManager.createWorker`'s creation-time validation choke point, not by this table. Consumed directly by that same validation branch — not via [AgentParameterCapabilitiesByKind](#agentparametercapabilitiesbykind), which discards the full row on purpose — because the branch needs `acceptedValues` / `reason`, not just a boolean.
- **See:** [Agent Surface design](design/agent-surface.md)

### EFFORT_LEVELS
**Implemented (Issue #1554, Phase 2 of #1521).** The closed `EffortLevel` value domain (`'low' | 'medium' | 'high' | 'xhigh' | 'max'`), hand-written in [embedded-agent-parameter-capabilities.ts](../packages/shared/src/types/embedded-agent-parameter-capabilities.ts) alongside [`EMBEDDED_AGENT_ENGINE_PARAMETER_CAPABILITIES`](#embedded_agent_engine_parameter_capabilities), and used as the `claude-sdk` engine's `reasoningEffort` row's `acceptedValues`. Anchored to the Claude Agent SDK's own `EffortLevel` type (`Options.effort?: EffortLevel`) via a mutual, both-directions type-level pin, so drift in either direction — the SDK adds/removes a level, or this array drifts from it — fails `tsc` rather than compiling silently. Freshness is bounded by `packages/shared`'s own devDependency pin on `@anthropic-ai/claude-agent-sdk`: bumping the SDK version in `packages/embedded-agent` (the runtime consumer) requires bumping `packages/shared`'s devDependency to match in the same PR, or the pin keeps compiling green against a stale `EffortLevel` definition that no longer reflects what the running subprocess actually sends.
- **See:** [Agent Surface design](design/agent-surface.md)

### workers.context_window_tokens
**Implemented (migration v38, Issue #1554, Phase 2 of #1521).** A nullable `INTEGER` column on `workers` — the per-worker context-window override, distinct from `embedded_agents.context_window_tokens` (the definition-level default, migration v34/v36). Meaningful only alongside a non-null `workers.model` override ([agent-surface.md](design/agent-surface.md) Ruling 4, "do not inherit"): a model override with no window of its own means undeclared, never inherited from the definition's own window, because the definition's number was operator-declared for the definition's own model, not for whatever the worker happens to be overridden to. The invariant `context_window_tokens IS NOT NULL ⇒ model IS NOT NULL` is enforced at `WorkerLifecycleManager.createWorker`'s embedded validation branch, not by a stored flag column. Effective value resolved by `resolveEffectiveContextWindow(definition, worker)` in `packages/server/src/services/embedded-agent-context-window.ts` — see [Context Usage](#context-usage).
- **See:** [Agent Surface design](design/agent-surface.md)

### Repository
A registered Git repository available for session creation. Code reference: `repositoryId` (UUID).
- **See:** [Core concepts in session-worker-design.md](design/session-worker-design.md#key-concepts)

### RepositoryInUseError
The single-writer rule for whether a [Repository](#repository) is currently in use by any session. Enforced by `RepositoryManager.assertRepositoryNotInUse`, which combines the in-memory active-session check with a check over persisted session rows that are not currently active in memory — a repository with a paused [WorktreeSession](#worktreesession) counts as in-use, not only one with active sessions. The `DELETE /api/repositories/:id` route maps a thrown `RepositoryInUseError` to `409 Conflict`.
- **See:** `packages/server/src/services/repository-manager.ts`

### Clone Job
An asynchronous server-side job that clones a remote Git URL into the shared [source-repos directory](#source-repos-directory) and registers the result as a [Repository](#repository) (Issue [#834](https://github.com/ms2sato/agent-console/issues/834)). The HTTP endpoint `POST /api/repositories/clone` returns `202 Accepted` with a `jobId`; the client polls `GET /api/repositories/clone/:jobId` for status (`pending` / `cloning` / `succeeded` / `failed`). On failure, a classified `CloneErrorCode` (`auth_failed` / `network_error` / `repo_not_found` / `permission_denied` / `name_conflict` / `timeout` / `validation_error` / `unknown`) lets the UI render actionable copy. In multi-user mode, the clone subprocess runs as the requesting user via the privilege-elevation pattern ([Issue #837](https://github.com/ms2sato/agent-console/issues/837)).
- **Aliases:** clone-and-register job
- **See:** `packages/shared/src/schemas/repository.ts` (`CloneRepositoryRequestSchema`, `CloneJobStatusResponse`)

### Worktree Deletion Job
An asynchronous server-side job (`worktree:delete`, [Issue #1327](https://github.com/ms2sato/agent-console/issues/1327)) that removes a [Worktree](#worktree) and its matching sessions in the background, replacing an earlier fire-and-forget pattern that reported outcome only via a one-shot WebSocket broadcast with no durable record. Triggered by `DELETE /:id/worktrees/*?async=true`, which enqueues the job (payload: `repoId`, `worktreePath`, `force`, `requestUsername`) via the existing persistent `JobQueue` and responds `202 { accepted: true, jobId }`. The handler (`jobs/worktree-delete-job-handler.ts`, deliberately kept out of `jobs/handlers.ts` to avoid an import cycle) runs the same `deleteWorktree` logic the synchronous path uses and still emits the live `worktree-deletion-completed` / `worktree-deletion-failed` broadcasts (`taskId` carries the job id) — but `GET /api/jobs/:id` is now the durable recovery path: a client that reloads, misses the broadcast, or opens the task in a different tab can re-derive terminal state from the persisted job row instead of losing it. Enqueued with `maxAttempts: 1` — deletion must not be silently retried, since force semantics, the open-PR check, and a watching user all make a silent second attempt wrong; a failure reaches job status `stalled` with `lastError` set rather than being retried.
- **See:** `packages/server/src/routes/worktrees.ts`, `packages/server/src/jobs/worktree-delete-job-handler.ts`

### Artifact (HTML Artifact)
**Implemented, phase 1 (storage, `create_html_artifact` tool, and the server routes) (Issue #1312, spec: [html-artifacts.md](design/html-artifacts.md)).** A single user-uploaded HTML document stored by the server under `<AGENT_CONSOLE_HOME>/artifacts/<users.id>/`, addressed by a random UUID, owned by the user whose session created it ([created_by](#created_by) of the calling worker's session — never the MCP caller identity, same layering as [Delegation Parent](#delegation-parent--parentsessionid-parentworkerid)), and viewable by **any authenticated user**. Created via the `create_html_artifact` MCP tool and removed via the `delete_html_artifact` MCP tool (Issue #1371), both reachable from terminal and embedded agents (no builtin-tool variant — excluded by the [Builtin Tool](#builtin-tool-embedded-agent) narrow-context invariant). Served byte-verbatim behind the **artifact origin boundary**: a `Content-Security-Policy: sandbox allow-scripts` response header giving the document an opaque origin (no cookies, no localStorage, no authenticated app API), plus a resource CSP making v1 artifacts self-contained (no external network). `allow-same-origin` is permanently forbidden. Scripts execute (owner requirement); the sanitizer is deliberately absent from this path. A same-origin-served, script-executing document can still navigate *itself* to an external URL to exfiltrate data — nothing in the CSP/sandbox pairing above stops this — so a mandatory, server-rendered **viewer shell** (`GET /artifacts/:id`, outside `/api`, its own `authMiddleware`) closes that gap: it wraps the raw endpoint in a sandboxed iframe and carries `Content-Security-Policy: default-src 'none'; frame-src 'self'`, which governs the artifact iframe's own navigations (including self-navigation). The raw endpoint gates on the `Sec-Fetch-Dest` request header first — a genuine iframe-embedded load (`Sec-Fetch-Dest: iframe`) gets raw bytes, anything else with the header present redirects to the shell. When the header is entirely absent (Issue #1366: browsers only attach Fetch Metadata to potentially-trustworthy origins — HTTPS or localhost — so a plain-HTTP LAN origin never sends it, including from the shell's own genuine iframe load), the gate falls back to a **viewer token**: a single-use, 60s-TTL, artifact-id-bound credential the shell mints on every render and embeds in the iframe `src` (`?vt=<token>`, `lib/artifact-viewer-tokens.ts`). The token is never an authentication signal — it proves only that a shell render induced the request, not who is asking. Phase 1 ships the `artifacts` DB table, on-disk storage, the `create_html_artifact` and `delete_html_artifact` MCP tools, the server routes (`GET /api/artifacts/:id` serving, `GET /api/artifacts` list, `DELETE /api/artifacts/:id` delete), and this mandatory viewer shell; a richer browsing UX (history list, title, delete button) is deferred to a later phase, layered around the same server-side shell rather than replacing it — see the wire summary type [`Artifact`](../packages/shared/src/types/artifact.ts) (id/title/createdAt/sizeBytes; content is deliberately never part of this shape). `create_html_artifact` / `delete_html_artifact` also emit a trigger-only `artifact-created` / `artifact-deleted` app-socket message (`packages/shared/src/schemas/app-server-message.ts`) after the repository write succeeds (Issue #1520), so the session artifacts panel, the `/artifacts` list route, and the [Notification Center](#notification-center) badge all refetch without a page reload — the message carries only `{ sessionId, artifactId }`, never content, per [Notification Center](#notification-center)'s N1.
- **See:** [html-artifacts.md](design/html-artifacts.md) §3 (boundary, named premises), §6 (surfaces)

### Bookmark
**Implemented (Issue #1379, extended by Issue #1390).** A pointer to an arbitrary external URL (plus an optional title), stored in the `bookmarks` table (`user_id`, `source_session_id`, `url`, `title`, `origin`, `created_at`). Owned by `user_id`, the sole authorization scope for read/delete (REST: `authUser.id === bookmark.userId`; MCP: `session.createdBy === bookmark.userId`); `source_session_id` is a secondary list filter, not an authorization boundary — a bookmark survives the deletion of the session it was filed from and remains among the user's bookmarks. This same column is also the **only correct address** for the realtime-refresh delete trigger's `sessionId` (Issue #1520): the session panel's read side is scoped by `source_session_id` (`findByUserIdAndSourceSessionId`), so the delete trigger's write side must name that same session — never the session that happened to call `delete_bookmark` — or the two addresses diverge for a cross-session delete (I-1, I/O Addressing Symmetry). Do not remove or repurpose this column without re-deriving that trigger's address. **`origin` (`'user' | 'agent'`) records who registered it**: `'user'` via the session-context UI form, `'agent'` via the `create_bookmark` MCP tool. Rendered as a plain external link (`target="_blank" rel="noopener noreferrer"`, title as a text node) plus a structurally independent host line (`new URL(bookmark.url).host`, always visible, never derived from registrant-supplied text) and an origin badge for agent-registered rows. A registration-time scheme allowlist (`http:`/`https:` only, single writer: `CreateBookmarkRequestSchema`) is the server-side gate; the host line is the click-time gate. Deliberately does **not** inherit the [Artifact](#artifact-html-artifact)'s sandbox/opaque-origin jail — a bookmark points at an external origin, outside the app's CSP entirely, so that boundary neither applies nor could apply. The server never fetches the target URL (no `<title>` resolution) to avoid an SSRF surface. Full threat model, premise-survival table, and the REST/MCP identity-anchor asymmetry (and why it is intentional, not drift) live in [`docs/design/session-bookmarks.md`](design/session-bookmarks.md) — this entry is a summary, not the canonical source. `create_bookmark` / `delete_bookmark` (MCP only, not the REST form) also emit a trigger-only `bookmark-created` / `bookmark-deleted` app-socket message after the repository write succeeds (Issue #1520), invalidating the session-scoped bookmarks panel query — there is no standalone bookmarks list route and no [Notification Center](#notification-center) composer for bookmarks, so the panel is this feature's only realtime-refresh surface, unlike [Artifact](#artifact-html-artifact)'s three.
- **See:** [Issue #1379](https://github.com/ms2sato/agent-console/issues/1379), [Issue #1390](https://github.com/ms2sato/agent-console/issues/1390), [`docs/design/session-bookmarks.md`](design/session-bookmarks.md)

### Memo
**Implemented (agent-writable since the feature's introduction; human-writable and always-visible added by Issue [#1569](https://github.com/ms2sato/agent-console/issues/1569)).** One Markdown file per [Session](#session), stored at `~/.agent-console/memos/{sessionId}.md` and capped at 256KB (`MemoService`, `packages/server/src/services/memo-service.ts`; the cap is enforced there, not duplicated in any request schema). Written by the agent via the `write_memo` MCP tool, or by a human via `PUT /api/sessions/:id/memo` (`UpdateSessionMemoRequestSchema`) — the human path is ownership-gated: the caller must be the session's owner, or the session must be a [SharedSession](#sharedsession). Read via `GET /api/sessions/:id/memo`, which returns `{ content: string | null }` (`null` means no memo exists). A `PUT` whose trimmed content is empty deletes the memo file rather than writing an empty one — an on-disk empty file would make reads return `''` forever, indistinguishable from "no memo" ever existing. Both write and delete broadcast `memo-updated { sessionId, content }` after the file operation succeeds; **`content: ''` means "deleted" on the wire — never `null`**, which is a REST-response-only value (`MemoUpdatedSchema`'s `content` is a plain non-nullable `string`). The memo editor is last-write-wins: it never merges a concurrent `memo-updated` broadcast into unsaved local edits, instead surfacing a "Load latest" affordance. **Known gap, out of scope for #1569 (tracked separately, Issues #1486 / #1555):** the `write_memo` MCP tool does not verify the calling agent's session ownership — any MCP caller with a valid session-scoped token can currently write any session's memo via that tool. The REST path added by #1569 does not have this gap.
- **See:** [Session Memo in session-worker-design.md](design/session-worker-design.md#session-memo), [Issue #1569](https://github.com/ms2sato/agent-console/issues/1569)

### StartupIntent / StartupIntentPreference
**Implemented (Issue [#1299](https://github.com/ms2sato/agent-console/issues/1299) PR-1).** The resolved decision, and the caller's unresolved preference, for how an [AgentWorker](#agentworker)'s PTY should start. Two separate three-member unions with overlapping literal names — do not conflate them by name alone. `StartupIntent` (the resolved value, produced only by `resolveStartupIntent` in `packages/server/src/services/startup-intent.ts`) is one of: `'continue'` (resume the existing conversation, selecting the agent's continue-mode command template), `'deliver-initial-prompt'` (start fresh and (re)inject the session's pending [Initial Prompt](#initial-prompt-session--initialprompt-initialpromptdelivered)), or `'fresh'` (start fresh, no prompt delivery). `StartupIntentPreference` (the caller's input) is `'continue' | 'fresh' | 'system'`: `'continue'`/`'fresh'` are a caller's explicit choice (e.g. the per-session restart dialog) and are honored/consulted the same way an intent of that name is; `'system'` means "the caller has no conversation preference of its own" (e.g. Restart All) and resolves to `'deliver-initial-prompt'` when a prompt is owed, `'continue'` otherwise. `resolveStartupIntent(preference, { deliverInitialPromptOnActivation, initialPrompt, initialPromptDelivered })` is the single writer of this decision — every PTY-activation call site resolves it once, before the worker is killed/recreated, and threads the resolved value to `WorkerManager.activateAgentWorkerPty`; no downstream site re-derives it from the eligibility/prompt/delivered fields itself. **Known gap, deliberately deferred (Issue [#1305](https://github.com/ms2sato/agent-console/issues/1305)):** a `'continue'` *intent* does not currently suppress prompt injection downstream — template selection and the initial-prompt-injection gate in `activateAgentWorkerPty` are independent conditions, so a custom agent whose continue-mode template contains `{{prompt}}` can still receive the initial prompt on a `'continue'` intent. Unreachable with the built-in agent; a design decision, not an oversight. The wire-level request body still carries a plain `continueConversation: boolean` (`CreateWorkerRequestSchema` / `RestartWorkerRequestSchema` in `packages/shared`) — translation into a `StartupIntentPreference` happens entirely server-side at the route boundary. `continueConversation` itself is not a domain concept and does not get its own entry.
- **See:** Issue [#1299](https://github.com/ms2sato/agent-console/issues/1299) (ruling R2, "a resolved startup intent, not a flag")

### Worktree
A Git worktree representing a physical working directory.
- **See:** [Core concepts in session-worker-design.md](design/session-worker-design.md#key-concepts)

### Session Data Address (dataScope / dataScopeSlug)
The filesystem location for a [Session](#session)'s data (worker outputs, memos, inter-session messages) — distinct from its [Worktree](#worktree)'s location. Resolved exclusively through `computeSessionDataBaseDir(configDir, scope, slug)`, which accepts two scopes: `'quick'` (fixed `_quick/` directory, no slug) and `'repository'` (`repositories/<slug>/`, slug required). The scope and slug (`dataScope` / `dataScopeSlug`) are captured once at session creation and stay frozen for the session's lifetime — they do not change on repository rename or on later changes to how the slug is derived. Two slug shapes coexist for `'repository'` scope: `org/repo` (git-remote derived) and a flat basename (for local-only repositories with no remote). Both shapes are produced by the single writer `deriveRepositorySlug` (`lib/git.ts`), consumed identically by worktree/template placement (`getRepositoryDir`) and by session creation's frozen slug (`RepositoryManager.getRepositorySlug`) — the two derivations converge going forward, closing the address split a repository with a remote used to produce. Sessions created before this convergence keep their frozen flat slug; the forward-only fix does not migrate or move existing session data, so a repository's legacy flat directory and its new `org/repo` directory can coexist until every session referencing the flat slug is deleted.
- **See:** [Session Data Path design](design/session-data-path.md)

### PTY-backed Worker
A capability grouping over the concrete worker types: a worker backed by a PTY process — currently the `agent` and `terminal` types — able to receive injected input and `[internal:*]` PTY notifications. The canonical single-writer predicate `isPtyBackedWorker` in [worker.ts](../packages/shared/src/types/worker.ts) codifies this capability. [GitDiffWorker](#gitdiffworker) is not PTY-backed; [EmbeddedAgentWorker](#embeddedagentworker) is not PTY-backed either (it streams NDJSON over stdout rather than terminal bytes — a v1 decision in the design doc). **Since Issue #1260 PR-2, `canReceiveSessionMessages` (the `send_session_message` / same-session-message capability predicate) has diverged from this grouping**: it now also admits `EmbeddedAgentWorker` (delivery routes through `EmbeddedAgentWorkerService.sendUserMessage` rather than a PTY write), so "can receive session messages" is no longer a strict subset/alias of "PTY-backed" — check `isPtyBackedWorker` when PTY delivery specifically is required, `canReceiveSessionMessages` when the send_session_message capability is what's being gated. **Since Issue #1574 PR A, a third predicate, `canReceiveNotifications`, governs `create_timer` / `create_conditional_wakeup` targets** (`agent` | `terminal` | `embedded-agent`) — broader than `isPtyBackedWorker` for the same reason `canReceiveSessionMessages` is: an embedded-agent target has no PTY, but the delivery seam (`SessionManager.deliverWorkerNotification`) routes to it through `EmbeddedAgentWorkerService.sendSystemNotification` instead. `isPtyBackedWorker` itself is unchanged and, after that PR, has exactly one remaining production consumer outside its own definition: the seam's internal PTY-vs-embedded branch (`run_process`'s guard is a pending follow-up migration onto `canReceiveNotifications`, not yet moved). Three predicates now exist, each answering a different question: "does this worker have a PTY" (`isPtyBackedWorker`), "can send_session_message target it" (`canReceiveSessionMessages`), "can create_timer/create_conditional_wakeup target it" (`canReceiveNotifications`).
- **Aliases:** PTY-backed worker
- **See:** [Capability predicates in worker.ts](../packages/shared/src/types/worker.ts); [MCP tool surface: capability predicates in embedded-agent-worker.md](design/embedded-agent-worker.md#mcp-tool-surface-capability-predicates-not-per-type-branches)

### EmbeddedAgentWorker
**Implemented for v1, including multi-user support** (Phases 1–4 landed: shared types, wire schema, persistence, registry + REST; the agent subprocess `packages/embedded-agent` and its server-side `EmbeddedAgentWorkerService`; WebSocket routing (`isStreamWorker`-gated `attachWorkerCallbacks`/`detachWorkerCallbacks`, the `embedded-agent` branch in `websocket/routes.ts`); the chat UI `EmbeddedAgentWorkerView` and the unified agent-selection picker; the multi-user elevation real-machine smoke (`scripts/smoke/check-embedded-agent-elevation.ts`), and terminal-agent MCP token-file delivery; the multi-user `enforce` default flip landed in Phase 4 but was reverted to `warn` for all modes in Sprint 2026-07-16 — see [MCP Caller Token](#mcp-caller-token) and Issue #1107). Phase 3.5 (EmbeddedAgentDefinition management UI, tracked separately as Issue #1029) is presentation-layer only and does not gate multi-user support** (worker type literal: `embedded-agent`). A worker type whose agent LLM loop is written and owned by Agent Console itself, instead of running a fixed external terminal program — "embedded" in the *embedded database* sense (SQLite vs a DB server): the app runs the capability within itself rather than delegating to an external program. The loop runs as a per-user subprocess (spawned via `spawnAsUser`), streams NDJSON-structured events (text / tool-call / tool-result / activity-state) over stdout rather than terminal bytes, and calls the built-in MCP server for app operations like today's terminal agents. Targets OpenAI-compatible API endpoints and local LLMs; complements (does not replace) the PTY-backed [AgentWorker](#agentworker). Configured by an [EmbeddedAgentDefinition](#embeddedagentdefinition), not an [AgentDefinition](#agentdefinition).
- **Aliases:** embedded agent worker, agent-owned-loop worker (former working name), loop-agent (former literal), in-process agent (historical framing, superseded — the chosen design is a subprocess, not in-process)
- **See:** [Embedded Agent Worker design](design/embedded-agent-worker.md)

### EmbeddedAgentDefinition
**Implemented** (type in [embedded-agent.ts](../packages/shared/src/types/embedded-agent.ts); registry `EmbeddedAgentManager` with REST CRUD under `/api/embedded-agents`; DB table `embedded_agents`). Also carries `isBuiltIn: boolean`, mirroring `AgentDefinition.isBuiltIn`.

- **See:** [Embedded agent registry in embedded-agent-worker.md](design/embedded-agent-worker.md#embedded-agent-registry-embeddedagentdefinition)

### Engine (embedded-agent) — openai-api / SDK
**Phase 1 implemented, including the SDK engine's actual runtime module** (spec: [embedded-agent-sdk-engine.md](design/embedded-agent-sdk-engine.md), Issue [#1324](https://github.com/ms2sato/agent-console/issues/1324), consulted with the Architect 2026-08-17). The in-subprocess machinery that turns user messages into NDJSON events — loop, tool execution, and provider communication as one unit. Two engines exist as siblings behind the SAME host↔subprocess stdio/NDJSON protocol (the seam is that protocol, not a new interface), both implementing a shared `Engine` contract (`packages/embedded-agent/src/engine-types.ts`: `runTurn` / `cancel` / optional `dispose`; the `handoff` member was removed by Issue #1401) that `main.ts`'s dispatch loop drives: the **openai-api engine** (`AgentLoop`, the existing `agent-loop.ts` + `providers/` + `tools/` + `mcp.ts` stack, untouched — satisfies `Engine` structurally with no changes) and the **SDK engine** (`SdkEngine`, `packages/embedded-agent/src/sdk-engine.ts`; hosts a real Claude Agent SDK session via a single `query()` call site plus a `spawnClaudeCodeProcess` override, the executing user's own claude authentication, no provider secret crossing the server). The engine is NOT user-facing configuration — it is a structural discriminant on [EmbeddedAgentDefinition](#embeddedagentdefinition) (`engine: 'openai-api' | 'claude-sdk'`, a discriminated union enforced by both the TypeScript type and `EmbeddedAgentDefinitionSchema`'s `v.variant`; field-presence inference is prohibited). Phase 1 registers exactly one `claude-sdk` definition — a built-in (`CLAUDE_SDK_AGENT_ID = 'claude-sdk-builtin'`, `packages/server/src/services/embedded-agents/claude-sdk-builtin.ts`), upserted by `EmbeddedAgentManager.initialize()` on every startup and never user-created or modifiable (mirrors `AgentManager`'s `claudeCodeAgent` built-in pattern); the REST create route always produces `engine: 'openai-api'`. The worker-side counterpart is `sdkSessionId` (`InternalEmbeddedAgentWorker.sdkSessionId`, persisted via `workers.sdk_session_id`, migration v30): the worker's CURRENT Claude Agent SDK session id, updated by a dedicated `sdk-session-id` `EmbeddedAgentEvent` — deliberately not a field on `ready`, because the session id was not stable across the (now-retired) handoff reseed, AND because `ready` is engine-authored at construction while `sdk-session-id` only arrives once the SDK's own `system:init` lands (a live probe found `system:init` is gated on the first prompt being yielded — a freshly-activated worker legitimately has no `sdkSessionId` yet; this is not a fault condition). The SDK engine's tool surface is allowlist-contained at runtime, not just by intent: on every `system:init`, the reported non-`mcp__` tool names are checked against the definition's `enabledTools`, and a leak (e.g. `WebFetch`) terminates the session with a `fatal` event rather than merely logging it. Key accepted trade (owner, 2026-08-17): an SDK-engine worker costs TUI-Claude memory (~450 MB), not custom-loop memory (~92 MB), in exchange for removing the subscription-vs-API-key configuration fork. **Naming (owner decision, Issue #1364):** `engine` values follow a `<vendor-or-dialect>-<access method>` convention (e.g. `openai-api`, `claude-sdk`) rather than a flat list — see [embedded-agent-sdk-engine.md §3.1](design/embedded-agent-sdk-engine.md#31-engine-selection-a-structural-discriminant-never-inference) for the full 2x2.
- **Aliases:** `native-loop` (former literal for this engine, renamed to `openai-api` in #1364 — the migration v29 DDL's historical default value; see `migration-v29.test.ts` and `migrateToV29` in `packages/server/src/database/connection.ts`, both frozen and left unrenamed)
- **See:** [embedded-agent-sdk-engine.md](design/embedded-agent-sdk-engine.md) §3 (seam), §4 (compatibility matrix), §5 (premises/hazards), Appendix A (event-mapping table, including the `ready`/`system:init` decoupling correction trail)

### Builtin Tool (embedded-agent)
**Implemented (FF-1a, Issue #1042; FF-1b, Issue #1043; FF-1c, Issue #1044; `TodoWrite`, Issue #1573)** (`Read`/`Glob`/`Grep` land in FF-1a; `Bash` in FF-1b; `Write`/`Edit` in FF-1c; `TodoWrite` in #1573). A tool executed *inside* the [EmbeddedAgentWorker](#embeddedagentworker)'s own subprocess (`packages/embedded-agent/src/tools/`), as opposed to an MCP tool proxied through the MCP server — matching how Claude Code / opencode implement their own file/shell tools rather than putting them on a tool-call RPC surface. Tool names and argument shapes match Claude Code's own tools. Which builtin tools a given [EmbeddedAgentDefinition](#embeddedagentdefinition) exposes to the provider is governed by its `enabledTools?: EmbeddedAgentToolName[]` field (`EmbeddedAgentToolName` derived from the single-writer constant `EMBEDDED_AGENT_TOOL_NAMES`): `undefined` = the loop's own default (`Read`, `Glob`, `Grep`, `TodoWrite` on, `Bash`/`Write`/`Edit` off), `[]` = all off, an explicit array = exactly that set (an excluded tool is not represented in the provider's tools list at all, not merely rejected if called). At `init` the loop merges its resolved builtin tools with the MCP-listed tools (`CompositeToolExecutor`); on a name collision the builtin wins. All builtin tools resolve their target path through path confinement (`resolveConfinedPath`) before touching the filesystem — a process-boundary floor (not OS-level sandboxing) that rejects any path resolving outside the session's `locationPath`, including via a symlink. `Bash` additionally spawns via `node:child_process` with `detached: true` so a timeout can kill the whole process group, and strips `AGENT_CONSOLE_*`-prefixed env vars before spawning (`env-cleaner.ts`'s `buildBashEnv`). `Write`/`Edit` share an `atomicWrite` helper (`packages/embedded-agent/src/tools/atomic-write.ts`) that writes to a same-directory temp file then renames it onto the target, so a crash mid-write never leaves a partial file; `Edit` matches `old_string` byte-exactly (no regex, no whitespace/CRLF normalization) and rejects zero-match, ambiguous multi-match (without `replace_all`), and no-op (`old_string === new_string`) calls. `TodoWrite` is the odd one out structurally: it touches no filesystem, so path confinement does not apply to it, and it is the only builtin tool constructed fresh per incarnation (private closure state, via a `createTodoWriteTool()` factory) rather than shared as a stateless module-level singleton — see [Built-in tools (fast-follow)](design/embedded-agent-worker.md#built-in-tools-fast-follow) for the full spec, including `TodoWrite`'s own subsection and the client-side [derived `TodoPanel`](design/embedded-agent-worker.md#ui).
- **See:** [Built-in tools (fast-follow) in embedded-agent-worker.md](design/embedded-agent-worker.md#built-in-tools-fast-follow)

### attachmentRoots
**Implemented (Issue #1570).** An optional `string[]` field on the `init` command's `context` object (`EmbeddedAgentInitCommandBase.context.attachmentRoots`, `packages/shared/src/types/embedded-agent.ts`; `v.optional(v.array(v.string()))` in the `strictObject` schema, `packages/shared/src/schemas/embedded-agent.ts`), naming additional confinement roots — beyond `cwd` — that the subprocess's builtin `Read` tool (only `Read`; see [Builtin Tool (embedded-agent)](#builtin-tool-embedded-agent)) may open via `resolveConfinedPath`'s `extraRoots` parameter (`packages/embedded-agent/src/tools/path-confinement.ts`). Today the only populated value is `[resolveUploadDir()]` (`packages/server/src/lib/message-upload-dir.ts`), the directory `POST /api/sessions/:sessionId/messages` saves uploaded message attachments to — keyed by the server process's uid: one directory per server, group-readable across all users in multi-user mode, unguessable per-upload names, the same boundary the PTY branch already delivers paths into — composed into `restoreContext` at activation time in `EmbeddedAgentWorkerService`. Consumed only by the `openai-api` engine's builtin `Read` tool: `claude-sdk`'s own native `Read` tool ignores this field entirely, since a live probe (real `@anthropic-ai/claude-agent-sdk` `query()` under the production `permissionMode`) confirmed it can already open files outside `cwd` without any confinement extension. `write.ts` / `edit.ts` / `glob.ts` / `grep.ts` deliberately never forward `attachmentRoots` to `resolveConfinedPath`, so a message attachment stays readable-only, never writable/editable/searchable, through the builtin tool surface.
- **Contrast:** `locationPath` (the PRIMARY confinement root, always `cwd`; `attachmentRoots` only ever widens where a resolved ABSOLUTE path is allowed to land, never the base used to resolve a relative one)
- **See:** [Path confinement (the FF-1a "minimum floor") § Extra confinement roots for Read only in embedded-agent-worker.md](design/embedded-agent-worker.md#path-confinement-the-ff-1a-minimum-floor), [UI § File attachments in embedded-agent-worker.md](design/embedded-agent-worker.md#ui)

### Reasoning/Thinking Content (embedded-agent)
**Implemented, backend and client (Issue #1070).** LLM reasoning/thinking output some OpenAI-Chat-Completions-compatible providers stream separately from the final answer text (DeepSeek-R1 API, many vLLM reasoning-parser configs, OpenRouter passthrough, some Ollama models), via a `choice.delta.reasoning_content` string field alongside (not instead of) `content`. `OpenAIChatAdapter` yields it as a `{ type: 'reasoning-delta' }` `ProviderEvent`; the [EmbeddedAgentWorker](#embeddedagentworker) loop maps it 1:1 onto the wire-level `assistant-thinking-delta` `EmbeddedAgentEvent`, interleaved with `assistant-delta`. It is never accumulated into the final `assistant-message` text and has no terminal/final event of its own — the iteration's unconditional `assistant-message` emit is the implicit boundary a client uses to know a thinking segment has ended (the client also defensively closes an open thinking entry on `turn-error`/`fatal`/`exited`, for the case where no `assistant-message` ever arrives for that turn). Client-side, `embedded-agent-store.ts` folds the delta stream into a dedicated `assistant-thinking` chat-entry kind (accumulate-then-finalize, same replace-not-mutate discipline as `assistant-message`), and `EmbeddedAgentWorkerView.tsx` renders it as a collapsed-by-default `<details>`/`<summary>` accordion (plain text, not Markdown), visually muted relative to the main assistant bubble.
- **See:** [The loop's turn cycle in embedded-agent-worker.md](design/embedded-agent-worker.md#the-loops-turn-cycle); [Provider adapter & tool-call normalization in embedded-agent-worker.md](design/embedded-agent-worker.md#provider-adapter--tool-call-normalization)

### Initial Prompt (Session) — `initialPrompt`, `initialPromptDelivered`
**Implemented (Issue #1068; eligibility marker persisted per Issue #1074; obligation-scoped auto-activation on revival per Issue #1264).** A user-supplied first message attached to a `Session` at creation time, delivered as the session's initial [EmbeddedAgentWorker](#embeddedagentworker)'s first user message rather than left for the user to retype after the worker connects. `EmbeddedAgentWorkerService.maybeDeliverInitialPrompt` runs when that worker first reports `ready`, and flips `Session.initialPromptDelivered` `undefined → true` via a durable write to the `sessions.initial_prompt_delivered` column (nullable `INTEGER` 0/1, migration v24). Delivery is single-shot per session: the persisted flag gates re-delivery, so a server restart followed by re-activation does not re-send it. A send failure leaves the flag `undefined` so a later activation can retry. Eligibility is scoped to the session's initial embedded-agent worker only — a worker added later via the generic add-worker route does not receive it — via the `InternalEmbeddedAgentWorker.deliverInitialPromptOnActivation` marker, durably persisted to the `workers.deliver_initial_prompt_on_activation` column (nullable `INTEGER` 0/1, migration v26) so the eligibility survives a server restart that happens before the worker's first activation. The three-part eligibility check is the single exported predicate `hasUndeliveredInitialPrompt(worker, session)`, called both by `maybeDeliverInitialPrompt` and by `SessionPauseResumeService.resumeSessionInternal`'s revival hook, which auto-activates exactly the embedded-agent workers this predicate matches when a session is revived (startup auto-resume or manual pause→resume) — the only class of revived worker nothing else would ever trigger.
- **See:** [Initial prompt delivery in embedded-agent-worker.md](design/embedded-agent-worker.md#initial-prompt-delivery-issue-1068), [Server-side management § obligation-scoped auto-activation on revival](design/embedded-agent-worker.md#server-side-management-embeddedagentworkerservice)

### clientMessageId
**Implemented (Issue #1117).** An optional, client-generated correlation id attached to an [EmbeddedAgentWorker](#embeddedagentworker) `embedded-user-message` send (`WorkerClientMessage`, `packages/shared/src/types/session.ts`) and echoed back verbatim on the corresponding persisted `user-message` `EmbeddedAgentServerEvent` (`packages/shared/src/types/embedded-agent.ts` and its `EmbeddedAgentServerEventSchema`). Exists to let a client's `sendUserMessage` pending-promise resolve only on ITS OWN echo, not on any `user-message` event — without it, the same worker open in two tabs/clients could have one tab's pending send falsely resolved by the other tab's accepted send. Generated via `crypto.randomUUID()` in `embedded-agent-store.ts`; capped at 64 characters and type-checked server-side (`packages/server/src/websocket/routes.ts`, `EMBEDDED_CLIENT_MESSAGE_ID_MAX_LENGTH`) before being persisted. Deliberately decoupled from the server-assigned `user-message.id` (which feeds the client's chat-entry key, `user-${id}`) so a client-supplied value can never collide with or pollute that key. The loop's stdin protocol (`EmbeddedAgentCommand`) is unaffected — correlation is strictly client↔server.
- **Aliases:** correlation id (informal)
- **Contrast:** `user-message.id` (server-assigned, feeds the chat-entry React key; never client-supplied)
- **See:** [Embedded Agent Worker design](design/embedded-agent-worker.md) "WebSocket & client protocol"

### notification (`EmbeddedAgentServerNotification`)
**Implemented (Issue #1351).** An optional structured marker (`{ kind: PtyNotificationKind; summary?: string }`) on a persisted `user-message` `EmbeddedAgentServerEvent` (`packages/shared/src/types/embedded-agent.ts`, validated by `EmbeddedAgentServerEventSchema`), distinguishing a system-originated internal notification from a real human/API-caller message on the same `user-message` wire shape rather than as a separate event type — a new event type would have required re-teaching `restore.ts`'s replay classification, while an added field is restore-transparent by construction (a `notification`-carrying row still replays as an ordinary `role: 'user'` turn). `notification` present ⟺ system-originated is the single discriminator; there is no separate `origin` field that could disagree with it. Composed and persisted only by `SessionManager.sendEmbeddedAgentSystemNotification` / `EmbeddedAgentWorkerService.sendSystemNotification`, which take the structured `PtyNotificationParams` type (`kind` + `fields`, from `packages/server/src/lib/pty-notification.ts`) rather than a pre-composed string, so a future PTY notification kind delivered to an embedded-agent worker is born-included at this entry point rather than requiring each caller to remember to mark it. `kind` is validated against the shared `PtyNotificationKind` enum (`packages/shared/src/types/system-events.ts`, duplicated from the server-internal `WritePtyNotificationParams` union for the same layering reason as `EmbeddedAgentRestoredToolCall`); `summary` is present only for kinds whose `fields` shape carries one (`internal-message`, `inbound-event`). Client-side, `EmbeddedAgentWorkerView` renders a `notification`-carrying row as a muted, collapsed-by-default, full-width row instead of the user-bubble treatment; pre-existing transcripts persisted before this field existed have no `notification` key and keep rendering as plain user bubbles (an explicit accepted cut — no client-side heuristic reclassification of old rows by pattern-matching their text).
- **Aliases:** `PtyNotificationKind`, `PTY_NOTIFICATION_KINDS`, `PtyNotificationParams`
- **Contrast:** the [Initial Prompt](#initial-prompt-session--initialprompt-initialpromptdelivered) delivery is explicitly NOT a notification (it is the conversation's substance, user-authored by proxy) and carries no `notification` field. Also contrast the [Notification Center](#notification-center) — that surface is the **human**-addressed awareness feed (bell + list); this field marks the **agent**-addressed delivery lane's own transcript rows, a different audience deliberately excluded from the Notification Center's admission rule.
- **See:** [PTY-backed Worker](#pty-backed-worker) for the `[internal:*]`/`buildPtyNotificationText` template this field's `kind`/`summary` are derived from; `docs/design/embedded-agent-worker.md` "WebSocket & client protocol"

### AGENTS.md / Instruction Loader / Instruction layers
**Implemented** (Issue #1072; extended to a fourth, rules, layer and to both engines by Issue #1343 Phase A). The [EmbeddedAgentWorker](#embeddedagentworker) loop's instruction-file discovery, run once per activation and injected into the system prompt between the context preamble and `EmbeddedAgentDefinition.systemPrompt`. **Since Phase A, both engines call the SAME loader** — `claude-sdk` no longer has a narrower opt-in-only path; its `settingSources: []` pin (disabling the SDK's own NATIVE settings-derived discovery) is unaffected, and this loader delivers equivalent content from outside that mechanism. Discovery spans FOUR layers, concatenated in order: **global** (`~/.config/agent-console/AGENTS.md`, honoring `XDG_CONFIG_HOME`), **chain** (every directory from the git root down to `cwd`, root-to-cwd order — reduces to `[cwd]` outside a git repository; root detection accepts `.git` as either a directory or a worktree gitfile), **`instructions[]`** (`EmbeddedAgentDefinition.instructions?: string[]`, an opt-in explicit file list, opencode-shaped; deduped by resolved path against the global/chain layers), and **rules** (every `<gitRoot>/.claude/rules/*.md`, sorted by name; a rule's `paths:`/`globs:` frontmatter — either spelling, string or the multi-line YAML list this repo's own rules use — determines its scope: unscoped rules are included eagerly under a `--- Rule: <origin> ---` delimiter, scoped rules are only named + globbed in a one-line index so the model knows they exist; lazily activating a scoped rule on a matching tool call is Phase B, tracked as a checklist in Issue #1343, not yet implemented). Within the global and chain layers, each directory applies AGENTS.md-canonical / CLAUDE.md-fallback: `AGENTS.md` wins when both are present (debug-logged, not warn — a normal state); neither present is silently skipped (the routine case for most directories). Each `instructions[]` entry is resolved relative to the session's `locationPath` through `resolveConfinedPath` — the same confinement helper builtin tools use — so a definition authored by a different party than the executing user cannot read outside the session's working tree; escape attempts are skipped and warn-logged, never fatal. **Two independent budgets:** the instructions layers (global/chain/`instructions[]`) keep their pre-existing per-file 16 KiB cap and 48 KiB aggregate cap (excluding `systemPrompt`), with whole-segment overflow-dropping from the general side first (global, then chain root-to-leaf, then `instructions[]` last-entry-backward); the rules layer has its own separate `RULES_LAYER_CAP_BYTES` (default 160 KiB, env-overridable), never truncating a rule mid-file — overflow drops whole unscoped rule files largest-first and appends a declared "rules omitted for size: <names>" line, so the loss is visible in-band rather than silent. Instructions and rules are read once at activation and cached for the worker's lifetime; a restart re-reads.
- **See:** [Instruction loader in embedded-agent-worker.md](design/embedded-agent-worker.md#instruction-loader); [Post-v1 fast-follows](design/embedded-agent-worker.md#post-v1-fast-follows); Issue [#1343](https://github.com/ms2sato/agent-console/issues/1343)

### MCP Caller Token
**Implemented** (Issue #878 phase 1, completed through Phase 4; transport-wide authentication added by Issue #1269). A per-worker bearer token verified by the `/mcp` endpoint. Two separate claims apply to two separate scopes — do not conflate them: **(1) authentication, all 22 tools:** the Issue #1269 transport-level gate (below) verifies, for every `/mcp` request, that a presented token resolves to a real minted identity; it does not itself compare that identity against any claimed session. **(2) authorization / identity-binding, 5 tools only:** `checkCallerOwnsSession` binds a claimed `sessionId` to the verified caller's `userId` — implemented only at the elevation-bearing tools (`delegate_to_worktree`, `remove_worktree`, `run_process`, `create_conditional_wakeup`) plus `send_session_message`; a presented-but-mismatched token is always rejected **at those 5 tools**, not as a blanket property of every MCP tool call. Phase 1 implements the in-memory registry, `/mcp` bearer verification, and the `checkCallerOwnsSession` ownership-enforcement wiring at those 5 tools. Phase 2 added minting and delivery for embedded-agent workers: `EmbeddedAgentWorkerService` mints a token at activation (failing activation when the session has no `createdBy` — a mint from an ownerless session would produce an identity that `checkCallerOwnsSession` always rejects), delivers it inside the stdin `init` message, and revokes it on subprocess exit. Phase 4 added minting and delivery for terminal-agent workers: in multi-user mode, the server mints a token, writes it to a user-owned `0600` file at `<homeDir>/.agent-console/mcp-tokens/<workerId>.token`, and passes only the file path via the `AGENT_CONSOLE_MCP_TOKEN_FILE` env var — never the raw token via argv, env-under-elevation, or PTY injection, all of which leak into world-readable or persisted-and-broadcast channels; the file is deleted on the same worker exit/kill/delete events that revoke the in-memory token. At those 5 tools, tokenless calls are logged-and-allowed under `warn` and rejected under `enforce`; before Issue #1269 this mode dependency was the ONLY auth mechanism reachable by any MCP tool, and only for those 5. Phase 4 made `enforce` the multi-user default, but Sprint 2026-07-16 reverted the default to `warn` for every `AUTH_MODE` (including multi-user): the deployment is a team-of-trust and the ops cost of `enforce` (existing-session token re-delivery, Claude Code `headersHelper` per-OS-user wiring, full dogfood) outweighed the safety benefit at the time. `warn` still logs tokenless callers for observability. An operator can still opt into `enforce` explicitly via `AGENT_CONSOLE_MCP_AUTH=enforce`; restoring `enforce` as the multi-user default is tracked in Issue [#1107](https://github.com/ms2sato/agent-console/issues/1107). **Issue #1269:** the other 17 registered MCP tools (several mutating) had no auth mechanism reachable from any request, regardless of mode, because `checkCallerOwnsSession` only ever ran inside the 5 tools above. Fixed by the transport-level authN gate (`createMcpAuthMiddleware` / `evaluateMcpAuthGate`) mounted via `mcpApp.use('/mcp', ...)` in front of every `/mcp` request, answering "is this caller anyone at all?" for all 22 tools structurally (one mount point, not per-tool wiring); `checkCallerOwnsSession` is retained unchanged as the separate, narrower authorization question ("does this caller own the claimed session?") at the 5 tools that ask it.
- **Key code:** `McpCallerIdentity` / `McpTokenRegistry` / `checkCallerOwnsSession` / `createMcpAuthMiddleware` / `evaluateMcpAuthGate` in [mcp-auth.ts](../packages/server/src/mcp/mcp-auth.ts), mounted via `mcpApp.use('/mcp', ...)` in [mcp-server.ts](../packages/server/src/mcp/mcp-server.ts); `writeUserOwnedSecretFile` in [privilege-elevation.ts](../packages/server/src/services/privilege-elevation.ts); mode env var `AGENT_CONSOLE_MCP_AUTH` (values `off | warn | enforce`; default `warn` for every `AUTH_MODE` since Sprint 2026-07-16, see Issue #1107; explicit `enforce` paired with a non-multi-user `AUTH_MODE` is a startup configuration error, see Issue #1269).
- **See:** [MCP caller identity in embedded-agent-worker.md](design/embedded-agent-worker.md#mcp-caller-identity-issue-878-phase-1); [Transport-level authN gate](design/embedded-agent-worker.md#transport-level-authn-gate-issue-1269); Issue [#878](https://github.com/ms2sato/agent-console/issues/878); Issue [#1269](https://github.com/ms2sato/agent-console/issues/1269)

### Compaction
**Implemented (Issue [#1401](https://github.com/ms2sato/agent-console/issues/1401), owner decision 2026-08-28).** Shortening an [EmbeddedAgentWorker](#embeddedagentworker)'s conversation in place when it approaches the model's context window. The normative user-facing contract, identical on both engines: *the conversation stays the same conversation and simply becomes shorter, and one line marking the compaction boundary appears in the transcript; automatic compaction is a worker-level toggle, manual compaction is a request made to the agent (a [Compact Tool](#compact-tool) call).* Two engine-specific mechanisms sit behind it and are never named to the user: on the **openai-api** engine the loop distills the conversation and splices the summary over its head (`AgentLoop.compact()`, `packages/embedded-agent/src/agent-loop.ts`) — auto fires at turn end when `contextUsage.promptTokens / contextWindowTokens >= threshold` (`EmbeddedAgentDefinition.compaction.threshold`, default `0.85`, leaving window room for the distillation call itself; it can never fire when `contextWindowTokens` is unset, because there is no denominator); on the **claude-sdk** engine the SDK's own auto-compaction does it, with the worker toggle composed into the SDK's settings. Both emit the same `context-compacted` [EmbeddedAgentEvent](#context-usage) (`{ source: 'auto' | 'manual'; summary?: string; preTokens?: number; postTokens?: number; coverage?: 'full' | 'partial' }`) as the persisted boundary marker — see [Compaction Coverage](#compaction-coverage) for the last field. The toggle is a property of the **worker**, not the definition (`EmbeddedAgentWorker.autoCompaction`, `workers.auto_compaction`, migration v35, **default ON** including for pre-existing rows), because the decision belongs to the conversation in front of the user rather than to the agent's configuration. **Failure invariant (the property under test/audit):** every openai-api failure path (prompt-load failure, provider failure, cancel, unusable summary) returns before the `context-compacted` marker is emitted, so the conversation is never mutated on failure. Supersedes [Context Handoff](#context-handoff-retired), which is retired. **Second firing point (Issue [#1411](https://github.com/ms2sato/agent-console/issues/1411)):** the same automatic predicate is also evaluated once **at the restore boundary** — right after `init` and before the first user turn — for a worker seeded from a [Transcript Restore](#transcript-restore), because a restored conversation that is already large sends its first provider call before any turn ends and so the turn-end trigger never gets a chance. Same event, same `source: 'auto'`, same failure invariant; only the trigger point is new, and `ready` is withheld until that compaction FINISHES (never until it succeeds — a dead provider at activation must not wedge the worker). Above a `FULL_DISTILL_MAX_RATIO` (0.9) ceiling it degrades to [Partial Distillation](#partial-distillation).
- **Aliases:** compaction (informal); NOT an alias of "handoff" — handoff terminated the session and seeded a successor, compaction does not
- **Contrast:** [Transcript Restore](#transcript-restore) (acts on an IDLE/dead conversation to recover it after a restart; compaction acts on a LIVE one to keep it inside the window)
- **Key code:** `AgentLoop.compact()` (`packages/embedded-agent/src/agent-loop.ts`); `SdkEngine`'s `compact_boundary` mapping (`packages/embedded-agent/src/sdk-engine.ts`); `buildCompactionSeedMessages` (`packages/embedded-agent/src/conversation-seed.ts`)
- **See:** [Compaction in embedded-agent-worker.md](design/embedded-agent-worker.md#compaction); Issue [#1401](https://github.com/ms2sato/agent-console/issues/1401)

### Compact Tool
**Implemented (Issue [#1401](https://github.com/ms2sato/agent-console/issues/1401)).** The builtin tool an [EmbeddedAgentWorker](#embeddedagentworker)'s model calls to request a manual [Compaction](#compaction). No parameters. Registered on both engines and **always enabled, structurally outside `enabledTools`' reach**: it is deliberately not a member of `EMBEDDED_AGENT_TOOL_NAMES` nor of `BUILTIN_TOOLS`, so no representable configuration removes it and it never appears among the definition form's tool checkboxes. The model-visible name differs per engine (`Compact` on openai-api, where `AgentLoop` prepends the definition and intercepts the call by name; `mcp__console__Compact` on claude-sdk, where an in-process SDK MCP server serves it) but the contract — no parameters, reservation semantics, result wording — is identical. Because a tool call happens inside a turn and compaction must never run mid-turn, the call sets a **reservation** drained at the turn boundary: idempotent within a turn, runs even in a small context (no threshold gate) and even after an error-terminated turn, discarded on cancel or shutdown. It is the first member of the **self-management tool class** — owned by the loop/engine, zero outward capability (no file, process, or network reach), which is why `enabledTools`' opt-in rationale does not apply to it; a future tool-permission floor ([#1045](https://github.com/ms2sato/agent-console/issues/1045)) must not govern this class with the same mechanism it governs capability tools.
- **Contrast:** [Builtin Tool (embedded-agent)](#builtin-tool-embedded-agent) (the capability class — `Read`/`Glob`/`Grep`/`Bash`/`Write`/`Edit`, each individually grantable through `enabledTools` precisely because each can reach outside the worker)
- **See:** [Compaction in embedded-agent-worker.md](design/embedded-agent-worker.md#the-compact-tool)

### EMBEDDED_AGENT_SLASH_COMMANDS
**Implemented (Issue [#1572](https://github.com/ms2sato/agent-console/issues/1572)).** The per-[Engine (embedded-agent)](#engine-embedded-agent--openai-api--sdk) slash-command table in [embedded-agent-slash-commands.ts](../packages/shared/src/types/embedded-agent-slash-commands.ts) — SINGLE WRITER of which slash commands the composer offers for completion, per engine, and of how each one is handled. A row is `{ name: string; description: string; handledBy: 'engine' | 'console' }`. `handledBy: 'engine'` means the command is forwarded as an ordinary `user-message` and the subprocess itself interprets it (`claude-sdk`'s own built-in `/compact`, `/cost`, `/context` — the Claude Agent SDK parses these out of the streamed prompt). `handledBy: 'console'` means the SERVER intercepts the command before it reaches the engine as prose and maps it to an existing console operation instead — `openai-api`'s `/compact`, which that engine has no slash-command parser of its own to honour, intercepted by `EmbeddedAgentWorkerService.sendUserMessage` (via `resolveConsoleSlashCommand` / `resolveConsoleSlashCommandOverride`) and dispatched as the wire command `{v:1, type:'compact'}` to `Engine.compactNow()` (only `AgentLoop` implements it). The persisted transcript event is unaffected by interception — it always shows exactly what the user typed. A command is offered by completion **only when the engine actually honours it**: `/clear` and `/model <name>` are deliberately excluded even though the SDK's own `system:init.slash_commands` advertises both — `/clear` resets the SDK's own conversation state with nothing on the console side to match (mapped instead to a `turn-error` via `sdk-engine.ts`'s `conversation_reset` case, declaring the divergence rather than offering the command); `/model` doesn't persist past the current session, conflicting with [agent-surface.md](design/agent-surface.md) Ruling 3's worker-persisted-override contract. Every `console`-handled entry across the whole table must have a matching handler in `CONSOLE_SLASH_COMMAND_HANDLERS` (`embedded-agent-worker-service.ts`) — mechanically pinned by that file's own test suite.
- **Contrast:** [Compact Tool](#compact-tool) (a model-invoked tool call the AGENT decides to make mid-conversation; a slash command is a USER-typed composer shortcut — the two converge on the same underlying manual-compaction mechanism but are triggered from opposite ends)

### Context Usage
**Implemented (Issue #1122; re-pointed by Issue #1401; denominator resolution widened by Issue #1554).** The token-accounting wire event and denominator that back [Compaction](#compaction)'s always-visible usage bar and its auto-fire threshold. `EmbeddedAgentDefinition.contextWindowTokens?: number` is the operator-declared model context window and the ratio's **fallback** denominator, not unconditionally "the" denominator: the actual denominator is the EFFECTIVE window resolved by `resolveEffectiveContextWindow(definition, worker)` (`packages/server/src/services/embedded-agent-context-window.ts`, [agent-surface.md](design/agent-surface.md) Ruling 4 "do not inherit"). When the worker carries no per-worker `model` override, this definition-level value applies unchanged (the pre-#1554 behavior). When a per-worker `model` override IS active, the definition's value is never used regardless of whether the worker also overrides the window — the denominator becomes the worker's own [`workers.context_window_tokens`](#workerscontext_window_tokens) if set, or UNDECLARED if not (undefined = raw-token display only, no ratio/color/threshold banners). The loop emits a `context-usage` `EmbeddedAgentEvent` (`{ v: 1; type: 'context-usage'; promptTokens: number; estimated: boolean }`) once per turn conclusion (last-provider-request-wins across a multi-tool-iteration turn — never per iteration, and not emitted at all when a turn's very first provider attempt fails), sourced from the OpenAI-compatible `usage.prompt_tokens` field (`stream_options: { include_usage: true }`) when the provider supplies it (`estimated: false`), falling back to a chars/4 estimate over the conversation when it does not (`estimated: true`). `EmbeddedAgentDefinition.compaction?: { threshold?: number }` (default `0.85` when unset) is the single ratio the openai-api engine's auto compaction fires at and the usage bar's colour bands escalate against. It replaced the retired `handoff?: { softRatio, hardRatio, auto }` pair, whose two-stage escalation existed only to drive threshold banners that #1401 deleted along with the manual-handoff CTA they pointed at. **A reading outlives its incarnation:** the newest one in the persisted log is carried across a restart as the [Restored Usage Seed](#restored-usage-seed--initrestoredusage) and decides the restore-boundary compaction check, which is also why `estimated` is part of the event rather than derived at the display layer.
- **Key code:** usage accounting in `AgentLoop`/`OpenAIChatAdapter` (`packages/embedded-agent/src/agent-loop.ts`, `providers/openai-chat-adapter.ts`); threshold-crossing predicate `crossedThreshold` (`packages/client/src/components/workers/context-usage-threshold.ts`); bar rendering `ContextUsageBar.tsx`.

### Partial Distillation
**Implemented (Issue [#1411](https://github.com/ms2sato/agent-console/issues/1411)).** The narrowed-input shape of [Compaction](#compaction) on the `openai-api` engine. It has **two callers**, which reach it for opposite reasons. At the **restore boundary** it is the edge-case fallback, taken only when that check's input `S` — the larger of the persisted [Restored Usage Seed](#restored-usage-seed--initrestoredusage) and the chars/4 estimate of the reconstructed text — already exceeds `FULL_DISTILL_MAX_RATIO` (0.9) of `contextWindowTokens`, the point past which the distillation request itself would overflow. (The **trigger** is `S`; the **budget** below is still measured with the estimator, which is why the two read differently.) From the **[Mid-turn Overflow Escape](#mid-turn-overflow-escape)** it is not a fallback at all but the definition: that caller has *observed* the overflow the ceiling merely predicts, so it takes this shape at any ratio. **The two callers also build their input differently, and must**: the restore-boundary caller selects, the escape shrinks — see that entry for why the tail is the right thing to keep in one case and the wrong thing in the other. At the restore boundary, only the **largest tail suffix** that fits `PARTIAL_DISTILL_INPUT_RATIO` (0.7) of the window becomes the distillation's input, measured over the assembled request (the conversation's system message, always kept, plus the suffix, plus the compaction prompt) with the same chars/4 estimator the loop uses everywhere. A suffix may never begin at a `{role:'tool'}` message — that would hand the provider a tool result whose owning assistant `tool_calls` entry is absent, the mirror image of what [Mid-turn Repair](#mid-turn-repair) prevents. The two ratios are deliberately **two constants and not one**: the live turn-end path sends the whole conversation successfully at and above the 0.85 threshold, so a single cut at 0.7 would make the same mechanism treat the same conversation differently depending only on where it was triggered. Neither ratio is operator-configurable — both are internal safety margins on our own coarse estimator. The resulting summary carries a fixed caveat line (`PARTIAL_DISTILL_CAVEAT_LINE`) **inside the `summary` string itself** rather than in the seed sentence around it, so that it survives into the persisted `context-compacted` event and is therefore still read by the model after a later [Transcript Restore](#transcript-restore) reseeds through the unchanged single-writer `buildCompactionSeedMessages`. When not even one message fits the budget, nothing is distilled: the conversation is preserved untouched and a `turn-error` names that specific cause. **What happens next depends on the provider, and only one of the two shapes is now handled.** A strict provider rejects the over-window request, and that rejection is no longer accepted behaviour: the [Mid-turn Overflow Escape](#mid-turn-overflow-escape) classifies it and forces one partial distillation with a single retry, inside the turn. A lenient provider returns no error at all — measured 2026-08-29, one model capped its reported `prompt_tokens` exactly at its window and answered anyway, silently dropping content — and an error-path mechanism is structurally blind to that. **Silent truncation therefore remains exactly where it was**, and the escape must not be read as covering it.
- **Contrast:** [Compaction](#compaction) (the ordinary shape — the WHOLE conversation is the distillation input; partial distillation narrows only the input, never the mechanism, the marker, or the `source`)
- **Coverage declared, not merely caveated (Issues [#1424](https://github.com/ms2sato/agent-console/issues/1424), [#1423](https://github.com/ms2sato/agent-console/issues/1423), PR [#1548](https://github.com/ms2sato/agent-console/pull/1548)):** the discriminating field this entry used to call for has shipped, as [Compaction Coverage](#compaction-coverage) — `coverage?: 'full' | 'partial'` on the persisted marker, read by `restore.ts`'s `boundaryCoverage`. A restore across a partial boundary no longer reseeds with the full-coverage wording at all: `buildCompactionSeedMessages` states plainly that only the most recent portion is covered, and the transcript's boundary label does the same. The embedded caveat line (`PARTIAL_DISTILL_CAVEAT_LINE`, described above) still exists and still travels inside `summary` for defense in depth, but the seed's OUTER sentence is no longer the mildly-contradicting one this bullet used to describe. **Residual, not closed by this fix:** on `claude-sdk`, `coverage` is inferred from the SDK's own `compact_metadata` shape (see [Compaction Coverage](#compaction-coverage)); a future SDK version that keeps the same field names but silently changes what their presence means would not be caught by any type-level check, only by the re-verification discipline named in `sdk-engine.ts`'s doc comment.
- **Key code:** `selectPartialDistillationMessages`, `FULL_DISTILL_MAX_RATIO`, `PARTIAL_DISTILL_INPUT_RATIO`, `PARTIAL_DISTILL_CAVEAT_LINE`, `AgentLoop.compactAtRestoreBoundaryIfNeeded()` (`packages/embedded-agent/src/agent-loop.ts`)
- **See:** [Compaction at the restore boundary in embedded-agent-worker.md](design/embedded-agent-worker.md#compaction-at-the-restore-boundary)

### Compaction Coverage
**Implemented (Issues [#1424](https://github.com/ms2sato/agent-console/issues/1424), [#1423](https://github.com/ms2sato/agent-console/issues/1423), PR [#1548](https://github.com/ms2sato/agent-console/pull/1548)).** The `context-compacted` [EmbeddedAgentEvent](#context-usage)'s `coverage?: 'full' | 'partial'` field, declaring whether a [Compaction](#compaction)'s distillation input was the whole conversation (`'full'`) or only a recent tail suffix ([Partial Distillation](#partial-distillation), `'partial'`). **Three-valued by absence, not by a third literal**: a row persisted before this field existed carries no `coverage` at all, which means UNKNOWN — never `'full'`. Both consumers (`buildCompactionSeedMessages`, which builds the post-compaction seed message, and the transcript's boundary label) branch explicitly on all three states, so an absent value can never fall through to the totality claim `'full'` carries; this is what corrects the pre-existing overclaim on every legacy row, not only on newly-compacted ones. `preTokens`'s own meaning is unaffected but easy to misread once `coverage` exists: it is always the distillation call's own input size, so for a `'partial'` compaction it is the narrowed suffix's size, not the whole pre-compaction conversation's — under-reporting exactly when the compaction discarded the most. No whole-conversation-size estimate is added alongside it; the honesty comes from declaring `coverage`, not from a second, less-precise number (mixing a measurement and a guess in one field is exactly what [Context Usage](#context-usage)'s `estimated` boolean exists to keep separate). Both engines know coverage unambiguously on `openai-api` (the loop already tracks whether its own distillation input was narrowed); on `claude-sdk` it is inferred from the SDK's own `compact_metadata.preserved_messages` / `preserved_segment` presence, per that SDK version's documented absence-semantics — a third-party premise, re-verified on every SDK version bump, because an unannounced SDK shape or semantics change could misreport a partial compaction as full, reintroducing the exact overclaim this field exists to remove.
- **Contrast:** [Context Usage](#context-usage)'s `estimated` boolean (also a flag about the honesty of a number, but two-valued; `coverage` is three-valued specifically so UNKNOWN stays distinct from FULL, since collapsing them would silently restore the totality overclaim on legacy rows)
- **Key code:** `coverage` field on `context-compacted` (`packages/shared/src/types/embedded-agent.ts`, `packages/shared/src/schemas/embedded-agent.ts`); `boundaryCoverage` (`packages/embedded-agent/src/restore.ts`); `compactionSeedLeadIn` (`packages/embedded-agent/src/conversation-seed.ts`); coverage inference in `SdkEngine.flushCompactionBoundary` (`packages/embedded-agent/src/sdk-engine.ts`); `formatCompactionBoundaryLabel` (`packages/client/src/components/workers/EmbeddedAgentWorkerView.tsx`)
- **See:** [Partial Distillation](#partial-distillation)'s "Coverage declared, not merely caveated" note; Issues [#1424](https://github.com/ms2sato/agent-console/issues/1424), [#1423](https://github.com/ms2sato/agent-console/issues/1423)

### Mid-turn Overflow Escape
**Implemented (Issue [#1433](https://github.com/ms2sato/agent-console/issues/1433)).** The `openai-api` loop's response to an **observed** over-window provider error: one forced [Partial Distillation](#partial-distillation) and exactly one retry, performed **inside the live turn** rather than at a turn boundary. It is the backstop for every case [Compaction](#compaction)'s predictive checks are structurally blind to — a worker that never published a reading, over-declaration of `contextWindowTokens`, a seed-only worker whose system prompt alone is large.

**Partial is its definition, not its fallback.** The `FULL_DISTILL_MAX_RATIO` ceiling exists to *predict* that a whole-conversation distillation would itself overflow; this path is triggered by the *observation* of exactly that overflow, so attempting whole would reproduce the error it is responding to.

**Its input is built by shrinking, not by selecting.** [Partial Distillation](#partial-distillation)'s tail-suffix rule is right at a restore boundary, where the tail is recent conversation; mid-turn the tail is the bloat, so selecting it would keep the tool dumps and discard the user's question. The escape caps tool-result contents largest-first and drops no message, which also preserves `tool_call`/`tool` pairing by construction — see the restore-boundary invariant below.

**Classification is an allowlist of measured provider signatures, and it fails toward doing nothing.** A false negative is safe (the turn ends as it does today); a false positive would turn a genuine provider outage into a compaction. Structure narrows the family and a per-entry message discriminator narrows within it, because a provider's code can be coarser than the condition — `invalid_parameter_error` covers every invalid parameter. An error carrying no provider envelope at all (an edge proxy's rejection) matches nothing, with no exclusion rule needed for it.

**Every `context-compacted` marker must be a valid restore boundary.** The escape writes one mid-turn, and [Transcript Restore](#transcript-restore) cuts its replay window at exactly that marker, so a window opening on an orphaned `tool-result` would route to the destructive reset. Today's placement satisfies this structurally: the escape fires at the top of an iteration, where every issued `tool_call` already has its result.

- **Bounded:** one escape per turn, reset when the turn ends; a second overflow ends the turn. Inert when `contextWindowTokens` is unset.
- **Blind to silent truncation** — see [Partial Distillation](#partial-distillation).
- **See:** [Mid-turn overflow escape in embedded-agent-worker.md](design/embedded-agent-worker.md#mid-turn-overflow-escape)

### Restored Usage Seed — `init.restoredUsage`
**Implemented (Issue [#1419](https://github.com/ms2sato/agent-console/issues/1419)).** The newest **authoritative context reading** extracted from an [EmbeddedAgentWorker](#embeddedagentworker)'s persisted NDJSON log during [Transcript Restore](#transcript-restore) reconstruction, and carried to the subprocess on the `init` command as `restoredUsage: { promptTokens, estimated }` (`EmbeddedAgentRestoredUsage`, `packages/shared/src/types/embedded-agent.ts`). It is what [Compaction](#compaction)'s restore-boundary check is decided by, replacing a re-estimate of the reconstructed text with a **measurement**. The reason it exists: `estimateTokensFromChars` sums each message's `.content` only, while the request a provider actually prices also carries every published tool schema — every [Builtin Tool (embedded-agent)](#builtin-tool-embedded-agent), every MCP tool, plus the [Compact Tool](#compact-tool) — so the estimate is systematically low by roughly a fixed per-worker constant. Measured on a real instance: **1102 estimated against 6722 reported** for the same request, and **5450 against 10512** on a second, larger one. Against a realistic window that constant is a rounding error; against a small declared `contextWindowTokens` it is the dominant term, and a conversation that would overflow can sit below the threshold and compact nothing.

**Two event kinds are readings, and the newer wins:** a `context-usage` ([Context Usage](#context-usage)), and a `context-compacted`'s `postTokens` — itself a reading, being the size that compaction left behind. Extraction takes the last `context-usage` **strictly after** the last compaction boundary; failing that, the boundary's own `postTokens`; failing that, nothing. **A reading from before the last boundary is never eligible** — it measures a conversation that boundary then discarded, so it overstates what remains by however much the compaction removed. The rule is not a separate policy kept in step with reconstruction: `findRestoredUsageSeed` is handed the same boundary index step 4b already computed, so it *is* the restore window.

**The check's input is the larger of the seed and the estimate**, because both are lower bounds on the priced request and each misses what the other catches: the reading measures a real request including tool schemas but only as the conversation stood when it was published, while the estimate covers every message present now but omits the schemas entirely. Taking the maximum is the tightest bound available without attributing individual restored messages to positions in the log — a message-index correspondence on the wire, to recover a term the reading already contains.

**`estimated` travels with the number rather than being recomputed, and that is a guard rather than bookkeeping.** A previous incarnation whose provider never sent `usage` fell back to the chars/4 estimator; its reading is still the newest one, but it carries the same bias this entry exists to remove. Recomputing the flag — or defaulting it either way — would let that estimate arrive at the next incarnation dressed as a measurement, so the usage bar would show `estimated: false` for a number no provider ever reported, and a future reader auditing the gap would find the two indistinguishable. A boundary's `postTokens` is likewise always the loop's own estimate of the seed it built, so it reports itself as one even when it is the newest reading available.
- **Aliases:** usage seed; seed (only within the restore-boundary context — unrelated to `buildCompactionSeedMessages`' conversation *seed*, which is the post-compaction first message)
- **Scope:** the **`openai-api`** arm only. `claude-sdk` carries its own context state through the SDK resume ([Transcript Restore](#transcript-restore), "Two mechanisms, one promise") and computes no ratio of its own, so an `init` for that engine carrying a seed is not representable — the same structural containment `resume` gets from the other direction.
- **Residual (stated, not closed):** a worker killed **before completing any turn** published no reading, so the field is absent and the estimator fallback stands with its bias intact. That population can still wedge; it is simply now the only one exposed. Closing it needs an error-path escape (forced [Partial Distillation](#partial-distillation) on a detected over-window response) rather than a better number up front — Issue [#1433](https://github.com/ms2sato/agent-console/issues/1433).
- **Key code:** `findRestoredUsageSeed`, `RestoreOutcome.usageSeed` (`packages/embedded-agent/src/restore.ts`); `AgentLoop.resolveRestoreBoundaryUsage()` (`packages/embedded-agent/src/agent-loop.ts`); the `init` composition in `EmbeddedAgentWorkerService.activate` (`packages/server/src/services/embedded-agent-worker-service.ts`)
- **See:** [Compaction at the restore boundary in embedded-agent-worker.md](design/embedded-agent-worker.md#compaction-at-the-restore-boundary) — the `S` definition and the "Seed extraction" subsection

### Transcript Restore
**Design-first (Issue #1123): Stage a (spec) and Stage b (implementation) have both landed.** Reconstitution of an [EmbeddedAgentWorker](#embeddedagentworker)'s LLM-facing conversation array from its persisted NDJSON output log at activation, replacing v1's unconditional reset (fresh epoch + empty conversation). Un-defers the "restart-resume" deferral recorded in the design doc's Design Decisions (owner directive, 2026-07-15) — closing the UX gap against the terminal worker's `-c` continuation — as a formal policy change, not a re-litigation of the original deferral's reasoning. Reconstruction stops at the most recent [Compaction](#compaction) boundary event — `context-compacted`, or a legacy `context-handoff` from before Issue #1401 (the deliberate discard of prior context is respected, not resurrected) and applies [Mid-turn Repair](#mid-turn-repair) to heal a conversation whose tail ends mid-tool-call (Tier C, adopted in the same scope as Tier B's context-usage threshold detection). **Restore failure, on the primary path (Issue #1447 stage 4), is preserve-and-declare: the log is kept in place, a `restore-failure-boundary` marker (a reconstruction boundary the next restore stops at, symmetric with `context-compacted`) is appended, and the transcript stays fully readable (C1) — the destructive reset-and-sidecar behavior of stage b/#1449 is now the FALLBACK, reached only when that in-band write itself fails, and a fallback for a `claude-sdk` worker whose SDK session survives also leaves a persistent `restore-failure-declaration` row (restore-transparent, the opposite of the boundary marker) so the divergence outlives the incarnation (Issue #1492).** `restore-info`'s failure form carries this state as `preservation: 'in-band' | 'sidecar' | 'lost'` alongside `{ failed: true; sdkResumed?: boolean }`, and the client derives which of three directions the divergence takes — **D1** (display ahead of memory, the pre-existing case below), **D2** (memory ahead of display — a `claude-sdk` failure whose SDK session may still resume), or **Loss** (both gone — an `openai-api` failure, or a `claude-sdk` failure whose resume also failed) — from the engine and `sdkResumed`; see [embedded-agent-worker.md § Failure invariant (restore)](design/embedded-agent-worker.md#failure-invariant-restore) and [§ Failure form: what it declares, and the D1/D2/Loss derivation rule](design/embedded-agent-worker.md#failure-form-what-it-declares-and-the-d1d2loss-derivation-rule-1449) for the full definitions (single writer, not restated here). The client learns about a successful restore via a new `restore-info` `WorkerServerMessage` variant carrying `restoredMessageCount` — **an entry counts if and only if its content originates from a line of the persisted transcript**: replayed messages and the compaction summary do; the synthetic system prompt and Tier C repair markers, both invented by the reconstruction so the provider accepts the array, do not (Issue [#1428](https://github.com/ms2sato/agent-console/issues/1428) renamed it from `messageCount` and corrected it: it had counted the reconstruction's own seed, so it never reached zero and a worker that had said nothing was told its conversation might not have carried over) — and a server-authoritative `completed` flag (dual-delivered: a fast-path push right after reconstitution with `completed: false`, plus authoritative bootstrap re-delivery to every new connection for the incarnation's lifetime, plus a third repush with `completed: true` once the server observes the new incarnation's `ready` event — corrected in Issue #1205 after the original client-derived-from-epoch/`ready`-order signal proved structurally unable to distinguish same-epoch incarnations) -- see [Transcript Restore in embedded-agent-worker.md](design/embedded-agent-worker.md#transcript-restore) § UI.
**Two mechanisms, one promise (R1, Issue #1410).** The contract the restore/eviction track states is that **a conversation survives a process boundary**, on either engine and whichever kind of boundary it was. How that is achieved is engine-specific and always has been: the `openai-api` engine reconstructs the conversation array described above and hands it back to the provider; the `claude-sdk` engine passes the worker's persisted `sdkSessionId` ([Engine (embedded-agent)](#engine-embedded-agent--openai-api--sdk)) as `Options.resume` so the SDK restores its own session state. It is still **sent** a `restoredConversation` — that field rides in the shared half of the `init` command rather than an engine-specific arm — and **deliberately ignores it**; the distinction matters because the server reconstructs, and reports `restoredMessageCount` for, both engines alike, and only the consumption differs. The transcript the user *reads* is a replay of the persisted NDJSON stream on both engines — one writer — and what R1 added on the SDK side is that the model's live memory now agrees with that display. A resume that does not take on a SUCCESSFUL restore is reported as `restore-info.sdkResumed: false` (set only by `claude-sdk`; the other engine omits the field, and absence must never be read as `false`), and that is the only case this SUCCESS-restore divergence (D1) notice still appears. **This is no longer the only notice a restore can produce (Issue #1449):** a restore FAILURE — a distinct, non-null `restore-info` form — is now also declared to the client, and renders as D2 or Loss depending on engine and `sdkResumed`; see this entry's paragraph above for the failure form and the D1/D2/Loss vocabulary. See [embedded-agent-worker.md § Transcript Restore](design/embedded-agent-worker.md#transcript-restore) "The track's contract".
- **Contrast:** [Compaction](#compaction) (acts on a LIVE conversation to avoid running out of context mid-lifetime; Transcript Restore acts on an IDLE/dead conversation to recover it after a restart). **Engine-scoped since SDK Engine Phase 1, and no longer a divergence since R1:** the `restoredConversation` reconstruction mechanism still runs only for the `openai-api` engine — a `claude-sdk`-engine worker's `restoredConversation` is deliberately ignored — but that is now a difference of *mechanism* rather than of outcome. It was recorded as an accepted-divergence (owner, Q2) only for as long as PS4 (`resume` fidelity) was unprobed; Issue #1400 verified PS4, which removed that premise, and R1 closed the divergence. SDK Engine Phase 3 (#1335)'s client-side notice survives with **inverted polarity**: shown only when `sdkResumed === false`, never on a successful resume — see [embedded-agent-sdk-engine.md §4.3](design/embedded-agent-sdk-engine.md#43-ui-the-restore-divergence-notice-sdk-engine-phase-3-polarity-inverted-by-r1).
- **See:** [Transcript Restore in embedded-agent-worker.md](design/embedded-agent-worker.md#transcript-restore); Issue [#1123](https://github.com/ms2sato/agent-console/issues/1123)

### Mid-turn Repair
**Generalizes the v1 "Mid-turn abort repair" mechanism** ([The loop's turn cycle](design/embedded-agent-worker.md#the-loops-turn-cycle)) across two call sites as of Issue #1123's [Transcript Restore](#transcript-restore) design: the original runtime site (a live turn aborted by `cancel` or the re-ask cap, operating on the in-memory `conversation` mid-`runTurn`) and the new restore-time site (a persisted log replayed at activation, operating on the reconstructed array before the loop resumes). Both sites push a synthetic `{role:'tool'}` message for every `tool_call_id` left unresponded by its enclosing assistant `tool_calls` entry — the requirement an OpenAI-Chat-Completions-compatible provider imposes before it accepts the next request; without it the provider rejects with 400 and the worker is permanently wedged. The two sites differ in trigger, detection surface (live in-memory array vs. log-derived event pairing), and the synthetic message's `Error: ${reason}` text (`Error: tool call canceled` / `Error: tool call not completed: turn ended after repeated malformed arguments` for the runtime site vs. `Error: tool call not completed: worker restarted before this response was recorded` for the restore site) — both routed through the shared `pushSyntheticToolError` insertion primitive (`packages/embedded-agent/src/tool-call-repair.ts`), which the runtime site's `fillPendingToolResponses` and the restore site's `repairDanglingToolCalls` each call once per unresponded call; the mechanism itself — synthetic tool-role message inserted before anything else touches the conversation — is identical. The client-facing UI transparency note shown on the restore site is separate, human-facing copy, not this internal string.
- **Aliases:** Mid-turn abort repair (the original, runtime-only name, still used for that specific call site)
- **See:** [The loop's turn cycle in embedded-agent-worker.md](design/embedded-agent-worker.md#the-loops-turn-cycle); [Transcript Restore in embedded-agent-worker.md](design/embedded-agent-worker.md#transcript-restore)

### SDK Resume Failed — `sdk-resume-failed`
**Engine-authored `EmbeddedAgentEvent` (R1, Issue [#1410](https://github.com/ms2sato/agent-console/issues/1410)).** Reports that a `claude-sdk` worker's SDK session could not be resumed. Carries the id that failed and a `reason`, whose three values are enumerated once in `SDK_RESUME_FAILURE_REASONS` (`packages/shared/src/types/embedded-agent.ts`) and read from there by the valibot picklist and by every branch that acts on them:

- `not-found` — the activation-time `getSessionInfo` pre-flight ran and the SDK reported that it could not find the session. **Not proof of absence**: on SDK `0.3.238` the store swallows read errors, so an EACCES or a malformed transcript arrives here too (measured — see PS7's table in [`embedded-agent-sdk-engine.md`](design/embedded-agent-sdk-engine.md)). No resume was attempted and no turn was lost.
- `lookup-failed` ([#1426](https://github.com/ms2sato/agent-console/issues/1426)) — the pre-flight could not run at all. Not a verdict about the session. **Currently unreachable on SDK `0.3.238`**, which reports every store-level fault as `undefined`; kept as the correct shape for a version that propagates the error, and documented as unreachable rather than deleted.
- `refused` — a resume WAS attempted and the SDK rejected it, which costs the turn in flight and leaves the SDK query dead inside a live harness.

All three report `restore-info.sdkResumed: false` — this incarnation runs on a fresh SDK session on every route, so the divergence notice is honest each time. They differ in what happens to the persisted id. **Only `refused` clears it**: the id was offered and rejected, and re-offering it repeats the damage. `not-found` and `lookup-failed` **keep** it, so the next activation pre-flights it again — both are decided before a resume is sent, so a retry costs one filesystem read and risks no turn. What clears a kept id is the fresh session **superseding** it at its first `sdk-session-id`; the accepted residual is that a user who speaks before the worker recovers loses the old session that way. Only `refused` additionally replaces the incarnation, through a teardown the exit observer covers.

**The invariant is `a refused id is never retried`**, narrowed from "there is never a second resume attempt, on any path" ([#1426](https://github.com/ms2sato/agent-console/issues/1426)). The wider form was never justified in that width — its argument is a property of refusal alone — and applied to `not-found` it discarded a resumable session permanently whenever the session store was momentarily unreadable, since every store-level fault arrives as `not-found`.

**The machine-readable half of a failure whose human-readable half is a separate event.** The `turn-error` emitted alongside it is what the user reads; this event is what the server branches on. Deliberately two events rather than one doing both jobs: the server must never have to string-match an error message to decide what happened. Detection is structural, not textual — see [`embedded-agent-sdk-engine.md` §5](design/embedded-agent-sdk-engine.md) premise PS6, since the SDK's result subtype for a refused resume is the same one an ordinary cancel produces.
- **Contrast:** [Turn Interrupted](#turn-interrupted--turn-interrupted) is the mirror image — *server*-authored and user-visible, a marker row in the transcript. This one is *engine*-authored and has no UI surface at all; its only user-visible form is `restore-info.sdkResumed: false` driving the divergence notice.
- **See:** [`embedded-agent-sdk-engine.md` §4.3](design/embedded-agent-sdk-engine.md#43-ui-the-restore-divergence-notice-sdk-engine-phase-3-polarity-inverted-by-r1) and Appendix A's `init` row; [Transcript Restore](#transcript-restore)

### Turn Interrupted — `turn-interrupted`
**Server-authored `EmbeddedAgentServerEvent` (R1, Issue [#1410](https://github.com/ms2sato/agent-console/issues/1410)).** Appended into an [EmbeddedAgentWorker](#embeddedagentworker)'s persisted NDJSON stream at activation, when replay shows a turn that never reached a terminal event: a `user-message` with neither a `state: 'idle'` nor a `turn-error` after it. Rendered on replay as a marker row, so a conversation cut off mid-turn says so rather than ending in silence. Engine-independent — the detection reads the persisted stream, not the engine.

**Server-authored deliberately, and never a synthesized `turn-error`.** The server does not forge engine-authored events; a fabricated `turn-error` would be a claim about what the model did, whereas `turn-interrupted` states only what the server itself observed about its own transcript. Contrast [Mid-turn Repair](#mid-turn-repair), which is also activation-time and also heals an unfinished tail, but acts on the LLM-facing conversation array and is deliberately never persisted as a wire event; `turn-interrupted` is the opposite on both axes — persisted, and purely a user-facing signal that changes nothing the model sees.

**`exited` is deliberately not a terminal event** for this rule: the server appends it on every exit it observes, so counting it would leave the detector firing only when the server itself died — never for a worker death it did observe, which is the common case and the one a deliberate eviction ([#1412](https://github.com/ms2sato/agent-console/issues/1412)) creates by design.
- **Scope:** R1 ships detection plus this local signal. Routing it to a delegating parent still waiting on a callback remains in Issue [#1273](https://github.com/ms2sato/agent-console/issues/1273); re-delivering the interrupted instruction is out of scope (owner decision, #1264's ruling). This event is the hook a future delivery mechanism would read.
- **See:** [embedded-agent-sdk-engine.md Appendix A.3](design/embedded-agent-sdk-engine.md#a3-server-side-events-engine-agnostic); [embedded-agent-worker.md § Transcript Restore](design/embedded-agent-worker.md#transcript-restore)

### Idle Eviction
**Implemented (R3, Issue [#1412](https://github.com/ms2sato/agent-console/issues/1412); the phase [#1336](https://github.com/ms2sato/agent-console/issues/1336) reserved. Extended to `openai-api` by Issue [#1502](https://github.com/ms2sato/agent-console/issues/1502)).** Dropping an idle [EmbeddedAgentWorker](#embeddedagentworker)'s subprocess on purpose to reclaim memory, while the worker stays **logically alive** — still in the session's worker map, still listed in the UI — so the next input transparently wakes it through the ordinary activation path. Eligibility is a property, not an enumerated engine list: any engine whose restore path has shipped and is exercised by a registered smoke. `claude-sdk` and `openai-api` both qualify today; the threshold is `EMBEDDED_AGENT_IDLE_EVICTION_MS` (default 30 minutes, non-positive disables). The lever is worth pulling for `claude-sdk` because the `claude` child is ~74% of a worker tree's measured footprint; `openai-api` has no such child, so eviction reclaims essentially the whole tree instead.

**Eviction is a policy, not a restore path.** Bringing the worker back is [Transcript Restore](#transcript-restore)'s mechanism, unchanged — which is what lets an evicted-then-resumed `claude-sdk` session inherit its compacted context rather than replaying pre-compaction history (Issue #1400's P5(c)).

**Two constraints that are requirements rather than tuning.** First, eviction terminates the subprocess **through the existing deactivation path, whose exit the server's exit observer covers**; a kill the observer does not see reproduces [#1414](https://github.com/ms2sato/agent-console/issues/1414)'s permanently-bricked worker by design, on a timer. Second, every path that delivers input passes a **single choke point** that wakes the worker or fails loudly — the wake condition is "there is no live subprocess", deliberately not "the worker is marked evicted", so that a silent drop is unrepresentable rather than merely covered by an enumerated list of triggers.
- **Contrast:** [Compaction](#compaction) shrinks what the model can recall and is lossy by design; eviction discards a *process* and is lossless. The two compose — a worker evicted after compacting resumes into the post-compaction state.
- **See:** [Idle eviction in embedded-agent-worker.md](design/embedded-agent-worker.md#idle-eviction-r3-issue-1412); [ExitReason](#exitreason)

### ExitReason
How a worker's subprocess exit is classified, on the worker WebSocket `exit` envelope, on the global worker-exit callback, and — since [Idle Eviction](#idle-eviction) — stamped on the persisted `exited` NDJSON row of an [EmbeddedAgentWorker](#embeddedagentworker). Three values: `managed` (someone asked for the shutdown), `unexpected` (the process died on its own), and `evicted` (the server dropped an idle worker's subprocess on purpose; the worker stays logically alive and the next message wakes it).

`evicted` is a strict subset of what was previously reported as `managed`, because eviction routes through the same deactivation path — so it is checked *first* when classifying, and any consumer that branched on `managed` had to be re-examined when it was introduced. Two consumers act on it today: the worker-exit notification is suppressed for `evicted` (otherwise an idle worker would notify the owner once per threshold period, forever), and the transcript renders an evicted exit as a quiet line instead of *"Agent process exited"* with a Restart button the user does not need.

**On the persisted event the field is three-valued and must be read as such.** Absent means the row was written before the field existed, and absent renders exactly as it always did; consumers test `reason === 'evicted'` and **never** `!reason` or truthiness — the same discipline `restore-info.sdkResumed` carries, where a negation would have shown a divergence notice on every `openai-api` worker. It is also the *single* identifier for "this exit was an eviction": there is deliberately no parallel boolean.

**Since [#1454](https://github.com/ms2sato/agent-console/issues/1454), an `'unexpected'` row may additionally carry a bounded `stderrTail`** (the process's last `STDERR_TAIL_CAP` characters of stderr — UTF-16 code units, not bytes and not an overall wire-size bound); `'managed'` and `'evicted'` rows never carry one — a routine deactivate or eviction has nothing diagnostic to attach.
- **See:** [Idle eviction in embedded-agent-worker.md](design/embedded-agent-worker.md#idle-eviction-r3-issue-1412)

### Login-Shell Sentinel
The spawn → gate → inject protocol used to launch an [AgentWorker](#agentworker) PTY through the user's login shell. Instead of running the agent command directly (which skips `.bashrc` / `.profile` and yields an incomplete PATH), the PTY spawns a login shell whose inner command echoes a per-activation random marker (`__AGENT_CONSOLE_READY_<id>`) and then execs an interactive shell. The worker-manager's onData handler **gates** on the marker: all output before it (login-shell init noise) is dropped and never reaches the output buffer, the persisted output file, clients, or the ActivityDetector; detection is chunk-boundary-safe via a bounded carry of the pre-sentinel tail. On detection, the pending agent command is **injected** with `pty.write(command + '\r')`, avoiding shell-quoting double-escapes.

Both spawn routes honor the same protocol: the direct path (`spawnDirectPty`, single-user mode and the multi-user elevation-skip case) wraps the marker in `$SHELL -l -c`, and the elevated path (`MultiUserMode.spawnSudoPty`) emits it from the inner command of the elevation argv (the elevated login shell provides the login init). A route that spawned without emitting the marker would leave the gate closed forever and silently drop all agent worker output.

- **Key code:** `AgentPtySpawnRequest.sentinel` ([user-mode.ts](../packages/server/src/services/user-mode.ts)); `InternalAgentWorker.loginShellSentinel` / `pendingCommand` ([worker-types.ts](../packages/server/src/services/worker-types.ts)); gate + inject in `WorkerManager.setupWorkerEventHandlers` ([worker-manager.ts](../packages/server/src/services/worker-manager.ts))
- **Aliases:** sentinel protocol, login-shell sentinel protocol, readiness sentinel
- **See:** Issue [#999](https://github.com/ms2sato/agent-console/issues/999) (structural enforcement follow-up: sentinel protocol single-writer + spawn-contract conformance suite)

### Base Spec
The persisted comparison base of a [GitDiffWorker](#gitdiffworker), stored in `workers.base_commit`. Unlike a frozen commit hash, a base spec records the user's *intent* and is **re-resolved on every diff computation**, so the diff stays aligned with GitHub's merge-base (three-dot) view as the branch absorbs upstream commits. Forms:
- `merge-base:<ref>` — fork point via `git merge-base <ref> HEAD` (e.g. `merge-base:origin/main`); re-resolves each diff.
- A branch name — re-resolves to the branch tip each diff.
- An explicit commit hash — stays pinned (no re-resolution).
- `reserved:default-fork-point` — sentinel for migrated workers; resolves the repository's default fork point fresh (prefers `origin/<default>`, falls back to local `<default>`, then the first commit). The `reserved:` namespace is illegal in git ref names, so it can never collide with a real branch/tag.

New git-diff workers default to `merge-base:origin/<default>` when the remote default exists, otherwise `merge-base:<default>`.
- **Aliases:** base commit spec
- **See:** [MERGE_BASE_REF_PREFIX / DEFAULT_FORK_POINT_SPEC in git-diff.ts](../packages/shared/src/types/git-diff.ts)

### Delegation Parent — `parentSessionId`, `parentWorkerId`
The ownership-inheritance chain for a session created via `delegate_to_worktree`: `parentSessionId` and `parentWorkerId` identify the calling session and worker, and are required as of Issue [#1293](https://github.com/ms2sato/agent-console/issues/1293) (previously optional, documented only as a reporting convenience so the delegated agent could call back via `send_session_message`). The parent session's [created_by](#created_by) is inherited as the delegated session's own `created_by` — this is what makes the pair identity-determining rather than a courtesy: a `parentSessionId` that does not resolve to any session, or one that resolves but has no `created_by` (an ownerless/legacy parent), is a hard error at delegation time, because neither can produce a working `created_by` → [requestUsername](#requestusername) chain for the child. `parentWorkerId` is separately resolved against the PARENT session's own workers (never a global lookup) and must name one capable of receiving `send_session_message`.
- **Contrast:** the verified MCP caller identity ([MCP Caller Token](#mcp-caller-token)'s `userId`) is never the source of `created_by` — it authorizes (`checkCallerOwnsSession`: may this caller act on the claimed session?), the parent session determines ownership. These are deliberately separate questions.
- **See:** [created_by](#created_by), [requestUsername](#requestusername), [MCP Caller Token](#mcp-caller-token); Issue [#1293](https://github.com/ms2sato/agent-console/issues/1293)

### clonedSourceRepoPath

### requestUsername
The OS username passed as the elevation context for `runAsUser` / `spawnAsUser`-routed operations in multi-user mode. Resolved at the request boundary from either `authUser.username` (for REST routes the user invokes directly, e.g. `DELETE /api/repositories/:id/worktrees/*`) or `session.createdBy → userRepository.findById → osUsername` (for MCP tools acting on behalf of a session, e.g. `delegate_to_worktree`, `remove_worktree`, `run_process`, `create_conditional_wakeup`). When `null` / `undefined` / matches the server process user, elevation is bypassed and operations run as the server user. Threaded through call chains so every step that touches user-owned files (worktree create / remove, rollback paths, hook commands, git operations) executes as the requesting user.

The session-side resolution is encapsulated by one of two sibling helpers in `packages/server/src/services/resolve-spawn-username.ts` with distinct downstream contracts:
- **`resolveSpawnUsername(createdBy, userRepository): Promise<string>`** — always returns a usable username (falls back to the [Service User](#service-user) on miss). For PTY-spawn callers that always pass *something* to `Bun.spawn` / `runAsUser` (e.g. worker lifecycle, session pause/resume).
- **`resolveRequestUsername(createdBy, userRepository, context): Promise<string | null>`** — returns `null` on miss so the explicit "no elevation" signal propagates downstream; `runAsUser` / `spawnAsUser` short-circuit elevation on null/undefined username (`shouldElevateForUser`). For MCP / route callers (`delegate_to_worktree`, `run_process`, `create_conditional_wakeup`). The `context` parameter (`{ toolName: string } & Record<string, unknown>`) shapes the structured warn payload emitted when `createdBy` is set but does not resolve.

- **Aliases:** requestUser (lib/git.ts trailing parameter name), elevation context, request username
- **Contrast:** [Service User](#service-user) (the OS account the server process runs as — what elevation is FROM, not TO).
- **See:** Issue [#837](https://github.com/ms2sato/agent-console/issues/837) (privilege-elevation umbrella), [`packages/server/src/services/privilege-elevation.ts`](../packages/server/src/services/privilege-elevation.ts) — exposes `runAsUser` / `spawnAsUser` / `rmRecursiveAsUser` (the canonical elevated-recursive-removal helper) / `writeUserOwnedSecretFile` (elevated user-owned secret-file write, forced 0600 regardless of ambient umask; used for the terminal-agent MCP token file, Phase 4). The strict-thin-wrapper family also includes domain-level runners that compose `runAsUser` plus caller semantics: [`packages/server/src/services/github-cli.ts`](../packages/server/src/services/github-cli.ts)'s `runGh` (gh-CLI-specific; throws on non-zero exit / timeout — lives in `services/` rather than `privilege-elevation.ts` per [Elevation Helpers rule](../.claude/rules/elevation-helpers.md) because it adds semantic layering). Identity-resolution helpers live alongside in [`packages/server/src/services/resolve-spawn-username.ts`](../packages/server/src/services/resolve-spawn-username.ts) (`resolveSpawnUsername` / `resolveRequestUsername` — see the bullet pair above). Issues [#879](https://github.com/ms2sato/agent-console/issues/879) and [#886](https://github.com/ms2sato/agent-console/issues/886). PRs #843 / #856 / #877 / #880 / #881 / #888 / #889 / #892 for individual consumer migrations and resolver / runner extractions

## Client Capabilities

### VSCodeOpenMode
Union type controlling how the client opens paths in VS Code from the "Open in VS Code" UI. Determined server-side and delivered to the client via `/api/config.capabilities.vscodeOpenMode`.

- `local-spawn` — the server spawns `code <path>` on its own host via `Bun.spawn`. Suitable for single-machine setups (server and browser run on the same OS). Default when `AUTH_MODE=none`.
- `remote-url-scheme` — the client navigates to `vscode://vscode-remote/ssh-remote+<host><path>`, letting the browser's local VS Code + Remote-SSH extension open the file over SSH. Suitable for remote-access setups (server on a remote host, browser on the user's local machine). Default when `AUTH_MODE=multi-user`.

**Server env overrides:**
- `VSCODE_OPEN_MODE` — explicit `local-spawn` / `remote-url-scheme`; wins over the `AUTH_MODE`-derived default. Invalid values throw at server startup.
- `VSCODE_REMOTE_HOST` — string surfaced on `/api/config.capabilities.vscodeRemoteHost` (null when unset). When null, the client falls back to `window.location.hostname` for host derivation.

**Related capability fields:**
- `capabilities.vscode: boolean` — the button-visibility gate. Unconditionally `true` in `remote-url-scheme` mode (the client's local VS Code handles the URL scheme, so the server's `code` binary presence is irrelevant); in `local-spawn` mode reflects the `which code` / `which code-insiders` detection.
- `capabilities.vscodeRemoteHost: string | null` — the host embedded in the SSH-remote URL when the client dispatches the URL scheme.

**Guardrails:** `POST /api/system/open-in-vscode` rejects (400) in `remote-url-scheme` mode so stale clients cannot silently spawn on the wrong host.

- **Aliases:** vscodeOpenMode (`ConfigResponse` field name), Open-in-VSCode mode
- **See:** Issue [#987](https://github.com/ms2sato/agent-console/issues/987) (introduces the URL-scheme dispatch); [`packages/shared/src/types/auth.ts`](../packages/shared/src/types/auth.ts) (`VSCodeOpenMode`, `ConfigResponse.capabilities`); [`packages/server/src/services/system-capabilities-service.ts`](../packages/server/src/services/system-capabilities-service.ts) (`resolveVSCodeOpenMode`); [`packages/client/src/lib/vscode-url.ts`](../packages/client/src/lib/vscode-url.ts) (`buildVSCodeRemoteUrl`).

### serverPort
The backend HTTP port the server is bound to, exposed to the client so it can compose absolute URLs pointing at the same server without hard-coding a port. Positive integer.

- **Source of truth:** `serverConfig.PORT` (env-configured; string in env, coerced to `Number(...)` at the response boundary; default `3457`).
- **Wire:** `/api/config.serverPort` (`packages/server/src/routes/api.ts`), typed on `ConfigResponse.serverPort` in [`packages/shared/src/types/auth.ts`](../packages/shared/src/types/auth.ts).
- **Consumer:** the client caches the value in [`packages/client/src/lib/server-info.ts`](../packages/client/src/lib/server-info.ts) (module-level `setServerPort` / `getServerPort` set once at app init, mirroring the `homeDir` pattern). Used by [`buildMcpInstallCommand`](../packages/client/src/lib/mcp-install-url.ts) to decide whether the current browser origin is same-origin with the backend (production single-port serving / reverse proxy on default 80/443) or split-port (dev with Vite on 5173 proxying `/api` to backend on `serverPort`); the split case composes `${protocol}//${hostname}:${serverPort}/mcp` so the copied install command targets the backend directly.
- **Related:** [`buildMcpInstallCommand`](../packages/client/src/lib/mcp-install-url.ts), the "Install MCP server in Claude Code" Settings section ([`McpInstallSection`](../packages/client/src/components/settings/McpInstallSection.tsx)).
- **See:** Issue [#991](https://github.com/ms2sato/agent-console/issues/991).

### user-accessible host
The hostname the user's browser can actually reach the server (and its sibling ports) at, derived from `window.location.hostname`. When AgentConsole is accessed remotely, `localhost` / `127.0.0.1` on the server side is meaningless to the browser, so the user-accessible host is used instead.

- **Canonical helpers:** [`getUserAccessibleHost()`](../packages/client/src/lib/user-accessible-host.ts) (returns `window.location.hostname` verbatim), [`isRemoteAccess()`](../packages/client/src/lib/user-accessible-host.ts) (true when the browser is not on a loopback host), and `bracketHostForUrl()` (IPv6 bracket-wrapping when composing a URL authority) in [`packages/client/src/lib/user-accessible-host.ts`](../packages/client/src/lib/user-accessible-host.ts).
- **Consumers:** VSCode remote-URL open ([`openInVSCode`](../packages/client/src/lib/api.ts)), MCP install-command composition ([`buildMcpInstallCommand`](../packages/client/src/lib/mcp-install-url.ts)), and terminal localhost-URL rewrite ([`localhost-rewrite.ts`](../packages/client/src/components/terminal/transforms/localhost-rewrite.ts)), which rewrites a printed `localhost` URL's href to the user-accessible host so a remote browser can click it.
- **See:** Issues [#987](https://github.com/ms2sato/agent-console/issues/987) (introduces the browser-host derivation), [#988](https://github.com/ms2sato/agent-console/issues/988) (extracts the helpers and adds the terminal URL rewrite).

## Events & Communication

### ConditionalWakeup
A registered shell-condition + interval that the server polls silently and notifies the session only when the condition exits 0 or a timeout is reached. Designed to preserve LLM context windows during "wait for X to be true" patterns. The target worker can be an `agent`, `terminal`, or (since Issue #1574 PR A) `embedded-agent` worker — see [PTY-backed Worker](#pty-backed-worker)'s `canReceiveNotifications` predicate. Delivery to an embedded-agent target routes through `SessionManager.deliverWorkerNotification` rather than a PTY write, and (per the [Mid-turn notification queue](#mid-turn-notification-queue)) queues instead of failing when the target is mid-turn.
- **Aliases:** wakeup, conditional poll
- **See:** Issue [#700](https://github.com/ms2sato/agent-console/issues/700), MCP tools `create_conditional_wakeup` / `delete_conditional_wakeup`
- **Contrast:** [Timer](#timer) (fires on interval regardless of state)

### Inter-Session Messaging
File-based message delivery channel between sessions. Used by the `send_session_message` MCP tool for explicit cross-session consultations and by `outputMode: "message"` of `run_process` to route long-form script stdout and `write_process_response` content to the receiving session/worker without flooding its PTY.
- **Aliases:** inter-session messaging, inter-session message files, inter-session message service, InterSessionMessageService, inter-session-message-service
- **See:** [Inter-Session Messaging design](design/inter-session-messaging.md), implementation [`packages/server/src/services/inter-session-message-service.ts`](../packages/server/src/services/inter-session-message-service.ts), MCP tool `send_session_message`, [outputMode](#outputmode)

### Mid-turn notification queue
The mechanism that lets a system-originated notification ([Timer](#timer), [ConditionalWakeup](#conditionalwakeup), or an inter-session message via `send_session_message`) land on an [EmbeddedAgentWorker](#embeddedagentworker) that already has a turn in flight, without either dropping the notification or interrupting the active turn. `EmbeddedAgentWorkerService.sendSystemNotification` parks the notification on a per-worker FIFO queue (`Runtime.pendingNotifications`, capped at 32 entries — overflow drops the OLDEST entry) instead of returning `TURN_IN_PROGRESS`, and delivers exactly one queued entry as the next ordinary turn on each subsequent `state: idle` event, in arrival order. The queue is cleared (nothing carried forward) when the worker's subprocess exits. This applies ONLY to system notifications — a human's own message via `sendUserMessage` mid-turn is unaffected and still rejects with `TURN_IN_PROGRESS`, exactly as before this mechanism existed.
- **Aliases:** notification queue, pendingNotifications, queueOnBusy
- **See:** Issue [#1574](https://github.com/ms2sato/agent-console/issues/1574), [`EmbeddedAgentWorkerService`](../packages/server/src/services/embedded-agent-worker-service.ts), [MCP tool surface: capability predicates in embedded-agent-worker.md](design/embedded-agent-worker.md#mcp-tool-surface-capability-predicates-not-per-type-branches)
- **Contrast:** [Idle Eviction](#idle-eviction) (a different mid-turn-adjacent concept: idle eviction never fires DURING an active turn — `turnActive` gates its commit point — while this queue exists specifically because a turn WAS active when the notification arrived)

### Notification Center
**Implemented** (spec: [notification-center.md](design/notification-center.md)) — Phase 1 (server: composed read-model, cursor, routes; [#1357](https://github.com/ms2sato/agent-console/issues/1357)) and Phase 2 (client: bell, badge, panel; [#1354](https://github.com/ms2sato/agent-console/issues/1354)) are both merged. The **human**-addressed awareness surface: a bell in the header plus a list of recent events, so a person who was not watching can still find out what happened. It is a **composed read-model, not an event store** — `GET /api/notifications` builds the list from existing domain rows at request time (v1 sources: artifacts, `worktree:delete` jobs), and an event kind is admitted only once it already has a durable domain record of its own (the record/awareness cut, §2 and §4). Two invariants carry the design: **N1** — the list renders only from domain rows read at fetch time, so a WebSocket broadcast is a cache-invalidation hint and never itself rendered (a phantom broadcast degrades to a refetch that finds nothing, the structural answer to [#1330](https://github.com/ms2sato/agent-console/issues/1330)); **N2** — items carry no state of their own. The badge's own realtime hint was worktree-deletion-only until [Artifact](#artifact-html-artifact) creation/deletion started emitting the same class of trigger (Issue #1520) — N1 governs both identically, since neither carries list content. v1 is **awareness-only and personal-scope** (both owner-confirmed 2026-08-18): obligations, which clear by *doing* rather than *seeing*, are a separate future lane, and the feed shows only events the viewing user owns or initiated. The response's `unreadCount` is computed server-side **pre-cap** and can exceed `items.length` once unread items pass the 50-item cap — the count and the list are computed over different windows, so client code must never derive the badge from `items.length`.
- **Aliases:** notification center, bell, notification list, NotificationItem
- **See:** [notification-center.md](design/notification-center.md) §3 (read-model + N1/N2), §4 (admission rule), §5 ([Notification Cursor](#notification-cursor)), §9 (phases)
- **Contrast:** [Inter-Session Messaging](#inter-session-messaging) and the `[inbound:*]` / `[internal:message]` PTY notifications (both **agent**-addressed delivery, with their own ledger and audience — deliberately excluded from this surface by admission rule 3); `NotificationManager` + Slack handler (outward push to an external surface, unchanged)

### Notification Cursor
The only new persistent state the [Notification Center](#notification-center) introduces: one row per user (`user_notification_cursor (user_id PK, last_seen_at)`) recording a **high-water mark of what that user has seen** — never what they have handled. Opening the bell advances it to the newest listed item's timestamp; the badge counts items newer than it. Server-persisted (not `localStorage`) so the state follows the user across browsers, and per-user because a shared read state would mark items read for people who never saw them. The accepted consequence: an individual item cannot stay unread once anything newer has been seen.
- **Aliases:** last_seen_at, user_notification_cursor, seen cursor
- **See:** [notification-center.md](design/notification-center.md) §5, `PUT /api/notifications/seen` (monotonic — the server rejects moving the cursor backwards)

### outputMode
Parameter on the `run_process` MCP tool that selects how the script's stdout and `write_process_response` content are delivered to the calling agent. Two modes:
- `"pty"` (default): the script's stdout is delivered as a `[internal:process]` PTY notification carrying the full content; `write_process_response` echoes content directly to the worker PTY. Existing behavior, backward-compatible with all prior `run_process` callers.
- `"message"`: the script's stdout is captured and routed through [Inter-Session Messaging](#inter-session-messaging) to the calling session/worker; `write_process_response` content is delivered through the same channel after stdin write succeeds. PTY receives only a brief `[stdout via message] path=… bytes=…` / `[response via message] …` notification per chunk so the owner retains progress visibility without the conversation being flooded by long-form Q&A. Designed for long interactive scripts (e.g., `.claude/skills/orchestrator/acceptance-check.js`, `sprint-retro.js`).
- **Aliases:** output mode, run_process outputMode
- **See:** Issue [#664](https://github.com/ms2sato/agent-console/issues/664), router [`packages/server/src/services/process-output-router.ts`](../packages/server/src/services/process-output-router.ts)

### Schema Version
A build-time content hash over the wire-schema file set (`packages/shared/src/schemas/*.ts`) that identifies the generation of the server/client wire contract. Derived by `scripts/generate-schema-version.mjs` into the committed constant `SCHEMA_VERSION` (`packages/shared/src/schema-version.gen.ts`), which is staleness-guarded by a test invoking the script's `--check` mode — no manual bump exists. The server advertises the version as the first frame on `/ws/app` (`{ type: 'schema-version', version }`) and as an `X-Schema-Version` header on every REST response (middleware mounted before auth). The client compares it against its compiled-in constant and force-reloads on mismatch at most once per server version (sessionStorage guard `agent-console:schema-version-reload-attempted`); a mismatch persisting after reload degrades to a manual-refresh error banner instead of looping.
- **Aliases:** SCHEMA_VERSION, X-Schema-Version, schema-version (WS message type)
- **See:** Issue [#927](https://github.com/ms2sato/agent-console/issues/927), [`scripts/generate-schema-version.mjs`](../scripts/generate-schema-version.mjs), [`packages/client/src/lib/schema-version.ts`](../packages/client/src/lib/schema-version.ts), [`packages/server/src/middleware/schema-version-header.ts`](../packages/server/src/middleware/schema-version-header.ts)
- **For implementers adding a schema field:** the standing ruling on what an older client does with an unknown field, and why no per-field compatibility machinery is built for it, is the header of [`packages/shared/src/schemas/index.ts`](../packages/shared/src/schemas/index.ts). This entry defines the concept; that header is the instruction.
- **Contrast:** [WebSocket Connection](#websocket-connection) (the transport itself; the schema version describes the payload contract generation carried over it)

### Archive Segment

A gzip-compressed slice of a worker's historical output stream (`<workerId>.seg-<N>.log.gz`), produced when the live output file exceeds its size limit. Replaces destructive truncation. Immutable once written; mapped to absolute stream offsets by the Segment Manifest. Defined in [terminal-history-paging.md](design/terminal-history-paging.md).

### Segment Manifest

Sidecar JSON (`<workerId>.segments.json`) recording each Archive Segment's absolute offset range plus `liveBaseOffset` (the absolute position of the live file's first byte). The single source for mapping a history-range request to a file. Defined in [terminal-history-paging.md](design/terminal-history-paging.md).

### Absolute Stream Offset

The byte position in a worker's cumulative output stream since worker creation (or last restart). Never rebased by archival. After the #959 accounting change, every `offset` on the worker WebSocket protocol uses this coordinate system (previously `history` offsets were live-file-relative and diverged from `output` offsets after truncation). Defined in [terminal-history-paging.md](design/terminal-history-paging.md).

### Worker Epoch

A per-worker incarnation identifier: the creation timestamp (milliseconds) minted when the worker is created or restarted, persisted in the Segment Manifest and carried on `output` / `history` / `history-range` messages. Clients compare epochs for **equality only** (never ordering), so clock regression across restarts is tolerated; a mismatch means the worker was restarted and the client must resync. A timestamp rather than a counter makes reuse impossible even if the manifest is lost. Defined in [terminal-history-paging.md](design/terminal-history-paging.md).

### Backwards Range Fetch

The `request-history-range` / `history-range` worker-WebSocket message pair for paging older history upward. A request names a `beforeOffset` (fetch bytes strictly before this Absolute Stream Offset), an optional `maxBytes` hint, and a `requestId` echoed back for correlation. The server answers with one storage unit's worth of bytes (a single Archive Segment or the live window — never stitched across a boundary), a `hasMore` flag (`startOffset > firstAvailableOffset`), and the Worker Epoch captured under the per-worker lock. Defined in [terminal-history-paging.md](design/terminal-history-paging.md) §5.

## Roles

### Orchestrator
The single owner-facing role for repository-level coordination. Owns prioritization, delegation, first-responder duties, work review, acceptance check, merge authority (subject to owner thresholds), retro execution, and rule/skill maintenance. The Orchestrator is invoked via the [`orchestrator`](../.claude/skills/orchestrator/SKILL.md) skill (typically `/orchestrator`). Auto-provisions the [Architect](#architect) session on startup if absent. Delegate workers spawned by the Orchestrator default to the `sonnet` model.

### Architect
An internal-only role for design review, spec drafting, multi-round audit, and cross-domain design consultation. **One Architect session per repository**, persistent across sprints, auto-provisioned by the [Orchestrator](#orchestrator) on startup. Idle-until-explicit-push — acts only on explicit Orchestrator messages. Owner does not interact with the Architect directly. Invoked via the [`architect`](../.claude/skills/architect/SKILL.md) skill and defaults to the `fable` model. Full role definition: [`docs/design/architect-role.md`](./design/architect-role.md).

## Maintenance

This glossary is canonical. When the following changes are introduced, the glossary must be updated in the same PR:

- New design doc (`docs/design/`) introducing a new domain concept
- New type, DB schema field, or API endpoint name representing a domain concept
- Existing design doc's Terminology section is added, renamed, or revised
- New rule / skill / narrative referring to a project-wide concept

If a term in the codebase or documentation does not appear here, either it is a drift to fix or a missing entry to add — both belong in the same PR that surfaced the gap.

**Responsibility**: PR author owns the glossary update for their PR. Orchestrator confirms during acceptance check via `acceptance-check.js` Q9 (Glossary Integrity).

**Operational rule**: see [`.claude/rules/glossary-maintenance.md`](../.claude/rules/glossary-maintenance.md) for the full trigger list, role assignments, and drift-handling decision tree. Automated linter detection is tracked separately (Issue [#671](https://github.com/ms2sato/agent-console/issues/671)).
