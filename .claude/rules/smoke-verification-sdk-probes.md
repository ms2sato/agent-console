# Smoke Verification: SDK premise probes

Smoke registrations for SDK premise probes; the registration rule and the reachability exceptions live in `test-trigger.md`.

**Shared prerequisites (referred to by the sections below).** Every probe here is a manual gate (the registration rule in `test-trigger.md`). Unless a section says otherwise it is billable and needs the invoking OS user's own real, authenticated `claude` CLI (the `claude-sdk` engine runs as that user; no provider key to configure), and sections state it with one clause (`Billable (...)`). The compaction-fidelity probe instead needs a provider key resolvable for `PROVIDER_KEY_REF` (default `opencode-go`, read from the single-user dev home; override with `PROVIDER_KEY_FILE`). **Exit codes for the measurement scripts** (unless a section lists its own): `0` = every selected arm produced a definite reading (a `STOP:` finding is a MEASUREMENT and still exits 0); `1` = INCONCLUSIVE for at least one selected arm (a control failed, a turn did not settle); `2` = HARNESS failure (bad arguments, unverified isolation, missing host precondition; nothing was measured).

## Additional Verification: Compaction Identifier-Fidelity Probe

PRs touching `DEFAULT_COMPACTION_PROMPT` / `loadCompactionPrompt` in `packages/embedded-agent/src/compaction-prompt.ts`, or `AgentLoop.compact()`'s distillation call in `packages/embedded-agent/src/agent-loop.ts`, should run `bun scripts/smoke/probe-compaction-fidelity.ts` locally before pushing (measurement, not a pass/fail gate — see below). This is the real-provider measurement for Issue [#1350](https://github.com/ms2sato/agent-console/issues/1350): whether conversation-local identifiers stated as **ordinary facts, with no preservation coaching**, survive a real `openai-api` compaction boundary verbatim. It boots a disposable server instance with a real `AppContext` and a real `/mcp` on a real port, plants three synthetic identifiers (a run id, a filename, a change reference) in a single uncoached turn, drives real pressure-round turns until a real `context-compacted` boundary fires, and reads the boundary's own persisted `summary` field — the actual distillation text the model produced — for each identifier's presence.

**A measurement, not a gate:** the script exits 0 whenever every requested run reached a real boundary and its summary was read, regardless of what fraction of identifiers survived. A non-zero exit means the *harness* could not produce a measurement (a run never reached a boundary within its round/time budget, a turn errored or timed out).

There is no CI-level pin on the prompt's composition (no preservation clause has shipped); this script is the only measurement of it.

Two properties of the script that matter when re-running it:

- **Billable (provider key):** a handful of small turns per `--n` repetition — cents, not dollars.
- **`--prompt-file <path>` selects the arm.** Omitted, the run measures the CURRENT bundled `DEFAULT_COMPACTION_PROMPT` (the PRE arm). Passed, the run measures the file's content instead, delivered through the exact same repo-layer override path `loadCompactionPrompt()` reads in production (`<cwd>/.agent-console/compaction-prompt.md`) — there is no test-only fork of the loader. `--n <count>` repeats the arm and aggregates a retention rate; comparing a PRE run against a POST run (pointed at a candidate revised prompt) is how a change to the clause is evaluated before it ships.

**Verification tier (Discipline 4 of `os-environment-coupling.md`):** Tier 4 (billable; dogfood host only -- permanent residue).

## Additional Verification: SDK Instruction-Loading Premise Probe

Before changing the SDK arm's `settingSources` value in `packages/embedded-agent/src/sdk-engine.ts`'s `buildOptions`, or before relying on any claim about what the SDK's native `settingSources: []` does or does not suppress, run `bun scripts/smoke/probe-sdk-instruction-loading.ts` against a real, authenticated `claude` CLI session. This is the Task 0 gate probe for Issue [#1343](https://github.com/ms2sato/agent-console/issues/1343)'s scoped section (project-instruction parity on the SDK arm): it drives two real SDK sessions against a scratch git repo containing three unguessable canary tokens — `CLAUDE.md` (canary A), `.claude/rules/unscoped.md` with no frontmatter (canary B), and `.claude/rules/scoped.md` with `paths: ["src/**"]` (canary C) — and asks the model, before and after a real `Read src/x.ts` tool call, whether it knows any of the three.

**What the two arms prove.** `--off` (`settingSources: []`, what ships today) asserts the whole Phase A design's load-bearing premise: that this setting suppresses the SDK's native project-instruction discovery ENTIRELY (CLAUDE.md and any native `.claude/rules/*.md` auto-discovery), both before and after a path-matching tool call — a leak of canary B or C is a STOP condition, not a tolerable finding (the SDK would be loading rules independently of `settingSources`). `--project` (`settingSources: ['project']`) is the positive control: it proves the canaries are actually detectable at all, and separately documents the native CLI's own lazy scoped-rule activation semantics (A and B known at session start, C unknown until the matching-path `Read` fires) — the empirical basis Phase B's `PostToolUse`-hook design premise rests on.

Two properties of the script that matter when re-running it:

- **Billable (`claude` CLI):** six small turns per full run (three per arm).
- **`--off` / `--project` select an arm**; omitted, the default is both, in order.

**Verification tier (Discipline 4 of `os-environment-coupling.md`):** Tier 4 (billable; dogfood host only -- permanent residue).

## Additional Verification: SDK PostToolUse Context-Injection Premise Probe

Before implementing the `PostToolUse` hook activation path in `packages/embedded-agent/src/sdk-engine.ts` for Issue [#1343](https://github.com/ms2sato/agent-console/issues/1343) Phase B (lazy activation of scoped `.claude/rules` on the claude-sdk engine), or before relying on any claim about whether a `PostToolUse` hook's `additionalContext` return value reaches the model, run `bun scripts/smoke/probe-sdk-post-tool-use-context.ts` against a real, authenticated `claude` CLI session. This is the Task 0 gate probe for Phase B's design premise: a `PostToolUse` hook is how a scoped `.claude/rules` entry gets injected lazily, the first time a matching tool call fires, rather than being loaded eagerly at session start.

**Three arms, and what each proves.** `--a` (SUBJECT) registers a `PostToolUse` hook matching `Read` that fires once and returns `additionalContext` containing a nonce; the turn sequence asks for the nonce before any tool call (expect: unknown), triggers `Read src/x.ts`, then asks again (expect: known). `--b` (NEGATIVE CONTROL) is mechanically identical but the hook returns only `{ continue: true }`, no `additionalContext` — this is what makes Arm A's result attributable to `additionalContext` specifically rather than to the model guessing or some other artifact of merely registering a matching hook. `--c` (SIZE-CEILING MEASUREMENT) repeats Arm A's shape but wraps the nonce inside ~40 KB of deterministic filler, recording whether the nonce still arrives at that size (the vendored SDK's `sdk.d.ts` documents no cap on `additionalContext` itself, unlike the neighboring `classifierContext` field's documented 2000-code-unit cap).

**STOP condition.** If Arm A fails while Arm B behaves as expected (B does not leak), the `PostToolUse` hook does not deliver `additionalContext` to the model on this build, and Phase B's claude-sdk arm takes the recorded fallback (R6): eager inclusion instead of lazy `PostToolUse`-hook injection. If Arm B leaks the nonce, the probe itself is unreliable, not the SDK, and Arm A's result cannot be trusted until that is understood.

Two properties of the script that matter when re-running it:

- **Billable (`claude` CLI):** nine small turns per full run (three per arm: ask#1, the Read, ask#2).
- **`--a` / `--b` / `--c` select an arm**; omitted, the default is all three, in order.

**Verification tier (Discipline 4 of `os-environment-coupling.md`):** Tier 4 (billable; dogfood host only -- permanent residue).

## Additional Verification: SDK Live Effort-Apply Premise Probe

PRs touching `SdkEngine.setModelParams` in `packages/embedded-agent/src/sdk-engine.ts` (the `query.setModel` / `query.applyFlagSettings({ effortLevel })` pair, or the `model-params-applied` reporting around it), or relying on any claim about what `applyFlagSettings` does to a live session's reasoning effort, must run `bun scripts/smoke/probe-sdk-effort-live-apply.ts` against a real, authenticated `claude` CLI session. This is the premise probe behind the mid-run effort path of Issue [#1521](https://github.com/ms2sato/agent-console/issues/1521) Phase 3.

**Conclusion a reader must act on:** the SDK DOES have a runtime effort setter (`applyFlagSettings({ effortLevel })`); the earlier restart-in-place design and its `effort-requires-restart` refusal were removed before shipping. The unit tests pin what our code CALLS; this is the only thing that measures what the SDK DOES with it, so a future SDK bump that changes the behavior surfaces here or nowhere (history: `docs/narratives/2026-10-12-sdk-probe-design-rationale.md`).

**Three arms, and what each measures.** `--set` (SUBJECT) constructs a query with `Options.effort: 'low'`, spends a control turn, then calls `applyFlagSettings({ effortLevel: 'high' })` and spends a second turn: `high` on turn 2 means the flag layer overrode a query-time effort on a live session. `--clear` answers what CLEARING falls back to — `'low'` at construction, then `'medium'`, then `null`; `'medium'` is deliberate (it separates `low` = stale query-time value, `high` = SDK default, `medium` = clear ignored). `--absent` (BASELINE) omits `Options.effort` entirely for one turn, giving the level a fresh session with no override runs at — which is exactly the state the discarded restart-based design would have produced, so `--clear`'s turn 3 read against it is what shows a live clear and a restart to be the same state or not.

**The positive control is a gate, not a formality.** Turn 1 of the `--set` and `--clear` arms must observe `low`; if it does not, the observables do not track `Options.effort` on that build and the arm reports INCONCLUSIVE rather than a verdict. The observables are a `PostToolUse` hook's `input.effort.level` (documented in the vendored `sdk.d.ts` as the active level for the current turn, after any silent per-model downgrade) cross-checked against `echo $CLAUDE_EFFORT` from a `Bash` call; the model is never asked what effort it is using. A call to `applyFlagSettings` that returns without throwing is NOT evidence — `scripts/smoke/probe-sdk-compaction.ts` measured that same call honouring `autoCompactEnabled` while silently ignoring `autoCompactWindow`, so only an observed effect counts.

Two properties of the script that matter when re-running it:

- **Billable (`claude` CLI):** six small turns per full run (two for `--set`, three for `--clear`, one for `--absent`).
- **`--set` / `--clear` / `--absent` select an arm**; omitted, the default is all three, in order.
- **Four exit codes, and they separate the two outcomes that matter.** `0` = measured, and PS9 HOLDS. `1` = INCONCLUSIVE — a failed positive control, an `applyFlagSettings` that threw, a turn that did not settle, or a run that selected no arm bearing on PS9 (a `--absent`-only run measures a baseline and says nothing about the premise). `2` = HARNESS failure, so nothing about the SDK was measured. `3` = measured, and PS9 is REFUTED. A conclusive refutation outranks an inconclusive sibling arm, because the refutation is a measurement in its own right and is precisely what this script exists to surface on an SDK bump. The mapping is pinned by `scripts/smoke/__tests__/probe-sdk-effort-live-apply.test.ts`, which imports the verdict function directly and never runs the billed measurement.

**Verification tier (Discipline 4 of `os-environment-coupling.md`):** Tier 4 (billable; dogfood host only -- permanent residue).

## Additional Verification: SDK Auto-Memory Premise Probe

Before writing the Phase 2 design for epic [#1636](https://github.com/ms2sato/agent-console/issues/1636)'s auto-memory work, or before relying on any claim about whether the SDK's `autoMemoryEnabled` / `autoMemoryDirectory` / `SDKMemoryRecallMessage` mechanism reads, writes, leaks, or redirects on a headless `claude-sdk` session, run `bun scripts/smoke/probe-sdk-auto-memory.ts` against a real, authenticated `claude` CLI session. This is the Task 0 gate probe for Issue [#1658](https://github.com/ms2sato/agent-console/issues/1658). Production now sets `settings.autoMemoryEnabled: false` (Issue #1681; see the `--auto-memory-off` bullet below), so the probe confirms the SDK actually honors the declared setting (origin and history: `docs/narratives/2026-10-12-sdk-probe-design-rationale.md`).

**Two corrections to the Issue's own wording** (confirmed against the vendored `sdk.d.ts`): `SDKMemoryRecallMessage.memories[]` carries `scope: 'personal'|'team'|'organization'` and a top-level `mode: 'select'|'synthesize'` (there is no `memory_type` field; that belongs to `InstructionsLoadedHookInput`), and `autoMemoryEnabled` / `autoMemoryDirectory` live on the `Settings` interface, reached via `Options.settings?: string | Settings`, not directly on `Options`.

**The sanitized-cwd algorithm cannot be read from source** (the auto-memory logic lives inside the `claude` binary, not the vendored bundle), so every arm that needs the SDK's default `autoMemoryDirectory` for a scratch `cwd` discovers it at runtime: one turn with `autoMemoryEnabled: true`, then diff the isolated `CLAUDE_CONFIG_DIR/projects/` listing.

**Four arms, each against a disposable scratch cwd and its own throwaway, isolated `CLAUDE_CONFIG_DIR` — no real user memory directory is ever touched**, by the same construction every sibling probe's own `verifyIsolation()` check relies on for session storage generally:

- **`--a` RECALL.** Seeds a nonce as an index-linked topic file (per the contract at [code.claude.com/docs/en/memory](https://code.claude.com/docs/en/memory); the index-line and frontmatter shape come from Claude Code's built-in auto-memory instructions, since the page documents the architecture in prose only) at the SDK's own default Project-scope memory directory (path discovered per the adaptation above), ask a fresh session at the same cwd whether it knows the fact. Observes both the MECHANISM (`SDKMemoryRecallMessage`, path-matched against the seeded topic file so "recall happened" means "recall happened for the format assumed") and the OUTCOME (the model's answer), with a negative-control cwd (nothing seeded) in the same run — a control failure (the control cwd itself recalls or answers with the nonce) gates the reading exactly like `probe-sdk-effort-live-apply.ts`'s positive control gates its own. **A `RECALL DOES NOT WORK` verdict from this arm must be read alongside Arm C's independently observed write-file layout in the findings comment** before being cited as a premise refutation — if Arm C's own write lands in a different shape than this arm assumed, that is evidence the assumed seeding format needs revisiting, not that recall itself is broken (same interpretation-time-cross-reference shape as Arm B's scope caveat below).
- **`--b` LEAK.** At a cwd with nothing ever seeded, asks a broad "what do you know about me" question and reports whether anything surfaces and, if so, its `scope`/`mode` — re-deriving #1348's finding under controlled conditions. `content` is never logged, by construction (`redactRecallEntry`): only `scope`/`mode` and whether the surfaced path lies within this run's own isolated config dir (this run's own scratch data) or not (a real leak from elsewhere). **Scope limitation (Architect ruling, 2026-09-13):** because every arm runs under an isolated `CLAUDE_CONFIG_DIR`, this arm can only observe a recall whose `path` is NOT rooted under that throwaway dir (`organization`, in principle `team`) — the `'personal'`/User-scope channel #1348 actually observed is unreachable by this arm's design, so a `NO LEAK` result must never be read as covering User-scope; see Issue [#1663](https://github.com/ms2sato/agent-console/issues/1663) for the tracked follow-up.
- **`--b1` / `--b2` PERSONAL-SCOPE sub-runs (Issue [#1663](https://github.com/ms2sato/agent-console/issues/1663); billable, never part of the bare default, <=2 billed turns each; SYNTHETIC seeds only, inside an isolated config dir).** The emitter's scope rule, read from the vendored 0.3.238 bundle (a reading of the binary, NOT a measurement): a recalled path is `team` if it lies under a memory-store mount, `personal` if it lies under the auto-memory directory, and `personal` as the fallback for anything unclassified; the auto-memory directory is `override ?? autoMemoryDirectory (policy/flag/local/project/user settings) ?? <CLAUDE_CONFIG_DIR>/projects/<sanitized repo/cwd>/memory`, so `personal` is NOT a separate user-global location and an isolated dir CAN hold it. **The ORACLE is the answer, not the recall-message channel:** the arms ask for a synthetic codename and test the answer for an unguessable nonce (a substring test, logged only as `textHasNonce` + length + `toolUseCount`, never the body), with `Options.tools: []` so zero tool calls holds by construction (tools on made "nonce + tool calls" ambiguous between injected-then-read and browsed-by-Bash). The nonce is in the INDEX line, because the session-start injection loads `MEMORY.md`, not topic files (a topic-only token cannot reach a tools-off answer -- an observable bug this arm hit once). The context-injection route emits NO `SDKMemoryRecallMessage` (measured: nonce in the answer, zero recall messages), so a recall-message-only detector cannot see it; **Arm B's old `NO LEAK` therefore means "no recall message", nothing stronger.** `--b1` is the CLI's MECHANISM (`CLAUDE_CODE_PROJECT_DIR_NAME` set beside the isolated config dir; NOT a production route -- `env-filter.ts` strips `CLAUDE_CODE_*` before `sdk-engine.ts` passes the env) with a variable-less negative; `--expect-no-personal` skips the seed. `--b2` is the PRODUCTION route: an isolated user-level `settings.json` (`autoMemoryEnabled: true` + `autoMemoryDirectory`), production's `settingSources: ['user','local']`, a positive control without our setting, then production's explicit `settings.autoMemoryEnabled: false`; a nonce or recall message under our false prints a `STOP` line and is an Issue against `buildOptions`, not a probe note. Measured 2026-10-13: B2 CONTAINMENT HOLDS (control carried the nonce, our explicit false left it out, zero tool calls, no recall message); B1 MECHANISM REACHABLE. These cover the INJECTION route only; whether a worker with `Bash` can browse its own `CLAUDE_CONFIG_DIR/projects/*/memory` is a separate property (tool-assisted nonce hits were measured with tools on). **Standing limitation of the ORIGINAL Arm B (`--b`, real-dir leak re-derivation): it has no safe oracle for the injection route** -- there is no known token to test for on a real directory and the answer body cannot be logged -- so it cannot be made to cover #1348's real-dir channel.
- **`--c` WRITE.** Tells the model something worth remembering, polls for a file to appear under the default directory within a bounded timeout (auto-memory write may have its own gate assuming an interactive TUI a headless SDK session can't satisfy — unknown until measured).
- **`--d` REDIRECT.** Sets `autoMemoryDirectory` explicitly and confirms both a read and a write land at the configured path — and that the write does not ALSO leak to the default location, which is what makes the override exclusive rather than merely additive.

Two properties of the script that matter when re-running it:

- **Billable (`claude` CLI):** roughly 6-10 small turns across the four arms, plus bounded local-filesystem polling for write detection.
- **`--a` / `--b` / `--c` / `--d` select arms**; omitted, the default is all four, in order. **`--expect-no-recall` (arm A) and `--expect-no-write` (arm C) are polarity flags**, not arm selectors — each runs its arm with the seeding/write-prompting step deliberately skipped and confirms the probe's OWN detection correctly reports absence, per `workflow.md`'s "a check's existence is not its detection power" applied to the probe's own apparatus before its numbers are trusted. They only take effect when their arm is also selected (explicitly, or via the all-four default).
- **Exit codes** as in the header (a measurement script, not a pass/fail gate: `0` regardless of which way any individual measurement came out). The mapping, each arm's verdict classifier and the privacy redaction function are pinned by `scripts/smoke/__tests__/probe-sdk-auto-memory.test.ts`, which imports them directly and never runs the billed measurement.

**Task 0b (Issue [#1667](https://github.com/ms2sato/agent-console/issues/1667)) adds `--e` / `--f` / `--g`:** arms A-D never set `Options.systemPrompt`, whose omitted value is undocumented -- a confound that could alone explain every REFUTED verdict. Arms E/F/G separate awareness, switches, and timescale, cheapest first:**

- **`--e` AWARENESS.** Seeds the same MEMORY.md-index-plus-topic-file shape as arm A (via the shared `seedMemoryTopic` helper both arms now call — never a second copy of it), with a NONCE-BEARING index title (arm A's own fixed title is guessable from this repo's source; a nonce is not). Runs one combined turn per `systemPrompt` configuration — (i) omitted entirely (arms A-D's and production's own shape today), (ii) `{ type: 'preset', preset: 'claude_code' }`, (iii) the same preset with `excludeDynamicSections: true` as a negative control — asking both required observables at once: (1) LOCATION, "quote the absolute path of your auto-memory directory", and (2) ACCESS, "what is the title of the entry in your memory index?". A four-way classifier (`classifyArmEConfig`) reads the two together per configuration — both hit -> aware-and-reading, ACCESS only -> aware-prose-only (NOT absence — this is what stops a prose-only dynamic section from being misread as a REFUTED premise), LOCATION only -> told-not-read (a real finding on its own), neither -> unaware. **The (iii) control is evaluated honestly, not assumed clean**: the vendored `sdk.d.ts` documents that `excludeDynamicSections` re-injects the stripped content as the first user message, so if either observable still surfaces under (iii), the script reports `control: NONE AVAILABLE` rather than treating the negative control as trustworthy. The `SDKControlGetContextUsageResponse.memoryFiles` accessor (the camelCase, harness-wired sibling of the Issue's own `SDKContextUsage.memory_files` — see the script header for the correction) is read as a bonus mechanism observable on these same turns via `pollUsage: true`, logged but not gating the classification.
- **`--f` SWITCHES.** Picks whichever of (i)/(ii) is classified as NOT `unaware` first — LOCATION awareness alone counts, not just ACCESS, since arm F's premise is "awareness exists under configuration X" (`--f-config <omitted|preset>` overrides explicitly when arm E did not run in the same invocation, defaulting to `omitted`). Under that configuration, sets `Options.settings.autoMemoryEnabled: true` AND `autoDreamEnabled: true` explicitly, then re-runs arm C's write check and arm A's recall check UNCHANGED via the same shared cores (`runWriteCheck` / `runRecallCheck`) both original arms now call.
- **Arm F/G halt by default, ONLY when no configuration shows awareness (Architect ruling, PR #1676 review, refining an earlier owner ruling).** When arm E ran in the same invocation and shows NEITHER (i) nor (ii) carries awareness, arm F reports a `HALTED` verdict instead of spending turns — measuring the switches against a model that cannot know what to write would be uninterpretable, and arm E's own verdict stays `conclusive` so the run still exits `0`. Arm G reports its own SKIPPED verdict in turn (it needs arm F's write result). **A dirty or unsettled (iii) control does NOT halt:** the vendored `sdk.d.ts` documents that `excludeDynamicSections` re-injects the stripped sections as the first user message, so (iii) surfacing an observable is the EXPECTED result on a doc-conformant build (halting on it would make F/G unreachable without `--force-f`). It only caveats attributing (i)/(ii)'s awareness to the dynamic section specifically. `--force-f` overrides the awareness halt for a deliberate operator run anyway; a standalone `--f` run with no `--e` in the same invocation is unaffected by this gate.
- **`--g` TIMESCALE.** Re-runs arm F's write check ONLY, with a longer poll via `--extended-timeout <ms>` (omitted or `0` behaves exactly like arm F's 60s poll). Runs ONLY when arm E showed awareness under PRODUCTION's configuration (`omitted`) AND arm F still showed no write — selecting `--g` therefore always also selects `--e` and `--f` as prerequisites, printing a SKIPPED verdict when the gate is not met rather than running. **Owner directive, 2026-09-13, binding: `--extended-timeout` is capped at 5 minutes (300000ms) regardless of what is requested** (`EXTENDED_TIMEOUT_CAP_MS`); the script clamps and warns rather than trusting the caller. No teardown arm, no recall re-check. The shared write-poll loop (`pollForContent`) makes no repeated LLM turns, so a longer window costs wall-clock only, never additional billed turns.
- **Order confound closed (Architect ruling, PR #1676 review).** (i)/(ii)/(iii) run sequentially against the SAME memory dir with `autoMemoryEnabled: true`, so a write during one configuration's turn could change what the next configuration observes. The memory dir is deleted and reseeded identically (same title, same nonce) immediately before every configuration's turn — zero extra turns — and the memory-dir file count is logged both after reseeding and after the turn.
- **Real config-location cross-check, run around every arm (not once at the end), with an attribution filter (Architect ruling, PR #1676 review).** Before ANY arm runs (arms A-D included), the script resolves where the OPERATOR's real, non-isolated `CLAUDE_CONFIG_DIR` lives (the env var if already set, else `~/.claude` — measured via existence, never assumed), recursively snapshots every file's mtime under it, and writes a small canary file there (named `probe-sdk-automem-canary-<runId>.tmp`, matching the `PROBE_SLUG` constant, `probe-sdk-automem`) as an in-band positive control. **This canary write is the ONE thing this script writes outside its own isolated per-arm config dirs** (owner ruling: compliant with `os-environment-coupling.md` Discipline 2 — same operator, project-scoped write to that operator's own home, self-cleaned). After every selected arm has run, the script snapshots again — but only a path ATTRIBUTABLE to this run counts toward escalation: its own path contains `PROBE_SLUG` (path-wide — the canary, or any probe-named scratch artifact), OR its post-run content contains one of the nonces this run minted (tracked via `trackedNonce`) WITHIN a `memory/` path segment specifically. **The `memory/` scoping is load-bearing:** the delegate session running this probe ingests its stdout (every nonce) into its own transcript `.jsonl` under the same real config dir, so an unscoped nonce match would false-escalate on every run; a transcript is never under `memory/`. Everything not attributable is logged as "unrelated concurrent activity: N paths, of which M echoed a run nonce outside any memory/ dir" and never escalates, since the same OS user's OTHER live Claude Code sessions write their own transcripts continuously and a raw "did anything change" diff would false-positive on any host with concurrent activity . The canary is classified through this SAME filter, not a raw diff check, so its positive control proves the filtered detector works. A failed positive control or an attributable change escalates the script's own exit code to `HARNESS` regardless of what the arms measured. The canary is removed in a `finally` block.
