## Additional Verification: Preview Sandbox Real-Browser Check

PRs touching `packages/client/src/lib/preview-sandbox.ts`, `packages/client/src/lib/__fixtures__/preview-sandbox-corpus.ts`, or `packages/client/src/components/workers/PreviewPanel.tsx` must run `bun run check:preview-sandbox-browser` locally before pushing. This runs `scripts/run-preview-sandbox-browser-check.mjs`, which re-verifies the mXSS regression corpus against a real Chromium browser — `bun:test`'s happy-dom environment does not reproduce Chromium's HTML5 parsing edge cases (see `.claude/rules/os-environment-coupling.md`). This check is a real-browser regression gate, not a sibling-test requirement, so it is not part of the `preflight-check.js` coverage patterns in `test-trigger.md`. **Verification tier (Discipline 4 of `os-environment-coupling.md`):** Unprivileged (no tier-2/3/4 residue; any machine with bun) — the real-Chromium requirement above is a browser dependency, not an elevation tier.

## Additional Verification: PTY Master FD Leak Check

PRs touching `packages/server/src/lib/pty-provider.ts` or `packages/server/src/services/worker-manager.ts`'s `detachPty` must run `bun scripts/smoke/check-pty-fd-leak.ts` locally before pushing. It drives 100 real spawn/kill cycles through the production `bunTerminalProvider` and asserts that the process's ptmx-fd count (`/proc/self/fd`) and the kernel-wide allocated-pty counter (`/proc/sys/kernel/pty/nr`) stay flat — confirming `BunTerminalPtyAdapter.dispose()` actually releases the `Bun.Terminal` master-fd handle deterministically, rather than relying on the object becoming unreachable and incidentally GC-finalized (unsound in production, where `InternalPtyWorker.pty` stays reachable via session/worker maps for the life of the worker) (see Issue #1196). This check is a real-fd regression gate, not a sibling-test requirement, so it is not part of the `preflight-check.js` coverage patterns in `test-trigger.md`. **Verification tier (Discipline 4 of `os-environment-coupling.md`):** Unprivileged (no tier-2/3/4 residue; any machine with bun).

**FREE AND DETERMINISTIC** -- no `claude` CLI turn, no provider key, no LLM call anywhere in this path (the two `claude-code-builtin` PTYs the script spawns for D and T are interactive shells with no prompt ever sent). The exception here is cost, not gate placement, same convention as `check-restore-failure-declaration.ts`'s header.

**Four scenarios in one run, and the controls are the point.** (1) POSITIVE CONTROL: `issues` `closed` -- unaffected by this PR, still fans out via the OLD per-session loop to both D and T (never the `quick` delegate), confirmed via a direct SQLite read of `inbound_event_notifications`. (2) NEGATIVE CONTROL: `issues` `labeled` with a non-matching label -- zero new notification rows, plus the server's own captured stdout contains `resolveIssueLabeledTargets`'s exact non-match log line (`"issue:labeled event did not match repository's configured trigger labels"` in `resolve-targets.ts`), so the negative result is attributed to the code path actually running rather than to silence indistinguishable from a broken harness (`workflow.md` sub-pattern 9/5). (3) POSITIVE: `issues` `labeled` with a matching label -- deliberately cased differently than the repository's configured `issueTriggerLabels` value, exercising `matchesAnyTriggerLabel`'s case-insensitive compare rather than a naive `===` -- routes exclusively to the repository's DESIGNATED SET, D and D2 (Issue [#1716](https://github.com/ms2sato/agent-console/issues/1716): both designated through real `set_orchestrator_session` calls, the second asserted to add D2 without displacing D), confirmed by reading D's AND D2's real worker output files for the `[inbound:issue:labeled]` PTY-notification tag; T and the delegate must NOT receive it. (4) POSITIVE: `issues` `opened` with a full label set (not `labeled`'s single-added-label shape) containing the matching label among others, exercising `parseIssueOpened`'s distinct matching path, same D-and-D2-not-T assertion shape. D2 stays paused for scenarios 5-7, and scenario 5 additionally asserts the paused D2 does not receive the fallback either (same per-session exclusion on the fallback path).

**Scenario 4c and the scenario-5 embedded assertion (Issue [#1739](https://github.com/ms2sato/agent-console/issues/1739)) cover an EMBEDDED-designated recipient, and are the shipping-path E2E for routing `AgentWorkerHandler` through `SessionManager.deliverWorkerNotification`.** After 4b, the smoke hosts a stub OpenAI-compatible provider in its own process (`Bun.serve`, port 0; every `POST /v1/chat/completions` answered with a scripted final assistant message, no tool calls, every request body recorded), creates an `openai-api` definition through the real `POST /api/embedded-agents` with `provider.baseUrl` pointed at the stub and a fake `apiKeyRef` resolved from a `provider-keys.json` written into the disposable home, creates a fourth worktree session E (`smoke-branch-e`) whose initial worker is that embedded agent (`embeddedAgentId`; E has NO PTY `agent` worker), and designates E through a real `set_orchestrator_session` call, asserting the set reads exactly {D, D2, E}. (5-E) The main-push fallback additionally asserts E received `[inbound:ci:completed]` the same way, with exactly one more stub request. Polarity (Q12, measured on unmodified `main` before the change): every E assertion FAILS and the skip record IS present naming E. Teardown deletes E's session through the real route before the child server is killed, stops the stub only after the server has exited, and prints the stub's port and request log when any assertion failed. Scenarios 6 and 7 still assert "T receives neither"; scenario 7 must stay the LAST webhook poster (its "most recent job" query depends on that).

**Two more scenarios extend this smoke for the designated-session fallback (Issue [#1661](https://github.com/ms2sato/agent-console/issues/1661)), covering the per-session-loop path's "resolves to nobody or a dead session" gap that `issue:labeled` routing does not share.** (5) POSITIVE, main-push fallback: a `workflow_run` `completed`/`success` event on `head_branch: 'main'` matches zero registered sessions (neither D's nor T's worktreeId) -- `resolveTargets`'s new fallback routes it to D, confirmed by reading D's real worker output file for the `[inbound:ci:completed]` tag; T must not receive it. `head_sha` is omitted from the payload so `job-handler.ts`'s `ciCompletionChecker` gate (active only when `commitSha` is present) never runs. The same `workflow_run` shape as scenario 5, branch-matching O, routes to BOTH O (direct match) and D (fallback, since O's parent P is no longer live); T must receive neither. Scenario 6 uses a paused parent (the row survives but the parent is absent from the live session manager); the genuinely-deleted parent is scenario 7 (Issue [#1677](https://github.com/ms2sato/agent-console/issues/1677); history: `docs/narratives/2026-10-12-server-smoke-history-and-measurements.md`).

**A seventh scenario (Issue [#1677](https://github.com/ms2sato/agent-console/issues/1677)) tests the genuinely-deleted-parent shape directly, plus proves the fix stops job-level retry.** (7) POSITIVE, deleted-parent fallback + no job retry: a fourth worktree session Q is created with `parentSessionId` pointing at a real session R, which is then genuinely DELETED via `DELETE /api/sessions/:id` -- unlike scenario 6's pause, this removes R's row from the `sessions` table entirely, reproducing the exact FOREIGN KEY-constraint shape scenario 6's comment describes. **Trust-dialog workaround:** a brand-new working directory (every fresh `git worktree add` path) trips the interactive `claude` CLI's "Do you trust the files in this folder?" prompt at PTY startup, which blocks forever. The script seeds an ISOLATED `CLAUDE_CONFIG_DIR` (a read-only copy of the real OS user's `~/.claude.json` with `projects` entries added for the worktree paths -- never a mutation of the real file) before spawning the disposable server; `CLAUDE_CONFIG_DIR` is not in `packages/server/src/services/env-filter.ts`'s blocked/protected lists, so it reaches the spawned PTY unchanged. A from-scratch config triggers the first-run onboarding wizard instead (rationale: `docs/narratives/2026-10-12-server-smoke-history-and-measurements.md`).

This is a real-process regression gate for the shipping webhook->job-queue->handler chain, not a sibling-test requirement, so it is not part of the `preflight-check.js` coverage patterns in `test-trigger.md`. It is a manual gate, never a CI job (same as this file's other real-child-process smokes).

**Deliberately NOT given a `#1872`-style `*.run.test.ts` CI wrapper, even though it is free:** it seeds `CLAUDE_CONFIG_DIR` from a copy of the operator's real `~/.claude.json` and spawns real `claude-code-builtin` PTYs, which a GitHub-hosted runner lacks, so "free and deterministic" (#1872's wrapping criterion) is necessary but not sufficient -- it must also be portable. It stays a manual gate.

**Verification tier (Discipline 4 of `os-environment-coupling.md`):** Unprivileged (no tier-2/3/4 residue; any machine with bun) — free and deterministic, no `claude` CLI, no provider key.

Without `--turn` the stub provider, the fake key and the stdout are unchanged. ## Additional Verification: PTY Exit-Observation Probe

PRs touching `pty-provider.ts`'s `BunTerminalPtyAdapter` exit wiring (the `subprocess.exited` bridge in the constructor, L281-300) or its `onExit` replay-on-attach handling (L353-372), the legacy `bunPtyProvider`'s native `bun-pty` library usage, or any Bun version bump / `MIN_BUN_VERSION` change, should run `bun scripts/smoke/probe-pty-exit-observation.ts` (and its `--contend` arm) before relying on any claim about whether a PTY exit event is reliably observed under host load. This is the Issue [#1879](https://github.com/ms2sato/agent-console/issues/1879) measurement instrument built to settle whether `check-exit-127-diagnostic.ts`'s `selfCheck()` flake under contention is a lost exit event in the underlying `PtyProvider` (LOST-EXIT) or a genuinely stuck child (STUCK-CHILD): it spawns the identical `sh -c 'echo ok'` PTY via the real, selected `PtyProvider.spawn(...)` in a sequential cycle loop, and on every timeout reads, in order, the real `/proc/<pid>` state, `kill(pid, 0)`'s errno, whether the provider's own exit listener fired, and `Bun.version`/`os.loadavg()` -- never via `pgrep -P` polling (the Issue records that method as the one that saw nothing).

**Provider identity matters.** `--provider bun-terminal` (default -- production's actual configured default, `PTY_PROVIDER=bun-terminal`, no systemd override) exercises `BunTerminalPtyAdapter`. `--provider bun-pty` (legacy opt-in) exercises the LEGACY native `bun-pty` library (`bunPtyProvider`, slated for removal per #828), a bare `require('bun-pty').spawn(...)` call with no JS-level wrapping in `pty-provider.ts` at all. A measurement against `bun-pty` says nothing about `BunTerminalPtyAdapter`'s exit bridge, and vice versa. (History of the provider split, #1879 / #1886 / #1888: `docs/narratives/2026-10-12-server-smoke-history-and-measurements.md`.)

**DELAYED-EXIT vs. LOST-EXIT (Issue #1888).** A `--timeout-ms 1` run cannot tell a lost exit event from one that simply had not fired yet at the 1-2ms mark the timeout loses at -- a healthy `echo ok` classified as LOST-EXIT under `--timeout-ms 1` is the same snapshot shape as a genuine loss, differing only in elapsed time. `--grace-ms N` (default 2000; `0` disables, reproducing the pre-#1888 behaviour) opens a post-timeout observation window BEFORE `pty.kill`/`dispose`: if the exit listener fires within the window, the cycle is `DELAYED-EXIT` (`exitFiredWithinGrace: true`, plus `lateFireMs`, the time from timeout to the late fire) rather than `LOST-EXIT`, regardless of `procState` -- the exit event arrived, so the pid being gone by the time it is observed is consistent, not contradictory. `LOST-EXIT` now means the listener fired neither at timeout nor within the grace window. `--grace-ms 0` reproduces the pre-#1888 verdicts exactly.

**MEASUREMENT, not a gate.** Exit codes: `0` = every cycle produced a definite reading (a timeout classified LOST-EXIT, DELAYED-EXIT, or STUCK-CHILD is a measurement, not a failure); `1` = at least one cycle was INCONCLUSIVE; `2` = harness (the in-run positive control failed, or bad arguments) -- a `2` prints no verdict, because the instrument's own ability to see a live-then-dead process was not established. The classifier (`classifyTimeout`) and the exit-code mapper (`determineExitCode`) are pinned by `scripts/smoke/__tests__/probe-pty-exit-observation.test.ts`, which imports them directly and never spawns a PTY.

**`--contend`** spawns (default 4, `--contend-n N` overrides) `bun -e` busy children (CPU spin + fork storm) owned and SIGKILLed by the probe itself in a `finally` block -- deliberately not `bun run test`, which would collide with the full-suite slot rule. `--cycles N` (default 20) and `--timeout-ms N` (default 30000, matching `check-exit-127-diagnostic.ts`'s `EXIT_WAIT_TIMEOUT_MS`) override the loop shape; `--timeout-ms 1 --cycles 1` is the Q12 sanity check that the instrument emits a complete observable set on a healthy child before trusting a real 20-cycle run -- against the legacy `--provider bun-pty`, this shape now reads `DELAYED-EXIT` rather than `LOST-EXIT` (the grace window catches the healthy child's late fire). `--provider bun-pty|bun-terminal` selects which `PtyProvider` is under measurement, per the paragraph above.

Free and unprivileged; no billed CLI or login dependency -- but NOT deterministic: the probe measures runtime-sensitive PTY exit behavior under real host load, so its verdict legitimately varies between runs (see Issue #1879's findings comments). It is a manual gate, never a CI job -- a measurement instrument, not a regression gate.

**Verification tier (Discipline 4 of `os-environment-coupling.md`):** Unprivileged (no tier-2/3/4 residue; any machine with bun).
