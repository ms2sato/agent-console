# Design Principles

These principles apply to all code changes in this project.

**Purpose over speed.** Do not rush to finish quickly at the expense of losing sight of the original purpose.

**Do not blindly follow existing patterns.** Existing code is not automatically correct. Evaluate whether patterns are appropriate before adopting them.

**Enforce constraints through structure, not convention.** If a constraint can be expressed in the type system, do not enforce it through runtime checks or documentation. `string` where a union type would work, `Record<string, string>` where a typed interface would work — all are type safety gaps. Always choose the path that makes invalid states unrepresentable.

**Define types by what they represent, not where they're used.** A type's home is determined by the scope of the concept it models, not by which module first needs it.

**Think before you act.** First consider the correct approach rather than immediately implementing the easiest solution.

**Speak up about issues.** When you notice something problematic outside the current task scope, mention it as a supplementary note.

**When identity filtering happens after the fetch, check whether the fetch window closes before the filter runs.** For every source that returns caller-specific data, ask two questions that take about two lines of reading each: *is the fetch itself scoped by the caller's identity, or is an unscoped result set filtered afterward?* and, if the latter, *is the row cap applied before or after that filter?* A capped-then-filtered source silently drops the caller's own rows once other users produce enough newer ones — the caller's data does not merely fall past the cap, it never enters the window at all.

The trap is that two sources can look symmetric at the call site (`findByUserId(...).slice(0, 50)` beside `getJobs({ type, limit: 50 })`) while only one of them is identity-scoped at the query. Symmetry of shape is not symmetry of semantics.

Note what this check is NOT: "reproduce it with two users". Multi-user reproduction is expensive and, in a single-user dogfood, impossible — which is exactly why the bug survives to production. The structural question above is answerable while writing the code, alone, without test data. (Lesson: Sprint 2026-08-18 PR [#1357](https://github.com/ms2sato/agent-console/pull/1357) — the notification feed's deletion composer fetched the 50 most recent jobs across ALL users and then filtered by username. Found by the Architect's audit, not by the acceptance check or any test; the delegate's own retrospective identified the missing question and its two-line answerability.)

**Grep for sibling call sites before implementing root-cause fixes.** When a fix changes a pattern (e.g., removing defensive invalidation, changing a contract, renaming a helper), grep the repository for all sites using the same pattern. If sibling sites exist, present a bundle-or-leave decision to the owner with Option A (bundle the sibling fixes for contract consistency) and Option B (leave them for a follow-up). Do not silently leave siblings inconsistent with the new contract.

**Pattern existence is not pattern appropriateness.** The sibling grep above has a second use — judging a flagged pattern — and there it is necessary but not sufficient. Finding N existing occurrences of a pattern proves only that the pattern exists, not that it is the one new code should follow; when the grep reveals that MULTIPLE idioms coexist for the same job, explicitly ask "which one is currently correct, and why does each exist?" before treating any of them as the established idiom (this is the sibling-grep corollary of "Do not blindly follow existing patterns" above). For low-materiality findings especially, complete the whole pass — sibling grep AND the why-does-each-idiom-exist question — in ONE round before ruling: a verdict issued on partial evidence invites a flip, and the round-trip cost of verdict flips can exceed the importance of the finding itself. (Lesson: 2026-07-30, PR #1252 — a test-file cast flagged as a violation flipped five times in one day between three reviewers, each ruling on partial evidence: asserted from rule text without a grep; the grep found numerous existing occurrences and flipped it to "established idiom"; a second look found a cleaner coexisting idiom, flipping it back. Final state — new code uses the cleaner idiom, legacy sites went to a neutrally-framed follow-up (#1253) — was available from the start had the full pass run once.)

**Sweep for what your change invalidated, not only for what it asserts.** The sibling grep above looks outward from the change; this looks back at what the change just made false. Verifying every claim *this* change makes — a natural discipline — cannot even in principle reach a paragraph written last month that your change has falsified. Nobody asserted it today, so nobody checks it today.

**Mechanise it like the sibling grep**: take the identifiers the change touched — setting keys, option names, renamed symbols — and grep the docs for them.

(Lesson: Sprint 2026-08-28 PR [#1403](https://github.com/ms2sato/agent-console/pull/1403) — after an earlier false "already updated" report, the delegate began mechanically checking every doc claim the PR *makes*. Two stale rows survived anyway: a table showing a setting as hard-coded `false` after the engine began deriving it, and the same row omitting two options the PR added. Neither was a claim the PR made; both were claims it broke. One grep on the setting key would have found both.)

**When a reviewer hands you a phrasing of the falsified claim, re-run the sweep on that phrasing before fixing the line it came attached to.** The mechanised grep above is keyed on identifiers, which is what makes it runnable — and is also its ceiling. A claim lives in prose too, and prose that says the same thing may share no token with any identifier: *"clears the id"*, *"never retried"*, and *"the session is not there"* are one assertion in three vocabularies, and a grep for the first two cannot reach the third. Nobody can enumerate a claim's paraphrases up front, which is why the identifier sweep is the one that gets written down and the paraphrase sweep does not happen at all.

A review comment is where a paraphrase arrives for free. Spend it while the finding is still open: grep for that wording, then fix. One command, aimed at the instances nobody is looking for — the reviewer has already found theirs.

(Lesson: Sprint 2026-08-29 PR [#1438](https://github.com/ms2sato/agent-console/pull/1438) — the PR measured that the SDK's session store swallows read errors, so its "not found" verdict is not proof a session is absent, and wrote that into the design doc and the premise ledger. A doc comment in the same diff still described the pre-flight as reporting *"that the session is not there"* — and reading that verdict as absence is precisely the reasoning the PR existed to remove, so the defect stood restated inside the fix. A second comment described the id-retention rule as it had been before a mid-PR ruling narrowed it. The delegate had run the identifier sweep deliberately and reported doing so; it matched `clears` and `never retried` and could not match either phrasing. CodeRabbit flagged one instance of the absence wording, and re-sweeping on that wording found another it had not.

**Both instances were added lines in the same reviewed diff** — confirmed from `git diff`, not assumed — so the review was partial *within* the class it catches best and within the diff it actually read. That is the measured reason this step is not optional politeness: a review is not exhaustive on the claim it just flagged, so "the reviewer would have caught the others" is false at the only moment it matters.)

**Before applying a criterion, ask whether the criterion governs this object.** Applying a criterion carefully is not the same as applying the right one, and the second failure hides inside the first — the work looks rigorous, the steps are followed, the answer is wrong. Usually it is a proxy standing in for a definition, or a rule borrowed from a neighbouring situation that shares a shape but not a subject.

(Lessons, both Sprint 2026-08-28: a delegate ran the en-passant three-condition test on whether to name an implicit guard and correctly found it failed the third — but en passant governs *a sibling defect noticed in passing*, and this was a contract surface the PR's own change had made load-bearing. Separately, the Orchestrator scoped an Issue's file list from a diff-size filter and shipped it as the class definition; two files with the same defect but larger diffs fell outside, excluded for "not a one-line change" rather than "not an instance".)

**Ask when uncertain.** When uncertain about a design decision, ask the user for confirmation.

**Validate task assumptions before implementing.** Understand WHY the task is needed. If a task assumes existing behavior that seems questionable, verify whether that assumption is correct before implementing.

**Specify boundary values in design briefs.** When writing acceptance criteria for a contract (predicate, validator, classifier, aggregator), explicitly state the expected behavior at boundary values: empty input (`length === 0`), single element, all-success, all-failure, mixed terminal / non-terminal. Vacuous truth (`[].every() => true`, `[].some() => false`) is a recurring agent blind-spot — initial test sets typically cover the "happy path with 2-3 elements" and miss the empty case, then CodeRabbit catches it after a round trip. Pre-specifying boundary expectations in the AC closes the gap before delegation. (Lesson: Sprint 2026-04-27 PR #703 race condition + PR #704 empty rollup, both flagged by CodeRabbit not by the agent's initial test set.)
